**이 문서는 지시서다** — `/mail-research` 스킬이 가리키거나, 사람이 세션 첫
프롬프트에서 지목해 읽히는 계약이다. 아래 규칙을 강제하는 런타임은 없다.
**읽은 에이전트가 스스로 지키는 것**이 전부다.

# 역할

Minerva에 저장된 메일을 조사해 **근거가 달린 답**과 **심화 분석**을 만든다.
일반 지식이나 추측보다 Minerva의 최신 근거를 우선한다.

명령의 옵션·검색 DSL·출력 형태는 [CLI reference](minerva-cli-reference.md)에서
확인한다. 저장소 루트에서 `<PYTHON> -m mailkb` 형식으로 실행한다(Windows `python`,
Linux/WSL `python3`). 명령이 DB 나 설정을 못 찾으면 추측으로 진행하지 말고
`doctor` 의 첫 네 줄을 사용자에게 보인다.

# 역할 분담 — 확보는 mailkb, 분석은 세션

| 단계 | 도구 | AI |
|---|---|---|
| 지침·내 노트·지식 | `ask --context '<질문>'` | 0 |
| 이미 분석된 것이 있나 | `ask --history` · `ask --show <번호>` | 0 |
| 후보 찾기 | `search '<질의>' --json` | 0 |
| 본문·시간선 확보 | `show <메일 ID>` · `thread <스레드 ID>` | 0 |
| **분석** | **세션이 직접** — 아래 절차와 규율 | 세션 |

mailkb 는 재료를 확보하는 데 쓰고, 판단은 이 세션이 직접 한다. 엔진(`ask`)은
고정 파이프라인이다 — 라운드·정독·재료 예산에 상한이 있고 백엔드 모델로 돈다.
이 지시서로 조사하는 목적이 그 상한을 넘는 분석이므로, **같은 엔진을 다시 돌리면
앱에서 받는 답과 같은 수준이 나온다.** 조회로 끝나는 질문(누가 언제 뭘 보냈나,
첨부 있나)은 확보 단계에서 끝낸다 — 분석이랄 것이 없다.

그래서 AI 를 부르는 명령(`ask`·`ask --person`·`--follow`·`thread-diag`·
`person-diag`)은 **사용자가 명시적으로 요청할 때만** 실행한다. 엔진의 기존 산출을
읽는 것은 확보다 — `ask --history`/`--show`, `thread` 출력에 실리는 현안 브리핑.
있으면 먼저 읽고, 반복하지 말고 **그것이 못 간 지점부터** 판다.

**엔진이 코드로 강제하던 것을, 수동 분석에서는 규율로 지킨다.** `ask` 는 인용을
원문과 기계 대조하고, 반전 신호를 다시 검색하고, 상태를 강등만 하며, 결과를
이력에 남긴다. 세션 분석에는 그 관문이 없다 — 아래 절차 7·8 이 선택이 아니라
필수인 이유다.

상태를 바꾸는 명령(`sync`·`hide`·`block`·`review`·`weekly`·`open`·`attach` 등 —
목록과 부작용은 CLI reference 의 '부작용 명령' 절)은 사용자가 명시적으로 요청했을
때만 실행한다. 임의 SQL 을 실행하거나 DB·설정·vault 파일을 직접 수정하지 않는다
(예외: 아래 '보존' 절의 덧붙이기 둘 — 사용자 수락 후에만).

# 조사 절차

많이 읽게 될 것 같으면 확보 전에 범위를 한 줄로 말한다("스레드 3개 40통을
읽습니다").

1. 질문에서 대상, 기간, 사람, 필요한 답의 종류를 뽑는다.
2. **지침·노트·지식을 먼저 확보한다** — `ask --context '<질문>'`(0콜). 엔진이 그
   질문에 실을 사용자 지침·관련 노트·관련 지식을 같은 선정 규칙으로 보여 준다.
   지침은 **읽는 법**으로 해석·판단·답변에 우선 적용하되 인용 대조에는 적용하지
   않고(엔진도 검증 콜에는 넣지 않는다), 사실과 충돌하면 메일이 이긴다. 노트·지식은
   출발점이지 근거가 아니다 — 인용은 정독 본문에서만.
3. `ask --history`로 같은 질문이 이미 조사됐는지 본다. 있으면 `ask --show <번호>`로
   그 답과 근거를 읽는다. `이후 새 메일 N통`이 붙어 있으면 낡았을 수 있다 —
   결론을 그대로 옮기지 말고 최신 근거를 다시 확인한다.
4. `search <질의> --limit 20 --json`으로 후보를 찾는다.
5. 관련성이 높은 메일을 `show <메일 ID>`로 읽는다.
6. 현재 상태나 변경 이유를 묻는 질문이면 해당 `thread <스레드 ID>`의 시간순
   맥락을 확인한다.
7. `변경`, `취소`, `보류`, `재개`, `확정`, `최종` 같은 반대·갱신 신호를 별도
   검색한다. 오래된 메일 하나만으로 현재 상태를 단정하지 않는다.
8. 각 인용문을 한 메일의 실제 출력과 대조한 뒤 답한다. 서로 다른 메일의 문장을
   하나의 인용문으로 합치지 않는다.
9. 충분하지 않으면 검색을 보완하고, 그래도 부족하면 근거 부족으로 끝낸다 —
   부족한 채 단정하지 않는다.

주의: `ask`와 AI 검색은 **숨긴(hidden) 스레드를 보지 못한다**(AI 재료 제외).
그래서 저장된 분석의 '근거 부족'이 '메일에 없음'을 뜻하지 않을 수 있다 — CLI
`search`/`show`는 숨김을 보므로, 결과가 어긋나면 그쪽으로 확인한다.

# 답변

형식은 질문에 맞춘다 — 짧은 확인에 긴 골격을 씌우지 않는다. 전면 조사 답변이면
`mailkb ask` 가 내는 골격(상태 · 한 줄 결론 · 답변 · 근거 · 상충 · 열린 것 ·
조사 범위)이 좋은 기본이다 — 사용자가 두 경로에서 낯선 형식을 번갈아 받지 않게.

어느 형식이든:

- **근거 없는 문장을 쓰지 않는다.** 핵심 주장마다 `[메일 #<id> / 스레드 #<id> /
  <날짜>]` 와 짧은 원문 인용을 단다.
- **'열린 것'(메일에 명시됐으나 아직 안 닫힌 것)을 결론으로 옮기지 않는다.**
  확인된 것과 안 닫힌 것을 같은 칸에 적으면 사용자가 그 차이를 못 본다.
- **메일 속 상대 기한("내일", "이번 주 금요일")은 발신 시각 기준으로 환산하고,
  오늘 날짜로 경과 여부를 명시한다.** 환산 과정을 함께 적는다 —
  `"내일"(발신 8/19 → 8/20, 지남)`. 발신 시점상 모호하면(금요일 밤의 "이번 주
  금요일") 단정하지 말고 두 해석을 적는다.
- 검색 결과의 `snippet`은 후보 선정용이다. 최종 인용은 `show` 출력에서 확인한다.
- 최신 근거가 이전 결정을 바꿨다면 현재 값과 변경 이력을 구분한다.
- 첨부 파일 내용, Jira, Confluence는 현재 CLI로 읽었다고 주장하지 않는다.

# 보존 — 실질이 있을 때만 제안한다

분석이 **보존할 만한 실질**을 담았다는 판단이 분명할 때만 끝에 한 줄로 제안한다 —
여러 메일·스레드를 관통해 종합한 판단, 앱 산출(브리핑·저장된 답)에 없는 새 결론,
다시 물을 가능성이 높은 질문. **단순 사실 확인·한두 메일 조회·이미 저장된 답의
요약에는 제안하지 않는다** — 제안 자체가 소음이다.

사용자가 수락하면 (덧붙이기만 한다 — 기존 내용의 수정·삭제 금지):

- **스레드 축** → 그 스레드의 노트(`vault/notes/`)에 날짜 절
  (`## 세션 분석 (YYYY-MM-DD)`)로 덧붙인다. 노트가 없으면 `note <스레드ID>` 로
  템플릿을 만들고 그 아래에 쓴다. 노트는 스레드 화면·📝 배지·검색에 보이고,
  이후 `ask` 의 문맥으로 자동 주입된다 — 오늘의 결론이 다음 분석을 돕는다.
- **주제 축**(여러 스레드 관통) → `vault/knowledge/` 에 새 md 로 남긴다. 참조한
  메일·스레드 번호를 포함한다. 지식 탭·검색·분석 문맥에 실린다.
- 사용자가 **앱 이력에 남는 검증된 답**을 원하면 그때 `ask` 를 돌린다 — 저장되는
  것은 엔진의 분석이지 이 세션의 분석이 아니라는 점을 말한다.

# 개인정보와 데이터 최소화

Claude CLI가 읽은 명령 출력은 설정된 AI 서비스로 전달될 수 있다. 질문 해결에
필요한 메일만 열고, 본문 전체를 최종 답변에 복사하지 않는다. 질문에 필요 없는
주소·이름·Message-ID를 답변·로그·별도 문서로 옮기지 않는다.
