## 1. 무엇을, 왜

**문제.** 업무 메일은 조직의 결정이 실제로 일어나는 곳인데, 메일 클라이언트는
그것을 기억해 주지 않는다. 6개월 전 "그래서 최종 결론이 뭐였지"를 답하려면
사람이 스레드를 뒤져야 하고, 답장을 기다리는 공이 어디서 멈췄는지도 머릿속에만 있다.

**입장.** mailkb는 메일 클라이언트를 대체하지 않는다. 읽고 쓰는 것은 Outlook에서
그대로 하고, **Outlook이 못 하는 것만** 한다.

| Outlook이 하는 것 | mailkb가 하는 것 |
|---|---|
| 수신·발신·보관 | 아카이브 인덱스(전문검색) |
| 폴더·규칙 | 스레드 지식화(누적 요약·신호) |
| 알림 | 하루 끝 회고 |
| — | 결정의 장기기억(사람이 승인) |
| — | 근거가 달린 질의응답 |

**이름.** `mailkb` = mail knowledge base. 웹 UI의 표시 이름만 **Minerva**이고,
코드·폴더·명령은 전부 `mailkb`다.

### 설계 원칙 다섯

1. **표준 라이브러리만.** 코어에 서드파티 의존이 없다. Windows의 `pywin32`가
   유일한 예외이고 `sources/outlook_com.py` 안에 격리돼 있다. 사내 PC에서
   패키지 설치 승인을 받는 비용이 기능 하나보다 비싸다는 판단이다.
2. **AI는 opt-in.** 결정론 경로가 항상 먼저 있고, AI는 그 위에 얹히는 층이다.
   관문은 **`--ai` 플래그 또는 명령 자체**다 — `ask`(분석)와 `diagnose`(백엔드 점검)는
   그 자체가 AI 명령이라 플래그가 없다. 그 밖의 모든 명령은 `--ai` 없이 네트워크
   호출이 0이다(§8 명령표의 AI 열이 기준).
3. **AI 산출은 초안, 확정은 사람.** 수확된 결정은 '반영 대기'로 쌓이고 사람이
   반영/유보를 누른다. 반영된 것만 검색·회고의 재료가 된다.
4. **인용은 코드가 검증한다.** AI가 메일을 인용하면 그 문자열이 실제 본문에
   있는지 코드가 대조하고, 통과한 것만 남긴다. 환각 차단이 프롬프트 지시가 아니라
   실행 경로에 있다.
5. **재수집을 강요하지 않는다.** 파생 로직이 바뀌어도 사용자가 Outlook에서
   다시 긁을 필요가 없다. 회사 PC의 전체 재수집은 수십 분짜리 작업이다.

## 2. 전체 흐름

```
Outlook (원본·hot, COM)
      │
      │ sources/  ── MailRecord 스트림 (시간순)
      ▼
   store.ingest ──┬─ clean: HTML→마크다운 · 인용 제거 · 서명 제거
                  ├─ features: 문장 단위 신호 비트
                  ├─ terms: 인물별 어휘 피처
                  └─ FTS5(trigram) 색인
      │
      ▼
   SQLite (db.sqlite) ── 메타 + 신규내용 + 누적요약 + 장기기억 + 파생 상태
      │
      ├── CLI:  ls · search · show · thread · review · ask · weekly · stats
      ├── Web:  Minerva (localhost, 좌/우 분할 SPA)
      └── vault/ (마크다운)  daily/ · weekly/ · notes/
```

- 원본과 첨부는 Outlook에 그대로 둔다. `GetItemFromID`(EntryID)로 O(1) 참조하고,
  폴더 이동으로 EntryID가 바뀌면 Message-ID(영구)로 재검색한다.
- **메일 본문과 파생 지표는 재생성 가능하다** — 원본이 Outlook에 있으므로 지우고
  다시 `sync`하면 돌아온다. 그러나 `db.sqlite`는 **사람의 산출물도 함께 담는다**.
  그것들은 재수집으로 복구되지 않으므로 **DB 파일 삭제는 백업 없이 되돌릴 수 없다.**

  ```
  sync 로 복구됨      messages · message_html · people · messages_fts
                     threads(요약·스레딩) · 모든 파생 테이블
  복구 안 됨          decisions(장기기억) · ask_cache(분석 이력)
  (백업 필수)         people_dossier(인물 요약) · action_overrides(신호 해제)
                     threads.flagged / threads.hidden · vault/
  ```

### 토큰 깔때기

AI 비용은 입력량에 비례하므로, AI에 닿기 전에 네 번 줄인다.

```
① 노이즈 필터      발신자·도메인·제목 패턴으로 제외
② 인용 제거        "새로 쓰인 부분"만 남김  (합성 282통 실측 절감 86%)
③ 롤링 요약 캐시   스레드 요약은 신규분만 갱신
④ 하루 1회 분석    실시간 호출 없음
```

②가 핵심이다. 검색 품질과 AI 토큰을 동시에 개선한다 — 12통짜리 스레드에서
같은 인용문이 12번 색인되는 것을 막는다.

## 4. 데이터 모델

`db.sqlite` 한 파일에 19개 테이블 + FTS5 가상 테이블 하나.

### 원본 성격

**원본은 Outlook 에 그대로 둔다 — 여기는 색인이지 사본이 아니다.** 로컬 보존
연한에 제한이 없음을 확인하고 `.eml` 복사를 폐기했다. COM 이 어차피 원본 MIME 을
주지 않기도 한다(MAPI 저장이라 재조립본이 된다).

| 테이블 | 내용 |
|---|---|
| `messages` | 메타 + `new_content`(인용 제거 본문) |
| `message_html` | 표시용 정제 HTML — 큰 blob을 분리해 `messages` 행 스캔을 가볍게 유지 |
| `threads` | 스레드 + 누적 요약. **단 `flagged`·`hidden` 두 컬럼은 사용자 상태**라 재수집으로 복구되지 않는다 |
| `people` | 인물 집계 |
| `messages_fts` | FTS5 **trigram**(한글 부분일치). 구버전 SQLite는 `unicode61` 폴백 |

### 사람의 산출물 (재생성 불가)

| 테이블 | 내용 |
|---|---|
| `decisions` | 장기기억 — 결정 원장(반영/유보/후보) |
| `action_overrides` | **신호 해제만** — `dismiss_action`(회신 필요·확인 후보·⏰), `dismiss_deadline`(⏰만). 숨김·플래그는 여기가 아니라 `threads`에 있다 |
| `people_dossier` | 인물 요약(AI 산출) |
| `ask_cache` | 분석 문답 이력 |

`action_overrides`는 해제 당시의 요청 메시지(`source_id`)에 키가 걸려 있어, 같은
스레드에 새 요청이 오면 자동으로 무시된다 = **신호 자동 복귀**. 스레드 전체를
덮는 숨김과 달리 그 요청 건만 끄는 장치다.

### 파생 (언제든 버리고 다시 만듦)

`message_features`, `thread_state`, `message_term_features`, `message_term_bags`,
`message_term_subject_delta`, `person_term_window`, `people_word_profiles`,
`distill_signals`, `ai_search`, `sync_state`

`reclean_backup` 은 파생이 아니다 — 절단 규칙 승격이 `new_content` 를 덮기 전의
원본이고, `sync` 는 이미 있는 메일을 건너뛰므로 **재수집으로 복원되지 않는다**.
`from_version` 이 '어느 버전 직전의 값인지'를 적는다(만료 후 다시 담긴 행은 최초
원본이 아니다). `RECLEAN_BACKUP_DAYS`(45일) 뒤 sync 의 프룬 훅이 지우며, 이 만료는
`image_retain_days` 설정과 무관하다. 복구 SQL 은 스키마 주석에 있다.

### 재수집을 피하는 장치

파생 테이블은 `ALTER`하지 않고 **드롭 후 재생성**한다(SQLite에 
`ADD COLUMN IF NOT EXISTS`가 없다). 재료가 전부 `messages`에 있으므로 Outlook을
다시 긁을 필요가 없다. 무효화는 **세 개의** 버전 키가 판단한다
(`clean_version` 은 앞의 둘을 캐스케이드로 무효화한다).

| 키 | 계산식 | 불일치 시 |
|---|---|---|
| `_feature_version()` | `FEATURE_VERSION` + `sha256(my_addresses + my_names)` | `message_features`·`thread_state` 재생성 → 전 메시지 재분류 → 행동 상태 재접기 |
| `_action_version()` | `sha256(ignore_senders + blocked_senders + subject_noise_strong)` | 본문·피처는 건드리지 않고 **행동 상태만 재접기** (1만 통 기준 ~9초 → ~85ms) |

배정 규칙은 **"누가 그 값을 읽는가"**다. `classify_message`가 읽으면 feature 버전,
`_is_hard_noise`가 읽으면 action 버전, 질의 시점에만 읽으면(예: `external_allowlist`)
둘 다 아니다.

#### 인물 어휘 지도는 3단계로 따로 무효화한다

어휘 파이프라인은 재계산 비용이 단계마다 크게 달라, 위 두 키와 **별개로** 세 단계를
쓴다. 점수·표시 규칙만 바뀌었을 때 본문을 다시 토큰화하지 않으려는 것이다.

| 단계 | 키 | 무엇이 바뀌면 | 무엇을 다시 만드나 |
|---|---|---|---|
| ① 토큰 | `_term_feature_version()` = `WORD_FEATURE_VERSION` (+ 분석 창 검사) | 추출 규칙, `[dossier] window_weeks` | **본문 재토큰화** — `message_term_*`·`person_term_window` 전부 비우고 최근 창의 수신 본문을 다시 읽는다. 가장 비싸다 |
| ② projection | `_term_bag_version()` = sha256(`WORD_FEATURE_VERSION`, `WORD_BAG_VERSION`, `window_weeks`, 주소록 이름, 추가 불용어) | 가중·집계 방식, 이름·불용어 설정 | bag 재구축. 토큰은 그대로 쓴다 |
| ③ 표시 프로필 | `terms.profile_signature()` = `WORDMAP_VERSION` + sha256(위 둘 + 불용어 + 대조 집단 + `top_n` + 인물명 + 코퍼스 지문) | 점수·표시 규칙, 비교 대상 인물 집합 | 그 인물의 `people_word_profiles` 행만 재계산. 가장 싸다 |

①이 무효화되면 ②의 키도 함께 지워져 아래로 연쇄한다. 반대로 ③만 바뀌면 위 둘은
건드리지 않는다. **새 규칙을 넣을 때 어느 단계 상수를 올릴지가 곧 재계산 비용의
선택**이므로, 표시만 바꾸면서 `WORD_FEATURE_VERSION`을 올리면 불필요한 재토큰화를
전 사용자에게 강요하게 된다. `people_dossier`만 예외로 `ALTER` 경로를 쓴다 — AI 산출이라
재구성이 불가능하기 때문이다.

### 수집 불변식

- 청크 커밋마다 어휘 피처와 `last_sync` 워터마크를 **함께** 커밋한다 → 중간에
  죽어도 일관된 접두부가 남는다
- `sync_state`에는 **역할이 다른 두 시각**이 있다. `last_sync`는 수집한 메일의
  `sent_on` 워터마크라 새 메일이 0통이면 안 움직인다. `last_sync_checked_at`은
  **성공한 실행 시각**이라 0통이어도 전진하고 실패하면 전진하지 않는다. 화면의
  "동기화 HH:MM"은 뒤엣것이다 — 앞엣것을 쓰면 "방금 돌렸는데 시각이 그대로"가 된다
- `Store.basis_info()`는 사이드바가 **매 렌더** 부르므로 `stats()`를 쓰면 안 된다.
  `stats()`에는 `SUM(LENGTH(new_content))`가 있어 본문을 전부 훑는다(7.5만 통에서
  20ms 대 0.008ms). 인덱스로 끝나는 `COUNT(*)`와 키 조회만 한다
- `message_id UNIQUE` → 재실행이 멱등
- `PRAGMA synchronous=NORMAL` — DB가 다시 받아올 수 있는 캐시라 정당하다
- 전체 `VACUUM` 금지(단일 스레드 웹 서버가 멈춘다). `auto_vacuum=INCREMENTAL`만

## 5. AI 계층

### 계약 하나 — `review.ai_run`

```python
ai_run(cmd, prompt, timeout=300, retries=2,
       *, system_prompt=None, json_schema=None, effort=None,
       effort_flag=None, on_event=None, cancel=None) -> str
```

**프롬프트를 stdin으로 넣고 stdout을 받는다.** 그게 전부다. SDK도, API 키도,
HTTP 클라이언트도 없다. 인증·프록시·모델 관리는 `opencode`/`claude` 같은 CLI에
무임승차한다.

- 타임아웃·비정상 종료·빈 응답 → `AIError`, 2s·4s 백오프로 재시도
- 명령을 못 찾으면(`FileNotFoundError`) 재시도 없이 즉시 `AIError`
- 밖으로 나가는 예외는 셋: `AIError`(재시도 후 실패) · `AICancelled`(사용자 중지) ·
  `AIAuthError`(백엔드 인증 만료). 뒤의 둘은 `AIError` 하위가 **아니다** — 콜 단위
  graceful 삼킴(`except AIError`)을 전부 통과해 파이프라인 꼭대기에서 멈추기 위해서다.
  인증 만료 판정은 **백엔드 채널(stderr·CLI 오류 봉투)만** 본다 — 모델 stdout 에는
  사용자 메일에서 나온 문장이 실려, 판정에 넣으면 정상 응답이 오진된다
- `shutil.which`로 해석 — Windows의 npm `.cmd` 셰임 때문에 필요하다
- `encoding="utf-8", errors="replace"` — cp949면 이모지에서 죽는다
- claude 는 역할을 `--system-prompt` 로 분리 전달하고 `--tools ""`·
  `--no-session-persistence` 로 도구·세션 지속을 끄며, `--setting-sources
  user` 로 저장소 CLAUDE.md 주입(콜당 ~4k 토큰)을 차단한다. **setting-sources
  값은 반드시 `user`** — `""`(전부 제외)는 user 설정(~/.claude/settings.json)의
  env 까지 건너뛰는데, 그 env 가 모델 라우팅(별칭 해석·Bedrock 경유)을
  정의하는 환경에서는 `--model` 별칭이 다른 모델을 찾다 전 모델이 실패한다
  (2026-07-28 실기기 확정 — 실사고 원인). 그 밖의 stdin 어댑터는 같은 정보를
  `[SYSTEM]` 블록으로 prompt 앞에 붙인다. `--json-schema` 는 롤백 유지(JSON
  계약은 프롬프트 지시 + 관용 파서). **effort 는 opt-in 으로만 재개**(2026-08-02):
  `[ai.backends.<name>] effort_flag = "--effort"` 를 선언한 백엔드에만
  `<플래그> high` 가 붙는다 — 사고 원인은 `--setting-sources ""` 로 판명됐지만
  `--effort` 의 실기기 지원은 여전히 미검증이라, 미선언(기본)이면 argv 가
  종전과 같다. 플래그·값은 단일 토큰만 허용(cmd.exe 셔틀 보호). 실기기에서
  켜기 전 `diagnose` 로 1콜 검증을 권장.
- **`--system-prompt` 값은 한 줄로 접어서 보낸다(개행 금지).** Windows 의 npm
  CLI 는 `.cmd` 셔틀이라 실행이 cmd.exe 를 거치는데, cmd.exe 는 명령줄의 개행에서
  줄을 끊는다 — 여러 줄 값을 주면 첫 줄만 전달되고 **그 뒤 인자가 통째로 사라진다**
  (`--tools`·`--setting-sources`·스트리밍 플래그까지). 2026-07-28 실기기 확정:
  이 때문에 stream-json 플래그가 유실돼 주간 보고·분석이 전부 실패했다(같은 호출이
  개행만 접자 정상 수신). 리눅스는 execve 라 개행이 무해해 개발 환경에서는 드러나지
  않으므로 **플랫폼 분기 없이 항상 접는다** — 개발에서 검증한 것이 실기기에서 도는
  것과 같아야 한다. 같은 이유로 시스템 프롬프트 상수에는 cmd.exe 특수문자
  (`% & | < > ^ "`)를 넣지 않는다(회귀 테스트가 지킨다).
- 웹의 모든 백그라운드 잡(일간 회고·AI 검색·주간 보고·분석·인물 요약·메일
  동기화)은 **같은 대기 카드**(`web._job_wait_card`, prefix `rv/ai/wk/ask/dz/sy`)로
  그려진다 — 스피너·제목·실모델 배지·진행바(결정론 `단계 n/N` 또는 인디터미닛)·
  단계 문구·수신 줄·작성 중 초안·경과·중지. 관측되지 않는 슬롯(비스트리밍
  백엔드의 수신·모델)은 비고 CSS `.waitslot:empty` 가 그 줄을 숨긴다. 폴링은
  `app.js patchJob(tmp, host, prefix)` 하나로 슬롯만 제자리 패치한다(전체 교체는
  스피너·경과를 되감는다). 새 잡을 만들면 `_new_job`/`_job_start`/`_RUNNING_MARKERS`
  세 곳에 등록한다 — 마지막 것이 빠지면 JS-off 환경에서 그 화면만 안 넘어간다.
- 중지는 **스트리밍(claude) 경로에서만 즉시** 듣는다. 블로킹 경로는 진행 중인
  호출이 끝난 뒤 멈추므로 카드가 그렇게 말하고(`_cancel_hint`), 중지를 누른 뒤에는
  수신 줄이 '중지 요청됨'으로 바뀐다 — 안 그러면 버튼이 안 먹은 것처럼 보인다.
- 스트리밍 경로에서 **이벤트가 하나도 안 오면 원시 stdout 을 답으로 쓴다**
  (`plain_output` 으로 로그만 남기고 성공 처리) — 플래그 유실·구버전 CLI 로
  진행 표시를 잃는 것은 기능 실패가 아니다. 단 `{"error": …}` 오류 봉투는
  답이 아니므로 `AIError` 로 올린다.
- 실패는 `<home>/logs/ai_error.jsonl` 에 남는다(명령·exit·stderr/stdout 꼬리·
  소요·프롬프트 크기) — **재현 없이 로그에서 원인을 확인한다.** claude -p 는
  오류를 stdout 으로 내는 경우가 많아 stdout 꼬리도 오류 메시지에 싣는다.
  `[ai] error_log=false` 로 끈다.
- `on_event` 를 주면 **claude CLI 에 한해** `--output-format stream-json` 으로
  수신을 스트리밍하고 중립 이벤트를 흘린다 — `model`(init 의 실모델 ID) ·
  `phase`(thinking/writing) · `delta`(수신 문자 수, writing 은 텍스트 포함) ·
  `retry`. 반환값·오류 계약은 그대로다(결과는 여전히 완결 텍스트 하나).
  다른 백엔드는 이벤트 없이 기존과 동일하게 동작한다 — 웹 대기 화면(2a
  수신 표시 · 실모델 · 작성 중 초안 미리보기 · 30초 무수신 경고)이 이 이벤트의
  소비자다. 미리보기는 검증 전 초안임을 흐림+라벨로 명시한다.
- `cancel`(threading.Event) 이 켜지면 진행 중 프로세스를 죽이고
  `AICancelled` 를 올린다 — `AIError` 와 다른 타입이라 graceful 삼킴 경로
  (weekly `_ai`, 웹 폴백)를 타지 않고 파이프라인 전체가 멈춘다. 취소는
  실패가 아니라 사용자의 결정이므로 부분 결과를 저장하지 않는다.
  웹 대기 화면의 **중지** 버튼(`POST /weekly/cancel`·`/ask/cancel`)이 켠다.

이 계약 덕분에 백엔드는 교체 가능하다. `tools/bedrock_run.py`가 반대편에서
같은 계약을 구현한 예다.

### 작업별 백엔드 라우팅

작업마다 비용·품질 요구가 달라 백엔드를 나눠 부른다. `config.toml`의 `[ai]` 항목이나
웹 **설정** 화면에서 바꾼다(설정 화면 변경은 `overrides.json`에 남아 재시작 불필요).

| 설정 키 | 기본 | 쓰는 곳 |
|---|---|---|
| `[ai] summary` | `sonnet` | 누적 요약 · 수확 · 하루 요약 |
| `[ai] search` | `sonnet` | AI 검색 — 질의 번역 · 재순위 · 심층 읽기 |
| `[ai] ask` | `[ai] search` 상속 | **분석** — 조사 · 답변 작성 · 의미 검증 |
| `[ai] weekly` | `[ai] summary` 상속 | 주간 보고 — 카드 · 토픽 · 서술 · 검증. 주 1회 무거운 호출이라 opus 지정 후보 |
| `[ai] default` | `internal` | 위로 라우팅되지 않는 호출 |

`ask`가 `search`를 상속하는 것은 호환 때문이다 — 분석 전용 키가 생기기 전에는 둘이
한 설정을 공유했다. 번역 위주인 AI 검색과 한 질문에 최대 12콜을 쓰는 분석은 요구가
다르므로, 필요하면 따로 지정한다. CLI `ask --backend`는 **그 실행 한 번만** 덮어쓰고
저장된 설정이나 사이드바 표시를 바꾸지 않는다.

저장된 답의 `scope.backend`는 **그 답을 실제로 만든 백엔드**다 — 나중에 설정을 바꿔도
과거 답의 기록은 그대로 남는다. `scope.model`(분석)과 주간 보고 푸터의 `모델 …`은
한 단계 더 간다 — 백엔드 *이름*(opus 등)은 움직이는 별칭이라, 스트리밍 init 이
알려준 **실모델 ID 실측값**을 남긴다(비스트리밍 백엔드는 빈 값).

### AI를 쓰는 곳과 실패 시 동작

| 기능 | 모듈 | AI 실패 시 |
|---|---|---|
| 누적 요약·하루 요약 | `review.py` | 결정론 리뷰는 그대로 나온다 |
| 결정·신호 수확 | `distill.py` | `None` 반환, 워터마크 안 전진 → 다음 실행에 재시도 |
| 인물 요약 | `distill.py` | 기준 카운트 안 전진 → 재시도 |
| 분석(질의응답) | `ask.py` | `AIError`를 올려보내고 호출부가 **일반 검색으로 폴백** |
| 주간 보고 | `weekly.py` | 삼키고 결정론 뼈대만 |
| AI 검색 | `review.py` | 일반 검색 |

원칙은 하나다 — **결정론 경로는 항상 살아남는다.**

### AI 프롬프트에서 빠지는 것 — 숨긴 스레드

숨김(`hidden`)은 "조용히"라는 뜻인데, 종전에는 `weekly.collect` 만 걸렀다 —
숨긴 스레드의 원문이 롤링 요약·수확·분석·AI 검색·인물 요약 프롬프트에 그대로
실렸다. 이제 **AI 재료를 조립하는 모든 경로**가 `store.hidden_thread_ids()` 로
거른다(검색 후보·seed·정독·스레드 전개·본문 심사·도시에 재료·문체 표본·디제스트).

- **예외 하나** — 사용자가 그 스레드의 메일에서 직접 [분석]을 누른 경우
  (`ask(allow_tids=…)`). 명시 의도가 '조용히'보다 우선한다. 확장 검색이 잡는
  **다른** 숨김 스레드는 여전히 제외된다.
- **표시 축은 불변** — 결정론 보고 뼈대·메일함 숨김 탭·`store.search`(일반
  검색)는 그대로다. 제외는 AI 축이다.
- **한계**: 숨기기 **이전**에 만들어진 산출물(ask_cache 의 옛 답·기존 롤링
  요약·과거 주간 .md)은 소급 정화하지 않는다(재수집 강요 금지와 같은
  트레이드오프). 그리고 hidden 은 새 수신 메일이 오면 자동 해제되므로 영구
  기밀 장치가 아니다 — 발신자 단위 영구 제외(ai_exclude 목록)는 검토 후
  보류했다(2026-08-02 사용자 결정), 필요해지면 그때 설계한다.

### AI 프롬프트에 더해지는 것 — 장기기억과 사용자 지침

- **장기기억 주입** — 사람이 승인(반영)한 결정 원장을 분석(ask·브리핑)
  프롬프트에 `[장기기억 — 문맥 전용, 인용 금지]` 블록으로 싣는다
  (`ask._memory_block`). 선정은 결정론: 질문과의 어휘 겹침 상위 5건(브리핑은
  인물 범위 결정 최신순), 겹침 0이면 블록 생략, 숨긴 스레드 결정 제외.
  '인용 금지'의 강제는 코드가 한다 — 인용 검증은 여전히 정독 본문만 통과.
- **사용자 지침(`<home>/ai-rules.md`)** — 사내 용어·우선순위 같은 자연어
  지침. 종전 수확 한 곳에서 수확 + 분석(STEP·ANSWER) + 주간(WRITE·OVERVIEW)
  으로 확장. 검증 콜(VERIFY·REPAIR·VERIFY_REPORT)에는 넣지 않는다 —
  검증기의 "외부 지식 금지" 계약을 문맥 주입이 흔들면 안 된다.

## 6. 핵심 파이프라인

### 6.1 수집 시 본문 정제 (`clean.py`)

`Store._insert` 안에서 메시지마다:

1. **`extract_new_content`** — 인용 시작점을 찾아 자른다(대시+라벨 줄, `On … wrote:`
   계열 귀속줄 6개 언어, `_{10,}`, 헤더 블록). 헤더 블록 판정은 2단 게이트다:
   From 라벨(한·영·불·독·서·이·화·일·중, 전각 콜론과 `**굵은 라벨**` 포함) 뒤
   6줄(빈 줄 제외) 안의 후속 필드 수가 **3개 이상**이어야 자른다. 발신인 줄에
   메일 주소가 있으면 2개로 낮춘다 — 문서 머리·표에는 주소가 없다. 이 기준이
   한국 공문(발신/수신/참조/제목)·물류 구간표·번역 대조표가 잘리던 오탐을 막는다.
   귀속줄(`On … wrote:`·`…님이 작성:` 등 6개 언어)도 같은 줄에 주소가 있을
   때만 인정한다.
   규칙을 넓히면 `clean.CLEAN_VERSION` 을 올린다 → 다음 열기에서 저장된
   `new_content` 를 1회 소급 재절단하고(원본은 `reclean_backup` 에 보관, 45일)
   파생 캐시를 무효화한다. 재수집은 필요 없다.
   `>` 줄 제거 → 서명·법적 고지 제거(**본문 2줄은 반드시 남긴다**) → 빈 줄 정리.
2. **`sanitize_html`** — 허용 목록 기반 태그·속성 정제, 원격 이미지 차단.
   파서가 터지면 `<pre>` + 이스케이프 텍스트로 폴백. 인용 절단도 여기서 따로
   한다: 경계 태그(`<hr>`·`border-top` 스타일 div·`divRplyFwdMsg`·Mac 컨테이너)
   뒤에 From 라벨이 오면 **후보**로 잡고, 이어지는 청크에서 후속 필드 2개를
   확인해야 자른다(라벨 한 줄로는 안 자른다). 저장된 `message_html` 은 소급
   재절단 대상도 백업 대상도 아니라 여기서의 오탐은 영구 손실이기 때문이다.
   조판용 표(스페이서)는 자르지 않고 **표시만 남긴다** — 작성자가 단
   `role="presentation"` 을 보존하고, `border`/`cellpadding`/`cellspacing` 도
   그대로 둔다. 화면 CSS 가 그 신호를 보고 테두리·패딩을 뺀다(알림 메일이 빈
   테두리 박스로 보이던 문제). 자르지 않는 이유는 같다 — 여기서의 오탐은 되돌릴
   수 없고, 표시는 CSS 를 되돌리면 그만이다.
3. **`inject_inline_images`** — 2단계를 통과한 HTML에만, cid당 한 번만 임베드.
   **정제 뒤에 넣는 순서가 보안 조건이다** — 먼저 임베드하면 정제기가 걸러야 할
   표면이 base64 로 부풀고, 원격 `http` 이미지 차단(추적 픽셀)도 그 단계에 있다.

**표시용 HTML 은 수명이 따로 있다.** `image_retain_days` 가 지나면 sync 가
`message_html` 을 비운다 — 이미지가 있었으면 `<div class='imgstrip'>` 한 줄
배너로 대체하고("보존 기간 경과, Outlook 에서 확인"), 없었으면 통째로 버린 뒤
`VACUUM` 으로 공간을 회수한다. 표시는 `new_content` 텍스트로 내려앉는다.
**검색·AI 는 영향이 없다** — FTS 도 요약·수확·분석도 전부 `new_content` 기반이라
`message_html` 은 어느 지식 기능에도 안 쓰인다. 그리고 꼬리의 이미지 서명(로고·
명함 카드)은 저장이 아니라 **표시 시점**에 `hide_image_signatures` 가 한 줄로 접는다.

**중간 합류(mid-join) 예외.** 이 메일이 스레드를 처음 만들었다면
(`preserve_quotes=True`) 인용 사슬을 버리지 않고 `PRESERVED_MARK` 아래 그대로
붙인다. 스레드 중간에 참조로 들어온 경우 **그 사슬이 이전 대화의 유일한 사본**이기
때문이다.

- **판정은 "내 사서함 기준 첫 보유분"이다.** '대화의 진짜 첫 메일'은 관측할 수
  없지만 그건 필요하지도 않다 — 시간순 입력 하에서 `store._assign_thread` 가
  **새 스레드를 만드는 순간의 메일**이 정확히 그것이다. 보존 조건은 `새 스레드
  생성 + 인용 체인 존재` 둘뿐이다.
- **전제는 수집이 전역 시간순이라는 것이다.** 폴더를 차례로 훑으면(받은편지함
  전체 → 보낸편지함 전체) 폴더 안에서만 시간순이라, 내가 시작한 스레드의 백필에서
  상대 답장이 내 원 메일보다 먼저 들어와 **인용본을 보존해 버리는 오탐**이 났다.
  `OutlookComSource.fetch` 가 두 스트림을 `heapq.merge` 로 병합해 이 가정을 실제로
  성립시킨다.
- 수용한 오탐 하나 — 30일 밖에서 재개된 스레드는 제목 매칭이 끊겨 새 스레드가
  되고 인용이 보존된다. 표시로는 맥락 복원이라 오히려 낫다.

**그 사본은 대화 턴으로 읽힌다 (2026-08-06).** 보존 사슬을 갖고 있으면서도 화면은
'이전 대화 (인용 보존)' 한 줄로 접어, 몇 턴이 누구 사이에 오갔는지도 안 보였다 —
실측 예: 스레드에 메시지는 3통인데 실제 대화는 5턴이고 앞 2턴이 그 덩어리 안에만
있었다. `clean.parse_preserved` 가 헤더(`보낸 사람/보낸 날짜/제목`, 한글·영문 ·
마크다운 변환본 모두)를 읽어 턴 목록으로 만들고, `preserved_label` 이 접힘
머리줄을 만든다 — `앞선 대화 2턴 — 강미래 선임 → 오태양 책임 · 07-31 ~ 08-01`.

- **기본은 접힌 채**다. 머리줄만으로 "내가 못 본 대화가 여기 있다"가 전해지므로
  주목 예산을 쓰지 않는다.
- **복원 턴은 메시지가 아니다.** DB 행이 없어 링크·앵커·검색 결과가 없다. 그래서
  링크를 주지 않고 `인용에서` 라고 출처를 밝히고 흐리게 그린다. 목록의 `[N통]` 도
  그대로 둔다 — 메시지 수는 안 늘었다.
- **파싱 실패는 보이지 않는다.** 못 읽으면 빈 목록이라 종전 화면 그대로다.
- **저장 HTML 은 렌더 시점에 갈아 끼운다**(`clean.retitle_qfold`). 접힘은 수집 때
  `message_html` 에 구워지므로 상수를 고쳐도 기존 메일은 안 바뀌고, 재수집은
  불변식(#5) 위반이다. `hide_image_signatures`·`add_dark_colors` 와 같은 자리다.
  HTML 층은 원본 서식을 지키느라 머리줄만 바꾸고, 턴 렌더는 텍스트 층에서 한다.

정제 철학: **과잉 제거보다 과소 제거가 낫다. 애매하면 남긴다.**

### 6.2 신호 판정 3층

```
L1  message_features   수집 시 1회, 메시지 단위 비트     (features.py)
L2  thread_state       증분 접기, 스레드 단위 집계        (store.py)
L3  actions.evaluate   질의 시 판정, 본문 재열람 없음     (actions.py)
```

- **문장 단위 게이팅.** 문장별로 판정한 뒤 OR한다(순서 무관). 한국어 맺음말
  "잘 부탁드립니다"가 요청 신호를 지배하지 않게 하려는 것이다. 단 "다시/재차/리마인드"는
  게이팅된 요청을 되살린다. "마지막 의도 채택" 방식은 그 맺음말 하나에 깨져서
  채택하지 않았다.
- **L2 는 스레드당 열린 요청 슬롯 1개**짜리 상태기계다(`store.fold_action`).
  최신 요청이 우선한다는 스레드 단위 도구의 철학을 그대로 따른 의도적 단순화이고,
  전이가 **순수 함수 하나**여서 증분 갱신·역순 삽입 refold·백필이 모두 같은 코드를
  지난다 — **증분 ≡ 전체 재계산**이 정의상 성립한다(무작위 순서 삽입 drift 테스트가
  지킨다). 열린 창 안에서 강도·기한은 단조 증가만 하고 `action_source_id` 만
  최신 요청으로 갱신한다.
- **슬롯을 닫는 것은 둘뿐이다** — 내 **실질** 발신(`++수신인 추가`·빈 본문 같은
  trivial 은 제외)과 명시적 철회("회신 불필요"). **상대의 완료 통보는 닫지 않는다** —
  `completion_after_action` 표시 후 MAYBE 강등까지다. 잘못 닫히면 조용한 실패가
  되는데 잘못 열려 있으면 눈에 보이기 때문이다(아래 비대칭 비용과 같은 이유).
- **비대칭 비용.** 놓치는 쪽(false negative)이 치명적이므로, 부정 규칙은 `NONE`이
  아니라 **`MAYBE`(접힌 확인 후보)**로 보낸다.
- 모든 `REQUIRED`/`MAYBE`는 사유 코드를 달고 다닌다(설명 가능성).
- 수신 대상 사다리 — 직접 수신·이름 지목·내 참여는 '회신 필요', 그룹·대량 발송·
  외부 발신은 '확인 후보'로 강등한다. 수신 50명 전사 메일의 "회신 바랍니다"가
  개인 액션 목록을 오염시키지 않는 장치다.

**엔진은 남기고 노출은 걷어냈다** (2026-07-30). 목록의 ↩/⏰ 탭·스레드 칩·`x` 키·
데일리 '지금 할 일'·개입 AI 분류(haiku 2콜)·CLI `act` 를 전부 제거했다 — 정규식
판정의 정밀도가 낮아 **상시 노출이 도구 신뢰를 깎았기** 때문이다. 판정 자체는
주간 보고의 '내 차례'와 누락 방지 백스톱 재료로만 남는다(거기서는 과잉 포함이
미덕이다). 시간 기반 사실인 정체 2종만 데일리 '참고'로 강등해 유지한다.
"이 메일이 뭘 요구하나"는 이제 온디맨드 [분석]이 답한다.

### 6.3 분석 — 근거 달린 질의응답 (`ask.py`)

검색은 "그 메일"을 찾아주고 끝나지만, 분석은 "그래서 결론이 뭐였지"에 답한다.
계획을 한 번에 확정하지 않고 **본 뒤에 다음을 정하는 라운드 루프**를 돈다.

```
라운드:  훑기(제목·발신·날짜·스니펫)
           → 판단(더 검색 / 이것들 정독 / 충분)
           → 정독(인용 제거 본문) → 반복
반전 검색: 호스트가 강제 — 이미 본 스레드 전개 + 변경·취소·최종 신호
답변 작성
의미 검증: 별도 AI 판정 — 주장이 인용에서 실제로 도출되는가
```

**모델이 도구를 자유롭게 호출하는 루프가 아니다.** 호스트가 실행과 상한을 강제한다
(`MAX_ROUNDS=6`, `MAX_BODIES=48`, `MAX_CALLS=12`). 답변·의미 검증·필요 시
검증 근거만 사용한 재작성까지 이 상한 안에서 끝낸다.

세 가지 답변 상태 — **확인됨 / 상충함 / 근거 부족**. 검증은 **강등만** 하고
승격하지 않는다. 인용 대조를 통과한 근거가 0이면 자동으로 근거 부족이다.

- **반전 검색**은 관련도 하한(tier ≤ 3)을 걸고, 안 본 스레드에서 새로 정독하는
  통수를 제한한다. 앵커에 단어를 덧붙이면 AND 매치가 되레 깨져 검색이 OR 폴백으로
  떨어지는데, 질문이 구체적일수록 무관한 메일이 쏟아지는 뒤집힌 특성이라 막아 둔다.
- 모델이 정독한 스레드는 최초·최신·결정·기한·철회·완료 메시지를 시간순으로
  펼친다. 최초 검색 후보에 이미 있던 최종 메일도 새 검색 결과가 아니라는 이유로
  건너뛰지 않는다.
- **의미 검증기 고장은 거부와 다르게** 다룬다. 호출 실패·응답 파손이면 인용 대조를
  통과한 근거를 남기고 `semantic_checked=False`로 알린다. 답변 본문은 구조화 근거로
  다시 쓴다(미검증 자유 서술을 내보내지 않는다).
**입력 예산 — 한 콜의 총량으로 묶는다** (2026-08-03). 손잡이는
`[ai] ask_max_input_tokens` **하나**이고 값은 곧 **백엔드 컨텍스트 창**이다
(기본 120,000 — Claude 기준. 0 = 제한 없음).

통당 상한으로 잡지 않는 이유: **총량을 못 묶는다.** 같은 3,000자 설정에서 3통을
읽으면 10K, 24통이면 75K로 그냥 늘어난다(실측). 사용자가 아는 값은 창 크기지
통당 자수가 아니고, 통당 자수를 정하려면 "몇 통 읽을지"를 미리 알아야 하는데
그건 조사가 끝나야 안다.

```
① 설정: ask_max_input_tokens (= 내 백엔드 창)
② 변환: 자수 예산 = 토큰 × chars_per_token   ← 추정은 여기 한 번뿐
③ 조립: 통당 예산 사다리(무제한→8000→…→300)로 프롬프트를 만들고
④ 실측: len(프롬프트) 이 예산에 들면 채택, 아니면 다음 사다리로  ← 정확한 측정
```

토큰은 셀 수 없다(stdlib only · 백엔드는 CLI). 그래서 추정은 ②에서만 쓰고
그 뒤는 조립 결과의 **정확한 문자 수**로 맞춘다 — 비율이 30% 틀려도 창의
70%나 130%를 쓸 뿐 넘기지 않는다. `chars_per_token` 기본 1.0은 보수적이다
(한국어는 대략 1자당 0.7~1.5토큰).

**라운드는 총예산의 25%**만 쓴다. 정독 블록은 이후 STEP 라운드마다 + 답변 콜에
다시 실려 본문 한 글자가 총 송신 **3.2자로 증폭**되는데, 라운드는 "더 읽을까/
이제 답할까"만 정하면 되기 때문이다. 전문이 필요한 것은 답변 콜 하나뿐이다.

실측(기본 120,000토큰, 통당 5,000자 원문):

| 정독 | 답변 프롬프트 | 예산 대비 |
|---|---|---|
| 3통 | 16,036자 | 13% (사실상 전문) |
| 12통 | 61,582자 | 51% |
| 24통 | 97,928자 | 82% |

통수가 늘면 통당 몫이 자동으로 준다. 창을 20,000으로 낮추면 3·12·24통 모두
16K 안팎(80%)으로 수렴한다.

- **절단은 앞뒤를 나눠 담는다**(`clean.smart_truncate`) — 업무 메일은 앞에
  인사·배경, **뒤에 결론과 요청**이 온다. 앞에서만 자르면 정작 필요한 쪽이
  날아간다: 통당 2,200자 16통 실측에서 **결론 생존 0통**이었고, 같은 예산으로
  앞뒤를 나누자 **16/16**이 남았다(비용 0). 중략은 `…(중략 — N자)…`로 **표시**한다 —
  종전 산문 절단은 표시가 없어 모델이 조각을 전문으로 믿었다. **표는 행 경계를
  지켜 자른다** — 맹목 슬라이스는 '온전해 보이는 반쪽 표'를 만든다. 이 함수는
  분석·수확·주간·AI 검색·인물 요약 **다섯 경로가 공유**하므로 한 곳을 고치면
  전부에 적용된다.
- **부분 열람을 밝힌다** — "이 스레드 20통 중 12통 열람". 조각을 보고 있다는
  사실을 알아야 모델이 "더 읽자"를 고를 수 있다. **롤링 요약을 주입하는 안은
  철회했다**: 대개 존재하지 않고(자동 회고는 `ai=False`), 더 약한 백엔드가 쓴
  산출이며, 인용 검증을 통과할 수 없어 근거가 못 된다. 지어낸 요약보다 "덜 봤다"는
  사실이 정직하고 비용이 0이다.
- **검증기는 전문을 본다** — `_quote_ok`는 `read[mid]["body"]`(자르지 않은 원문)와
  대조한다. 절단은 프롬프트 조립에서만 일어난다. 그래서 절단이 심하면 모델이
  **답을 알면서 인용하지 못해** '근거 부족'으로 강등되던 비대칭이 있었다.
**답변의 형태 — 메일을 다시 열지 않게** (2026-08-03). 사용자 지적: "답변이 너무
담백해서 내용 확인을 위해 메일을 다시 읽게 된다." 원인이 둘이었다 — 인용이
조각이라 조건·전제가 안 보였고, `answer` 가 2~4문장으로 묶여 수치·조건이 빠졌다.

- **인용의 앞뒤를 코드가 붙인다**(`clean.quote_context`). 인용은 이미 원문의
  연속 부분 문자열임이 검증된 값이라 **위치를 찾아 앞뒤를 그대로 복사**하면
  된다 — 모델이 문장을 더 만들지 않으므로 **환각 위험이 0**이다. 대조가 공백을
  무시하므로 정규화 인덱스 ↔ 원문 인덱스 대응표로 위치를 되찾고, 문장 경계로
  다듬는다. 방향이 중요하다 — 앞은 pad 안의 **가장 이른** 경계부터, 뒤는 **가장
  늦은** 경계까지다(가까운 경계로 자르면 9자만 늘어 쓸모가 없다). 폭은
  `[ai] quote_context_chars`(기본 120): 실측 100 이면 폴백 조건까지 들어오고
  250 은 과하다. 문맥은 **표시용**이라 줄바꿈을 접는다.
- **결론이 구조로 올라온다** — `headline`(한 줄 결론)과 `claims[].role`
  (결론·근거·배경). 종전에는 결론이 문단 첫 문장에 묻혀 읽어야 알았다.
  headline 은 **검증 통과 claim 이 0이면 코드가 비운다** — 근거 없는 결론을
  내지 않는다.
- **`open[]`** — 메일에 명시된 열린 것. `claims` 와 **같은 인용 검증**을 탄다.
- **`answer` 에서 메일 번호를 뺀다** — "(2026-07-26, #271)" 이 문장 안에도 있고
  claims 에도 있어 같은 것을 두 번 읽었다. 길이는 3~6문장이고, guide 가 있으면
  guide 의 형식을 따른다(종전 "2~4문장" 규칙은 3~4개 절을 지시하는 브리핑·메일
  분석 guide 와 **모순**이었다).
- **`claim.text` 는 라벨이 아니라 문장** — 의미 검증이 실패하면 폴백
  (`_safe_answer`)이 claim.text 를 이어 붙이므로, 폴백 답변까지 함께 좋아진다.
- **`REPAIR` 도 같은 규칙을 든다**(2026-08-04). 의미 검증이 answer 를 떨어뜨리면
  `_repair_answer` 가 검증된 근거만으로 다시 쓰는데, 여기가 예전 "2~4문장" 규칙을
  들고 있어 재작성될 때마다 답이 종전 톤으로 되돌아갔다. 실기기 첫 조사(sonnet)
  에서 **바로** 이 경로를 탔으니 드문 분기가 아니다. 재작성이 쓸 수 있는 재료는
  `text`·`date`·`quote` 뿐이고 결과를 같은 검증기에 다시 태우므로, 조건·수치는
  **인용 안에 있는 것만** 쓰라고 적었다 — 더 요구하면 재검증에서 통째로 떨어진다.
- **"기준" 줄은 코드가 만든다** — 근거의 시간 범위·정독 통수·덜 본 스레드.
  모델에게 묻지 않는다(자기가 뭘 안 봤는지는 코드만 정확히 안다).
- 프롬프트는 **자료를 앞에, 과업을 뒤에** 둔다. 예산 모델로 근거가 100배
  길어졌으니 생성 지점에서 먼 지시는 힘을 잃는다.
- 새로 생긴 절단 마커를 위해 **"`…(중략)…` 을 가로질러 인용하지 마라"** 를
  명시한다 — 원문에 그런 연속 문자열이 없어 그 항목이 통째로 버려진다.

- **캐시 키**에 `MAX(rowid)` 기준선이 들어가 새 메일이 오면 자연히 무효화된다.
  옛 답은 지워지지 않고 "이후 새 메일 N통"으로 낡음을 알린다.
- 이어 묻기는 모델 세션이 아니라 **매번 다시 조립한다** — 이전 문답과 정독 목록을
  프롬프트에 실어 보낸다. 백엔드 교체 가능성과 재현성을 지키기 위해서다.

### 6.4 일간 회고 — 오늘 하나와 어제 대비 (`review.py`)

주간이 '기간의 지도'라면 일간은 **오늘 판단이 필요한 것**만 남긴다.

```
Executive Summary(1건) → 내 약속 → 변화(어제 이후) → 오늘 확정·변경 → 오늘 흐름 → 참고(접힘) 
```

- **Executive Summary** — 대상 1건 선정은 결정론이다(오늘 내가 보낸 스레드 중
  `_worth_reporting` 최상위). 문장만 AI 가 쓰고, 주간과 **같은 문체 표본**을 쓴다.
  고를 만한 것이 없으면 호출하지 않는다.
- **AI 를 안 돌린 리포트는 이 절을 내지 않는다.** 기본 일간은 `ai=False` 로 자동
  생성되므로, 절을 내면 매일 첫 줄이 '없음'이 된다.
- 비었을 때의 문구는 상황을 가른다(`review.EXEC_EMPTY`) — 올릴 것이 없으면
  "특이사항 없음", 호출이 실패하면 "받지 못했습니다", 주간의 근거 검증에서
  떨어지면 그렇게 적는다. **실패를 '없음'이라 말하면 거짓이다.**
- **내 약속**(`promises.py`) — 내가 직접 쓴 확정 어미만. 보존 인용(mid-join)은
  떼고 본다: 안 떼면 남이 쓴 문장이 '내 약속'으로 올라간다.
- **변화** — 어제 상태판을 다시 계산해 달라진 것만(`review.state_shift`).
  상태판은 주간 엔진을 `report_extras=False` 로 빌려 쓴다(보고서 전용 계산 생략).
  각 줄에 **마지막 메시지의 발신자 + 첫 문장 발췌**를 붙인다 — "왜 이게 내
  차례가 됐지"를 스레드를 열지 않고 확인하려는 것이다(2026-08-03). **인용이
  아니라 발췌**라고 부른다 — AI 가 고른 근거가 아니라 코드가 뗀 문장이라,
  이 저장소는 둘을 같은 이름으로 부르지 않는다. `store` 를 안 넘기면 종전 그대로다.
- AI 회고 분석은 '참고'(접힘) **앞**에 온다. 뒤에 두면 그 접힘 안으로 들어간다.

#### AI 산출은 파일 밖에도 남긴다

데일리 md 는 재생성마다 **통째로 덮어써진다**(`notes.write_daily`). 웹은 새 메일이
들어오거나 서버가 다시 뜨면 결정론 회고를 배경에서 다시 만드는데
(`web._maybe_auto_review`, `ai=False`), 그때 사용자가 돈 주고 받은 AI 절이 파일에서
조용히 사라졌다 — 재현: AI 회고 → 서버 재시작 → 홈 1회 조회 → `## Executive
Summary` 증발. 통계의 **기억 커버리지**가 바로 그 절 유무로 '지식이 쌓인 날'을
세므로(`report._AI_DAILY_MARKS`) 지난 기록까지 함께 거짓이 됐다.

- `run_ai_layer` 가 산출을 `sync_state` kv 에 날짜별로 남기고
  (`daily_ai:<date>` — 머리글·상태·수확·흐름의 AI 한 줄), `deterministic()` 이
  다시 얹는다(`review.restore_ai_layer`). **되읽기지 재호출이 아니다** —
  AI opt-in 불변식은 그대로고 결정론 경로의 호출 수는 0 그대로다.
- 새 표를 만들지 않는다(`sync_state` 는 어느 DB 에나 이미 있다) → 재수집 불필요.
- 이 장치 이전에 만든 파일은 md 의 `## Executive Summary` 절에서 한 번 구제한다
  (`_exec_from_file`). `- 특이사항 없음` 같은 `EXEC_EMPTY` 문구는 본문이 아니라
  **상태**로 되살린다 — 안 그러면 실패·미실행 구분이 무너진다.
- 같은 날 **두 번째 수확은 새 메일분만** 돌아온다(`last_harvest` 워터마크가 이미
  앞서 있다). 그것으로 덮으면 '오늘 확정·변경'이 통째로 사라져서, AI 회고를 한 번
  더 눌렀다는 이유로 오늘 확정된 것이 화면에서 없어졌다 → `_merge_harvest` 로
  합친다. 머리글도 **재실행이 실패했다고 이미 받아 둔 요약을 지우지 않는다.**

### 6.5 주간 보고 — 원문에서 다시 만드는 델타 (`weekly.py`)

기본 범위는 **최근 1주**다. 기간 내 내가 관여한 스레드 중 내 차례·막힘·결정·기한을
우선해 최대 64개를 소배치로 읽고, 원문 인용이 붙은 근거 카드로 압축한 뒤 토픽을
묶는다. 상위 20개만 보고 나머지를 누락하던 경로는 없다.

**누적 요약과 데일리는 재료로 쓰지 않는다.** 사실·상태·중요도·후보 선별을 전부
원문에서 다시 하고, '기간 전 상태'도 그 시점 이전 원문으로 복원한다. 요약의 요약은
오차가 쌓이는데 주간은 그 오차가 가장 비싸게 드러나는 자리다.

```
기간 내 원문 → 근거 카드 → 토픽 묶기 → 토픽 서술 → 총평 → 누락 점검 → 의미 검증
```

보고서는 **상태판이 먼저**다(2026-08-01 재구성 — 진행 항목이 같은 무게로 나열되면
읽고 나서 무엇을 해야 할지가 남지 않았다).

```
Executive Summary(최대 5건) → 내 차례 → 막힘 → 기한 → 지난 차수 점검 → 토픽 서술 → 그 외
```

개수 제한은 절마다 다르다 — **일부러 그렇다**.

| 절 | 상한 | 왜 |
|---|---|---|
| Executive Summary | `EXEC_TOP` 5 | 상위 보고는 다섯 줄이면 충분하다 |
| 내 차례 · 막힘 · 지난 차수 점검 | `WEEKLY_TOP` 5, 나머지 '외 N건' | 중요한 것 먼저 |
| 기한 | **없음** | 놓치면 곤란한 것이 섞여 있다. 대신 정보성은 '중요도 낮음' 표시로 낮춘다 |
| 그 외 | `REST_TOP` 20, 나머지 '외 N건' | 훑어보는 자리 |

가벼운 건(회식·사무용품)을 빼는 `review._worth_reporting`(일간과 공유)은
**상태판 버킷(내 차례·막힘)에만** 걸린다. 기한·지난 차수 점검·그 외는 안 걸린다 —
기한은 놓치면 곤란하고, 지난 차수 점검은 내가 한 말이 기준이기 때문이다.
그 판정의 '기한'은 환산된 날짜가 아니라 `has_deadline` 개수라, "금요일까지"가 든
가벼운 메일도 통과한다(알려진 느슨함).

- 최종 항목은 `thread_id`만이 아니라 **`message_id` + 연속 원문 인용**으로 고정한다.
- `mine=true`는 해당 메시지가 내 발신일 때만 통과한다.
- 인용 문자열 대조 뒤 별도 AI가 시제·주체·확정/예정/취소의 의미까지 검증한다.
- 누적 요약·데일리 요약은 사실·상태·중요도·후보 선별에 쓰지 않는다.
- 기간 이전 상태도 현재 누적 요약이 아니라 **기간 이전 원문 마지막 3통**으로 복원한다.
- 직전 주간보고는 표현 중복 회피용 참고일 뿐, 사실 근거나 누락 판단에 쓰지 않는다.
- AI 실패 시에도 결정론 목록을 담은 보고 파일은 남는다.

**차수 잇기.** 주간 보고가 이전 차수와 이어지지 않아 지난번에 내가 한 약속을
아무도 다시 보지 않았다. 세 갈래로 잇는다(2026-08-01).

- **열람** — 웹 기억 › 주간 보고에 ◀▶ 인접 차수 이동. 주간 파일은 생성한 날만
  있어 간격이 불규칙하므로 날짜 산술이 아니라 **목록의 앞뒤 원소**를 가리킨다.
- **지난 차수 점검** — 새 표를 만들지 않는다. 약속은 내 발신 원문에서 나오므로
  `promises.review_period`가 지난 차수 창으로 **다시 계산**한다(일간의 '어제 대비'와
  같은 수법). 창은 **저장된 보고서 두 개 사이**다 — 직전 보고의 종료일이 끝,
  그 앞 보고의 다음 날이 시작(`weekly.report_rounds`). 앞 보고가 없으면 그때만
  같은 `weeks` 로 되짚는다. 이번 창에서 `weeks*7`일
  되짚으면 안 된다: 주간 파일은 생성한 날만 있어 간격이 불규칙해서, 07-25에 낸
  보고를 07-29에 열면 두 차수 전을 가리키고 그 사이 약속이 어느 창에도 안 잡힌다
  (2026-08-01 적대 검토 실측). 후속 판정은 "그 뒤 내가 그 스레드에 보냈나" +
  웹의 '처리함'뿐이고, **'안 지켰다'고 쓰지 않는다** — 다른 스레드나 메일 밖에서
  처리했을 수 있다.
- **머리글의 근거** — `board_facts`(코드가 센 카운트 + 지난 차수 점검 결과)가
  총평이 '지난 차수 대비'를 쓸 수 있는 **유일한** 사실 근거다. 이전 보고의
  **문장**은 여전히 머리글에 넣지 않는다.
- **문체 표본** — 내가 쓴 보고성 메일 최근 2건(제목이 보고성 + 본문 400자 이상,
  최근 400통 안)을 머리글 프롬프트에 **어조 참고 전용**으로 넣는다. 선정은
  결정론이다(고르는 일까지 AI 에게 맡기면 중요도 판단이 표본 쪽으로 샌다).
  사실 오염은 라벨 · 규칙문 · 총평 검증(`summary_supported`) 세 겹으로 막는다.
- **머리글 few-shot** (2026-08-03) — "경과 나열이 아니라 판단이 서는 문장"이라는
  지시는 원래 있었는데 **예시가 없어 잘 안 지켜졌다.** 좋은 예 3 + 나쁜 예 1을
  `OVERVIEW` 에 박았다(전부 가상값이고 "형태만 참고, 사실을 가져다 쓰지 마라"를
  함께 적는다). 프롬프트만 고치면 되는 가장 싼 개선이다.

**리포트 '처리함'.** 회의·구두처럼 메일 밖에서 처리한 항목은 다시 올라오면
안 된다(사용자 확정 2026-08-01: "한번 처리하면 다음 판단에는 잡히지 않아야 해").

- 리포트 마크다운의 해당 줄 끝에 `<!--done:종류:키-->` 표식을 넣는다. HTML 주석이라
  다른 뷰어·편집기에서는 보이지 않고, 웹(`_md_inline`)만 **처리함** 버튼으로 바꾼다.
  키를 본문에 심는 것은 **화면에 보이는 그 항목**을 정확히 가리키기 위해서다 —
  화면에서 다시 계산하면 그 사이 들어온 메일 때문에 목록이 달라진다.
  표식은 **줄 끝에 붙은 것 하나만** 신뢰한다. 이스케이프를 지난 형태로 잡으면
  메일 제목에 심은 표식이 가짜 버튼을 만든다(2026-08-01 적대 검토 실증).
- 종류는 `promise`(내 약속) · `stalled`(정체·막힘) · `deadline`(기한). 키가
  일간·주간 공통이라 **한 번 접으면 양쪽에서 빠진다** — `stalled` 는 스레드 번호로,
  나머지는 원문 문장으로 만든다.
- 제외는 **결정론 단계**에서 한다(`review.deterministic` · `weekly._calendar` ·
  `weekly._bucket` · `promises.extract`). 렌더에서 빼면 다음 판단에 다시 올라온다.
- 이미 **저장된** 리포트에서도 그 줄을 빼고 절의 `(N건)` 을 다시 센다
  (`web._apply_done`). 파일은 다시 만들어지지 않으므로 화면에서 세야 한다.
  남은 항목이 0이면 절을 통째로 뺀다.
- 되돌리기는 리포트 하단 접기(`처리함으로 접은 항목`)에 남는다 — 접힌 채로 잊히면
  '사라진 것'과 구별되지 않는다. 저장은 `report_done` 표(`kind`+`key_hash` PK).
- **알려진 한계**: `CLEAN_VERSION` 이 올라 본문이 재절단되면 `promise`·`deadline`
  키가 달라져(그 문장이 절단 경계에 걸릴 때) 접은 항목이 되살아날 수 있다.

### 6.6 장기기억 — 결정의 영구 기억

```
수확(AI)  →  원문 인용 대조  →  '반영 대기' 후보  →  사람이 반영/유보  →  장기기억
```

`distill.harvest`가 추출한 항목은 **반드시 `quote`를 달아야** 하고, 그 문자열이
스레드의 `new_content`에 (공백 무시) 실제로 있는지 대조해 통과한 것만 남는다.
AI는 제안만 하고, 반영은 사람이 웹 UI **기억 › 장기기억**에서 누른다.
반영된 것만 검색·회고의 재료가 된다.

**대조 대상은 신규 작성분뿐이다** — 보존 인용(mid-join)은 뺀다(2026-08-06).
그 블록은 남이 주고받은 글을 옮겨 실은 것이라, 그대로 대조하면 **A 가 쓴 문장을
B 의 결정으로** 원장에 올릴 수 있다(실측: 오태양 책임의 「sync_for_cpu 훅 호출은
UMD 책임입니다」가 강미래 선임 메일 안에 있어 결정자를 강미래로 붙여도 통과했다).
인물 요약 쪽(`_PersonQuoteChecker`)은 처음부터 이렇게 하면서 "발화자 오귀속 차단"
이라고 적어 두었는데 수확 쪽만 빠져 있었다 — 지금은 같은 `_QuoteChecker` 가
발신자 제한만 옵션으로 갖는다.

수확은 성공했을 때만 `last_harvest` 워터마크를 전진시킨다. 소급 상한은
`[ai] summary_max_days`(기본 **1일** — 오늘만, 요약과 공유)이고, 며칠 건너뛴 뒤
소급하려면 그 값을 늘린다.

"이미 보고한 것 반복 금지" 재료(`_recent_delta`)는 **어제 데일리 md 의 확정·변경
절**을 읽는다. 2026-08-06 까지 이 정규식이 모델 출력의 절 이름(`## 오늘 델타`)을
보고 있어서 렌더된 파일(`## 오늘 확정·변경 (N건)`)과 어긋났고, 그 재료가 한 번도
프롬프트에 실린 적이 없었다. 지금은 두 이름을 다 받는다.

### 7.2 통계는 왜 이만큼만 남았나

2026-07-13 개편은 "mail-trends·Email Meter 등 **표준 지표 이식**"이었다. 그 기준이
이 도구의 목적("Outlook이 못 하는 것만")이 아니라 남의 제품에서 왔다는 것이
문제였다 — 개편 직전 기록도 "기존 §1~5가 신호성 위주라 **큰 도움 안 됨**"이었으니,
같은 질문에 두 번째로 답한 셈이다. 이번엔 **"그래서 뭘 할지가 나오는가"** 하나로
쟀다. 4타일+6섹션 → 2타일+4섹션.

| 뺀 것 | 이유 |
|---|---|
| 자주 주고받는 상대 | **인물 화면이 흡수.** `report.py` 안에서 `rank_people`과 옛 `sig_volume`이 같은 것을 두 번 랭킹했다. `person_metrics`는 §3·§5·§6 내용을 **그 사람 기준**으로 이미 전부 준다(docstring: "→ /stats 수치와 정의상 일치") |
| 답 기다리는 내 발신 | **2026-07-30 신호 노출 폐기의 잔존분.** 정규식(`?`·부탁드·바랍니다…)으로 '내 발신이 요청인가'를 판정했다. 데모 실측에서 1위·26일·critical 항목이 "상세는 별첨 참고 **바랍니다**"(진척 보고의 맺음말)였다. `person_metrics`도 이걸 계산했지만 **웹은 렌더하지 않았다** — 죽은 계산까지 함께 걷었다 |
| 야간·주말 비율 | 메일 지식이 아니라 자기 정량화. 활동 히트맵과도 중복 |
| 응답 시간 절 | 대기 목록이 빠지면 숫자 둘짜리 카드다 → **타일로 승격**. 내 값 하나로는 27시간이 느린지 알 수 없어 상대 값이 기준 역할을 하므로 **둘은 짝**이다(떼면 남은 하나가 해석 불가) |
| 볼륨 타일 2개 | §1 차트와 **같은 함수 한 번 호출**에서 나왔다. 스파크라인은 발신·수신이 각자 축을 써서 '두 선의 벌어짐'을 못 보여주므로 차트를 남기고, 타일에만 있던 최근 주 수치·델타를 §1 안 한 줄로 옮겼다 |

**검토 기간 선택(2/4/8/16W)도 없앴다.** 근거 셋:

1. **절마다 필요한 창이 다르다.** 추세는 길어야 읽히고(코드가 스스로 "6~8주부터
   안정화"라고 경고한다) 왕복 목록은 짧아야 '회의 전환 후보'로 쓸모가 있다(넉 달
   전 핑퐁은 끝난 논의다). 하나로 강제하면 **어느 값을 골라도 절반은 틀린 창**을
   본다. 선택기가 권한을 준 게 아니라 타협을 강요했다.
2. **안 쓰였다는 증거.** 이 선택기는 한동안 **고장난 채**였는데(축만 바뀌고
   데이터셋은 전량) 사용 중이 아니라 코드 검토로 발견됐다(2026-07-10 수정).
3. **전부에 먹지도 않았다.** 응답 지표만 늘 '최근 2주' 앵커라, 16주를 고르면
   `내 응답 중앙값`이라는 같은 이름이 한 화면에서 29.1h와 26.2h를 냈다.

대신 창을 상수로 고정하고(`TREND_WEEKS=12` / `RECENT_WEEKS=4`) **각 절이 자기 창을
화면에 적는다**(`최근 12주` 칩) — 전역 선택기가 있는데 일부만 따르는 것보다 정직하다.
`load()`는 가장 긴 창으로 **한 번만** 읽고 짧은 창 절이 잘라 쓴다(누를 때마다 전량
재적재하던 것보다 싸다). 구 북마크의 `?weeks=`는 조용히 무시한다.

**숨김의 취급이 절마다 다르다** — 왕복 논의 같은 **목록**은 숨김을 존중하고,
볼륨·히트맵 같은 **집계**는 전량 센다. 숨김은 "조용히 하라"이지 "없던 일로 하라"가
아니기 때문이다. `sig_pingpong`은 인물 카드의 '진행 중'도 만들므로 이 제외가
거기까지 전파된다 — 같은 규칙이라 의도된 것이고, 회귀 테스트가 지킨다.

#### 하나 더한 것 — 통계 5절 '기억 커버리지'

지운 것만 있는 정리는 아니다. **이미 있는 트레이드오프의 계량기**를 하나 더했다.

`review._summary_window`의 소급 상한은 `[ai] summary_max_days`(기본 1일)라
**앱을 안 연 날의 메일은 요약·수확에서 영구히 빠진다.** 그 함수 docstring이
"3일 넘게 비운 구간의 가장 오래된 날은 요약에서 빠질 수 있음(의도된 트레이드오프)"
이라고 스스로 적고 있다. 설계는 옳은데 **대가가 어디에도 안 보였다** — 사용자는
자기 기억에 구멍이 몇 개인지 모르는 채로 그 상한을 올릴지 판단할 수 없었다.

- 요일(행)×주(열) 격자에 **채운 칸 = 그날 지식이 쌓인 날**. 농도가 아니라 2단계인
  것은 질문이 '얼마나'가 아니라 '쌓였나'이기 때문이다. 주말은 테두리로만 구분한다
  (빈 칸이어도 문제가 아니므로).
- 판정은 **회고 파일의 AI 절 유무**(`## Executive Summary` · `## AI 회고 분석`)다.
  **파일 존재만 보면 거짓말이 된다** — 웹의 자동 생성(`_maybe_auto_review`)은
  `ai=False`라 파일은 매일 생기지만 요약·수확은 돌지 않는다.
- 숫자 셋: 지식이 쌓인 날 / 요약된 스레드 / 확정된 결정. 구멍을 메울 방법
  (`summary_max_days` 상향)을 문구에 함께 적는다 — 진단만 하고 처방이 없으면
  또 하나의 허영 지표가 된다.
- AI를 한 번도 안 돌린 설치에는 **0/N 격자 대신 한 문장**을 낸다. 실패·미실행·
  없음을 가르는 이 저장소의 관례(`review.EXEC_EMPTY`)와 같은 태도다.

### 7.3 관계 배지

목록 행의 발신인 뒤에 붙는 두 글자짜리 사실 — **`↩ 0`**(이 사람에게 한 번도 보낸
적이 없다, 받은 것이 `_ONEWAY_MIN`=3통 이상일 때만) · **`첫 메일`**(이 사람에게 받은
첫 메일). '읽을지 말지'의 1차 판단이 화면에 없었다는 것이 출발점이다.

- **왜 노이즈 규칙 위에 또 두나.** 노이즈는 발신 주소·제목 문자열이라 설치마다
  손으로 채워야 한다. 왕래 수는 **사용자 행동 기록**이라 설정 없이 개인화되고,
  규칙이 놓친 발신자를 잡는다(실측: 데모에서 광고·뉴스레터·웨비나가 노이즈 규칙을
  통과해 목록에 남았는데 셋 다 `↩ 0` 이었다).
- **할 말이 없으면 아무것도 안 쓴다.** 모든 줄에 붙는 배지는 배지가 아니라 소음이다.
- **표시만 한다.** 정렬·필터·자동 숨김에 쓰지 않는다 — 쓰는 순간 "내가 처음 답하는
  사람"이 화면에서 사라진다.
- `첫 메일` 판정은 `people.first_seen` 과 **그 행의 시각**을 맞춘다. `from_count` 는
  지금까지의 누계라 과거 행에 그대로 쓰면 옛 메일이 전부 첫 메일이 아니게 된다.
- 재료는 목록 쿼리에 `LEFT JOIN people` 하나로 딸려 온다(행당 추가 조회 없음).

### 7.4 선택 검색

우측 본문에서 텍스트를 고르면 「이 말 찾기」 버튼이 뜨고, 누르면 **좌측**이 검색
결과로 바뀐다(`/search` 는 좌측 라우트) — 읽던 스레드는 우측에 그대로 남는다.
새 엔드포인트·새 화면이 없다: `load("/search?sel=1&q=…&exclude=…", "left")` 한 번이
조각 로딩·히스토리·`←` 복원을 전부 기존 경로로 태운다.

- **읽던 그 메일은 뺀다**(`exclude`). 안 빼면 1등이 늘 방금 읽던 문장이다.
- **질의를 다듬지 않는다.** 대신 정밀 결과(tier 1~3)가 하나도 없을 때만
  **좁힐 말을 칩으로** 내고 고르는 것은 사람이 한다(`_narrow_chips`).
- 버튼은 **포커스를 훔치지 않는다**(`mousedown` 에서 `preventDefault`) — 훔치면
  브라우저에 따라 선택이 풀린다. 버튼이 떠 있는 동안 `Enter` 실행 · `Esc` 닫기 ·
  `Space` 는 읽기 창을 넘기지 않는다(기존 키보드 가드는 **입력란 포커스만** 보고
  선택 상태를 모른다).

#### 왜 질의를 자동으로 다듬지 않나

2026-08-07 실측(코퍼스 문장 150개, 읽던 메일 제외):

| | 정밀 결과 회복 | 평균 스레드 | 0건 |
|---|---|---|---|
| 선택 그대로 | 0% | 8.3 | 17% |
| 드문 말 3개 AND | 6% | 1.2 | **64%** |
| 긴 말 3개 AND | 10% | 5.8 | 30% |

**AND 로 묶으면 소음 대신 아무것도 안 남는다.** 그런데 같은 표본에서 **97%는
선택 안의 어느 한 단어로는 정밀 결과가 나온다** — 정보가 없는 게 아니라 어느
단어인지 코드가 모르는 것이다. 그래서 고르지 않고 **보여 준다**(칩 3개면 94% 커버,
긴 말 순. 드문 말 순은 75% — 드문 말은 변별력이 아니라 토큰화 조각이 드물어서
올라온다). 서술형 어미는 뺀다(커버리지 손실 없이 조각이 0이 된다).

**같은 약한 신호라도 코드가 대신 고르면 해가 되고 사람에게 보여 주면 해가 없다** —
칩이 빗나가면 안 누르면 그만이지만, 자동 정제가 빗나가면 결과가 통째로 사라지고
사용자는 이유를 못 본다(폐기한 '지금 할 일' 큐와 같은 부류의 실수다).
칩 아래에 기존 「AI로 다시 찾기」가 이어진다 — 긴 선택의 진짜 답은 어휘 검색이
아니라 의미 검색이고, 싼 수를 먼저 낸다.

또 하나: **"길다"를 자수로 정의할 수 없다.** 어절 수를 1→10 으로 늘리며 재 보면
정밀 결과 비율이 75% → 36% → 19% → … → 0% 로 매끄럽게 떨어진다. 계단이 없어서
어디를 잘라도 임의값이다. 그래서 기준은 입력 길이가 아니라 **결과**다.

### 7.5 검색으로 들어간 낱말 강조

검색 결과 링크가 `?focus={mid}&hl={낱말}` 을 싣는다. **어느 메일인지는 `focus`
가, 무엇 때문에 걸렸는지는 `hl` 이** 알려준다 — 종전에는 앞의 절반만 있었다.

- `hl` 은 원문 질의가 아니라 `search.parse_query` 가 갈라낸 **본문 낱말만**이다
  (`from:강미래 after:2026-06 리포트` → `리포트`). 질의 문법의 진실원은 한 곳이다.
- 칠하는 것은 **클라이언트**다. 서버는 `render_thread` 를 손대지 않는다 —
  본문은 정제된 메일 원본 HTML 이라 정규식으로 `<mark>` 를 끼우면 태그 안쪽에
  걸려 마크업이 깨진다.
- **CSS Custom Highlight API**(`CSS.highlights` + `::highlight(kw)`)로 Range 만
  등록한다. DOM 무변형이라 되돌릴 코드가 없고, 선택 검색이 고른 문자열이 노드
  경계에서 잘리는 일도 없다(`<mark>` 로 감쌌다면 둘 다 문제가 됐다).
  못 쓰는 브라우저에서는 조용히 넘어간다 — 스크롤·메일 테두리는 그대로다.
- **접힌 인용 안에 일치가 있으면 먼저 편다.** 닫힌 채로는 칠해도 안 보인다.
  순서가 중요하다: 접힘을 열어 높이를 확정한 **뒤에** `focusMsg` 가 스크롤한다.
  (실측: `CMA` 로 찾아 들어가면 일치 1건이 전부 인용 안에 있다.)
- 흔한 말(`합니다`)로 들어올 때를 위해 Range 상한 `HL_MAX`=200.
- 끄는 것은 `Esc` 인데 **맨 뒤**다 — 입력란 탈출이 먼저다. 순서를 뒤집으면 검색창
  포커스 중 `Esc` 가 blur 를 안 하고 강조만 끈다(실기 확인).

### 7.6 키보드

`j/k` 이동 · `n/p` 스레드 내 메시지 이동 · `f` 플래그 · `h` 숨김 · `/` 검색.
`f/h`는 우측에 열린 스레드에, 없으면 목록 커서 행에 동작한다.
필터 바 오른쪽 ⓘ에 안내가 있다.

### 7.7 테마와 스킨 — 두 개의 독립 축

`<html data-theme data-skin>` 두 속성으로 갈린다. **밝기(theme)와 모양(skin)은
별개 축**이라 네 조합이 모두 성립한다. 둘 다 즉시 적용되고 `overrides.json`에 남는다.

| 축 | 값 | 바꾸는 것 |
|---|---|---|
| `theme` | `light` · `dark` | 색 |
| `skin` | `classic` · `bento`(화면 표기 **카드형**) | 색조·둥글기·그림자·서체 + 홈·리포트 배치 |

- **classic 은 스킨 블록의 영향을 받지 않는다.** `_SKIN_CSS`의 모든 규칙이
  `[data-skin='bento']`를 요구하므로, 고르지 않으면 존재하지 않는 것과 같다
  (회귀 테스트가 모든 선택자를 검사한다).
- **스킨은 토큰 오버라이드가 본체**다. `_CSS`는 컴포넌트 규칙에서 `var(--…)`를
  342곳 쓰고 색을 박아 넣은 곳은 9곳뿐이라 값만 덮으면 된다. 선택자 규칙은
  토큰으로 표현할 수 없는 것만 최소로 둔다(현재 3개). 규칙을 계속 더하고 싶어지면
  그건 스킨이 아니라 레이아웃 변경이라는 신호이므로 별도 렌더러로 간다.
- **특이도 함정**: 다크 토큰은 `:root[data-theme='dark']`(0,2,0)이라 스킨의 라이트
  블록과 같다. 순서로 이기게 두면 '다크+벤토'에서 라이트 색이 덮어쓰므로, 라이트
  블록에 `:not([data-theme='dark'])`를 붙여 특이도를 올린다.
- 벤토는 **강조색을 건드리지 않는다** — 라이트의 파랑, 다크의 코랄은 앱이 이미
  내린 판단이다(다크에서 파랑보다 눈이 편하다).

**레이아웃까지 바꿀 때의 선.** 색·모양만으로는 벤토의 감각이 안 나온다(목록 행이
이미 카드 형태라 토큰이 바꿀 것이 적다). 마크업을 바꾸되 **"이미 화면에 있는 것을
다시 배치"하는 데까지만** 한다 — 새 AI 호출이나 새 질의가 끼면 그건 스킨이 아니라
다른 기능이다(2026-08-01 사용자 지적). 현재 적용분은 하나다:

- **리포트 절 카드** — `_md_to_html(cards=True)` 가 `##` 절마다
  `<section class='rcard'>` 로 감싼다. 읽는 파일도 계산도 그대로고 감싸는 방식만
  바뀐다. `## 참고` 는 이미 접힘이라 이중으로 감싸지 않고, 꼬리말(조사 범위)은
  카드 밖에 둔다. classic 은 `cards=False` 로 지금과 완전히 같은 HTML 이다.
- **벤토 홈** — 랜딩(`_ask_landing`)이 '이어서 볼 것' 줄 대신 격자를 깐다.
  재료는 지금 랜딩이 이미 읽는 값(장기기억 카운트·최근 주간 보고·자주 왕래)과
  **저장된 오늘 회고 파일**(`load_daily` + `_md_sections`)뿐이다 — 리포트를
  **다시 만들지 않는다**. 회고가 없으면 그 타일을 그리지 않고, AI 가 쓴 절
  (Executive Summary)은 사용자가 AI 회고를 돌렸을 때만 파일에 있으므로 있으면
  보여주고 없으면 비운다. 홈에는 '처리함' 버튼을 달지 않는다(누르면 화면이
  튄다) — 다만 이미 접힌 항목은 같은 집합을 써서 홈에서도 빠진다.
  실측: 클래식 홈 DB 질의 2회, 벤토 5회(0.04 → 0.14ms). 결정론 엔진을 돌렸다면
  회당 +7.4ms 였다.
  **칸 크기는 내용 수에 맞춘다** — 전부 같은 크기면 격자가 아니라 표다. 12열 위에서
  줄이 딱 떨어지는 조합만 쓴다(내용 타일 1장 `12` / 2장 `8+4` / 3장 `12+6+6`,
  숫자 타일 3장 `4+4+4`). 화면 표기는 '카드형'이고 **저장값은 `bento` 그대로**다 —
  값을 바꾸면 이미 고른 설정이 조용히 풀린다(장기기억의 '반영/유보'와 같은 방식).

### 7.8 다크 모드에서 메일 본문

메일은 **흰 배경을 전제로** 색을 고른다. 메일 본문은 `body`의 `--bg`(다크 기준
`#16181b`) 위에 그려지는데(`#right`·`.msg`에 배경 선언이 없다), 거기 그대로 얹으면
Outlook 기본 강조색이 전부 WCAG AA(4.5:1) 미달이다 — 빨강 `#C00000` 2.75:1 ·
파랑 `#0070C0` 3.45:1 · 보라 `#7030A0` 2.22:1. 그래서 `.mailhtml *`을 테마색으로
평탄화하는데, 그러면 작성자가 준 강조가 전부 사라진다.

`clean.add_dark_colors()`가 **색상(H)은 두고 명도(L)를 올린**(채도는 0.75로 상한)
값을 `--dk` 커스텀 속성으로 함께 실어 보내고, 어느 쪽을 쓸지는 CSS가 고른다.

```
<span style="color:#C00000; --dk:#ec7979">      6.42:1 로 올라가면서 빨강은 빨강
```

- 채도 8% 미만(검정 본문·회색 안내문)은 손대지 않는다 — 본문 글자는 테마색이 맞다
- **인라인 `!important`는 렌더 시점에 걷어낸다** (2026-07-27). 인라인 스타일의
  `!important`는 시트의 `!important`를 항상 이기므로, 남기면
  `color:black!important`(Confluence·뉴스레터형 표 템플릿에 흔한 패턴)가
  평탄화를 뚫고 다크 배경 위 검은 글자로 남는다. 메일 색과 경쟁하는 시트
  규칙은 다크에만 있어 제거해도 라이트 표시는 안 변한다 — `add_dark_colors`가
  `--dk` 주입과 함께 처리한다
- **저장이 아니라 렌더 시점**에 붙인다. 저장 시점에 구우면 이미 저장된 메일은
  재수집해야 색이 살아나고, 그건 §1 원칙 5 위반이다. 비용은 데모 코퍼스 기준
  본문 1건당 0.002ms(색이 많은 본문도 0.03ms 미만)
- **서버가 한쪽 색만 구워 보낼 수 없다.** 테마 토글이 클라이언트에서 즉시
  `data-theme`을 바꾸고 다시 받아오지 않기 때문이다
- CSS 두 줄의 **순서가 중요하다** — 자손 상속이 먼저, 자기 색이 나중. ①이 없으면
  `<span color=red><b>긴급</b></span>`에서 `<b>`가 평탄화에 걸려 혼자 흰색이 된다.
  둘의 특이도가 (0,4,1)로 같아 순서가 승부를 가른다. 링크는 둘 다 제외(링크색 유지)
- 라이트 테마에는 `--dk`를 읽는 규칙이 없어 선언만 남고 무해하다

**배경색은 아직 다루지 않는다** — 형광펜과 표 헤더 `bgcolor`는 다크에서 사라진다.
살리려면 배경 명도를 낮추면서 그 안 글자 대비까지 함께 설계해야 한다.

### 7.9 SPA 배선 (건드릴 때 주의)

- `paneFor(path)`(클라이언트)와 `route()`의 pane 배정(서버)이 **반드시 일치**해야
  한다. 어긋나면 폴링이 엉뚱한 패널을 보다가 대기 화면이 멈춘다.
- `history.pushState`는 `inject()` 한 곳에서만 부른다. 뒤로가기는 좌·우 URL과
  깊이를 함께 담은 상태로 두 패널을 동시에 복원한다.
- 백그라운드 잡(리뷰·동기화·분석·주간)은 단일 슬롯 + 진행 dict + `/xxx/status` 폴링
  구조를 공유한다.
- 분석 잡 생성은 **POST `/ask/jobs`**만 한다. GET은 저장된 것만 연다 — 새로고침이나
  북마크가 AI를 부르면 안 되고, 질문 문구가 브라우저 이력에 남아서도 안 된다.

### 7.10 보안

- stdlib `http.server`, 의존성 0, **`127.0.0.1` 바인딩만**
- CSP — 원격 이미지(추적 픽셀) 기본 차단, 인라인 스크립트 차단(`script-src 'self'`)
- POST Origin 검사
- 메일 HTML은 저장 시 정제하고 CSP로 다시 막는다(이중 방어)
- 단일 스레드 `HTTPServer`가 의도다 — Outlook COM은 스레드마다
  `CoInitialize`가 필요하고, sqlite 스레드 규칙도 함께 피해 간다. 로컬 1인 도구 전제.

| `stats` | 저장소 통계 | ✗ |

**`--ai` 플래그가 없어도 AI를 부르는 것이 셋 있다** — `ask <질문>`, `ask --person`,
그리고 `diagnose`다. `diagnose`는 `--ai` 인자가 아예 없는데도 설정된 백엔드에
짧은 시험 호출을 보낸다(`cli.py`의 `[AI 백엔드]` 절). 플래그 유무가 아니라 이 표의
AI 열을 기준으로 판단한다.

`serve`는 명령 자체로는 호출이 0이다. 웹 UI를 열어 두는 것만으로는 AI가 돌지
않는다 — 화면을 열 때 배경에서 도는 일간 회고 자동 생성은 `ai=False`로 결정론
층만 만든다(`_maybe_auto_review`). AI는 **사용자가 누를 때만** 나간다: 분석 질문 ·
AI 회고 버튼 · 주간 보고(AI) · AI 검색 · 인물 AI 요약 · 메일 분석.

메일 분석(2026-07-30)은 스레드 화면의 메일별 '분석' 버튼 — 그 메일+스레드를
seed 로 분석 엔진(ask)을 돌리되 범위를 잠그지 않아 관련 스레드로 확장한다
(`ask.analyze_mail`). 결과는 ask_cache 에 영구 저장돼 분석 이력에 나타나고,
머리글이 '분석 보기 · N일 전 · 이후 새 메일 M통'으로 낡음을 알린다. 제거된
회신/기한 신호의 '이 메일이 뭘 요구하나'를 온디맨드로 대체하는 기능이다.

인물 요약은 2026-07-29 까지 일간 회고 파이프라인에 얹혀 있었다(회고가 돌 때마다
상위 15명 중 낡은 6명을 배치 갱신). 하루 정리와 인물 카드 유지보수는 성격이 다른
일이라 한 버튼의 비용·시간에 묶여 있을 이유가 없어, **인물 화면의 '요약 갱신'
버튼**으로 분리했다(`distill.refresh_person_dossier`, 1인 1콜). 대신 자동 신선도가
사라지므로 카드 푸터가 경과일과 반영되지 않은 새 메일 수를 함께 보여준다.
`DOSSIER_VALIDATOR_VERSION` 을 올려 옛 카드가 숨겨졌을 때도 화면이 다시 만들기를
안내한다 — 배치가 없으니 그것이 유일한 복구 동선이다.

## 9. 검색 DSL

| 표현 | 의미 | 예 |
|---|---|---|
| 일반 단어 | 제목·본문 | `납기 검토` |
| `"정확한 구"` | 연속 구 | `"최종 승인"` |
| `from:` `to:` `cc:` | 사람 (이름은 공백 무시, `@` 있으면 주소) | `from:강미래` |
| `after:` `before:` `on:` | 날짜 (`YYYY` \| `YYYY-MM` \| `YYYY-MM-DD`) | `after:2026-01` |
| `is:` | `unread` `read` `sent` `received` `flagged` | `is:unread` |
| `has:attachment` | 첨부 있음 | |
| `file:` | 첨부 파일명 | `file:schedule.xlsx` |
| `thread:` | 특정 스레드 | `thread:42` |

`after:`는 이상(포함), `before:`는 미만(배타). **OR 문법은 없다** — 필요하면
여러 번 검색한다.

### 완화 tier

정밀 → 느슨 순으로 내려가며 `limit`을 채운다. `--json`의 `tier` 필드로 노출된다.
**tier 가 1차 정렬키**이고, 같은 tier 안에서는 `bm25(fts, 3.0, 1.0)`(제목:본문 = 3:1)
→ 최신순이다. 시간 감쇠 블렌드는 넣지 않았다 — 지금은 동점일 때만 최신이 이긴다.

| tier | 방식 |
|---|---|
| 0 | 본문 검색어 없이 필터만 |
| 1 | 연속구 |
| 2 | FTS AND |
| 3 | LIKE AND (부분일치) |
| 4 | FTS OR — **유일한 '관련 낮음'** |

**trigram FTS는 3자 미만 토큰을 색인하지 못한다.** 그래서 2자 이하 한국어
키워드는 `LIKE`로 우회하고, 인접한 2자 단어는 구(phrase) tier로 회수한다.

## 10. 테스트

```bash
python3 -m unittest discover -s tests -p 'test_*.py'
```

외부 의존 없이 수 초 안에 끝난다. `tests/test_mailkb.py` 한 파일에 850건 이상이
들어 있고, 이 저장소에서는 **테스트가 사양서 역할**을 한다. 기능을 바꾸면
테스트도 함께 바꾼다.

| 파일 | 내용 |
|---|---|
| `tests/test_mailkb.py` | 본체 — 정제·신호·검색·분석·웹 라우팅·렌더 |
| `tests/test_synthetic_corpus.py` | 합성 코퍼스 자체의 성질 |
| `tests/synthetic_corpus.py` | 코퍼스 생성 헬퍼 |
| `tests/benchmark_wordmap.py` | 인물 어휘 fast/raw 성능·동등성 |

Outlook COM은 Windows에서만 동작하므로 여기서는 실제 동기화를 검증할 수 없다.
웹 흐름은 임시 홈 + 각본대로 답하는 가짜 AI 백엔드를 만들어 `serve`로 띄우고
`curl`로 태우는 HTTP 에뮬레이션으로 확인한다. 자세한 것은 [CLAUDE.md](../CLAUDE.md).
