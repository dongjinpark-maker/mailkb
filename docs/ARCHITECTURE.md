## 1. 무엇을, 왜

**문제.** 업무 메일은 조직의 결정이 실제로 일어나는 곳인데, 메일 클라이언트는
그것을 기억해 주지 않는다. 6개월 전 "그래서 최종 결론이 뭐였지"를 답하려면
사람이 스레드를 뒤져야 하고, 답장을 기다리는 공이 어디서 멈췄는지도 머릿속에만 있다.

**입장.** mailkb는 메일 클라이언트를 대체하지 않는다 — 보내고 보관하고 규칙을
거는 것은 Outlook에서 그대로 한다. mailkb는 **읽기**를 로컬 웹으로 가져오고(읽기
전용 — 답장·삭제·이동이 없다), 그 위에 **Outlook이 못 하는 것**을 얹는다: 기억,
검색, 지식화, 심화 분석. 처음(2026-07)에는 "읽고 쓰는 것은 Outlook"이었는데, 웹이
스레드 타임라인·인용 접기·AI 브리핑을 갖추면서 읽기의 무게중심이 이쪽으로 왔다
(2026-08-21 문구 정정).

| Outlook이 하는 것 | mailkb가 하는 것 |
|---|---|
| 수신·발신·보관 | 아카이브 인덱스(전문검색) + 읽기 전용 웹(메일함·스레드·인물) |
| 폴더·규칙 | 스레드 지식화(현안 브리핑·신호·쟁점 분석) |
| 알림 | 하루 끝 회고 · 주간 보고 |
| — | 암묵지의 지식화(사람이 승인해 md 로) |
| — | 근거가 달린 질의응답(웹 분석) · 심화 분석(`/mail-research` — 확보는 mailkb, 분석은 세션) |

**이름.** `mailkb` = mail knowledge base. 웹 UI의 표시 이름만 **Minerva**이고,
코드·폴더·명령은 전부 `mailkb`다.

### 설계 원칙 다섯

1. **표준 라이브러리만.** 코어에 서드파티 의존이 없다. Windows의 `pywin32`가
   유일한 예외이고 `sources/outlook_com.py` 안에 격리돼 있다. 사내 PC에서
   패키지 설치 승인을 받는 비용이 기능 하나보다 비싸다는 판단이다.
2. **AI는 opt-in.** 결정론 경로가 항상 먼저 있고, AI는 그 위에 얹히는 층이다.
   관문은 **`--ai` 플래그 또는 명령 자체**다 — `ask`(분석)와 `diagnose`(백엔드 점검)는
   그 자체가 AI 명령이라 플래그가 없다. 그 밖의 모든 명령은 `--ai` 없이 네트워크
   호출이 0이다(§8 명령표의 AI 열이 기준).
3. **AI 산출은 초안, 확정은 사람.** 수확된 암묵지 후보는 대기 상태로 쌓이고
   사람이 [지식으로 저장]/[유보]를 누른다. 저장된 것만 md 파일이 되어
   검색·분석의 재료가 된다(§6.6b).
4. **인용은 코드가 검증한다.** AI가 메일을 인용하면 그 문자열이 실제 본문에
   있는지 코드가 대조하고, 통과한 것만 남긴다. 환각 차단이 프롬프트 지시가 아니라
   실행 경로에 있다.
5. **재수집을 강요하지 않는다.** 파생 로직이 바뀌어도 사용자가 Outlook에서
   다시 긁을 필요가 없다. 회사 PC의 전체 재수집은 수십 분짜리 작업이다.

## 2. 전체 흐름

```
Outlook (원본·hot, COM)
      │
      │ sources/  ── MailRecord 스트림 (시간순)
      ▼
   store.ingest ──┬─ clean: HTML→마크다운 · 인용 제거 · 서명 제거
                  ├─ features: 문장 단위 신호 비트
                  ├─ terms: 인물별 어휘 피처
                  └─ FTS5(trigram) 색인
      │
      ▼
   SQLite (db.sqlite) ── 메타 + 신규내용 + 누적요약 + 지식 색인 + 파생 상태
      │
      ├── CLI:  ls · search · show · thread · review · ask · weekly · stats
      ├── Web:  Minerva (localhost, 좌/우 분할 SPA)
      └── vault/ (마크다운)  daily/ · weekly/ · notes/ · knowledge/
```

- 원본과 첨부는 Outlook에 그대로 둔다. `GetItemFromID`(EntryID)로 O(1) 참조하고,
  폴더 이동으로 EntryID가 바뀌면 Message-ID(영구)로 재검색한다.
- **메일 본문과 파생 지표는 재생성 가능하다** — 원본이 Outlook에 있으므로 지우고
  다시 `sync`하면 돌아온다. 그러나 `db.sqlite`는 **사람의 산출물도 함께 담는다**.
  그것들은 재수집으로 복구되지 않으므로 **DB 파일 삭제는 백업 없이 되돌릴 수 없다.**

  ```
  sync 로 복구됨      messages · message_html · people · messages_fts
                     threads(요약·스레딩) · 모든 파생 테이블
  복구 안 됨          knowledge_candidates(저장/유보 이력) · ask_cache(분석 이력)
  (백업 필수)         people_dossier(인물 요약) · action_overrides(신호 해제)
                     threads.flagged / threads.hidden · vault/
  ```

### 토큰 깔때기

AI 비용은 입력량에 비례하므로, AI에 닿기 전에 네 번 줄인다.

```
① 노이즈 필터      발신자·도메인·제목 패턴으로 제외
② 인용 제거        "새로 쓰인 부분"만 남김  (합성 282통 실측 절감 86%)
③ 롤링 요약 캐시   스레드 요약은 신규분만 갱신
④ 하루 1회 분석    실시간 호출 없음
```

②가 핵심이다. 검색 품질과 AI 토큰을 동시에 개선한다 — 12통짜리 스레드에서
같은 인용문이 12번 색인되는 것을 막는다.

## 4. 데이터 모델

`db.sqlite` 한 파일에 19개 테이블 + FTS5 가상 테이블 하나.

### 원본 성격

**원본은 Outlook 에 그대로 둔다 — 여기는 색인이지 사본이 아니다.** 로컬 보존
연한에 제한이 없음을 확인하고 `.eml` 복사를 폐기했다. COM 이 어차피 원본 MIME 을
주지 않기도 한다(MAPI 저장이라 재조립본이 된다).

| 테이블 | 내용 |
|---|---|
| `messages` | 메타 + `new_content`(인용 제거 본문). `id` 는 시각에서 계산한 11자리 정수(§4 '번호 체계'), `ingest_seq` 는 도착 순서 |
| `message_html` | 표시용 정제 HTML — 큰 blob을 분리해 `messages` 행 스캔을 가볍게 유지 |
| `threads` | 스레드 + 진단(`rolling_summary`). **단 `flagged`·`hidden` 두 컬럼은 사용자 상태**라 재수집으로 복구되지 않는다 |
| `people` | 인물 집계 |
| `messages_fts` | FTS5 **trigram**(한글 부분일치). 구버전 SQLite는 `unicode61` 폴백 |
| `notes` | 스레드 노트 **색인**(2026-08-11) — 원본은 `vault/notes/*.md`. 웹 인라인 편집기도 외부 편집기와 같은 자격의 편집자라 **파일 → DB** 방향은 그대로다(저장은 방금 쓴 본문을 바로 색인, 그 밖에는 `reindex`가 mtime 으로 따라간다). 색인은 지워도 재색인으로 복구 |
| `knowledge_candidates` | 암묵지 후보(2026-08-14) — 수확이 캐고 사람이 회고 화면에서 저장/유보. 승인 전에는 md 파일이 없다(§6.6b) |
| `knowledge` | 지식 **색인** — 원본은 `vault/knowledge/*.md`(사람이 승인해 만든 산출물). 미러라 지워도 `knowledge.reindex` 가 복구 |

### 사람의 산출물 (재생성 불가)

| 테이블 | 내용 |
|---|---|
| `messages.gone_at` | Outlook 에서 못 찾은 시각 (NULL=정상) — 판정에서만 제외, 내용은 유지(§6.8) |
| `action_overrides` | **신호 해제만** — `dismiss_action`(회신 필요·확인 후보·⏰), `dismiss_deadline`(⏰만). 숨김·플래그는 여기가 아니라 `threads`에 있다 |
| `people_dossier` | 인물 요약(AI 산출) |
| `ask_cache` | 분석 문답 이력 |

`action_overrides`는 해제 당시의 요청 메시지(`source_id`)에 키가 걸려 있어, 같은
스레드에 새 요청이 오면 자동으로 무시된다 = **신호 자동 복귀**. 스레드 전체를
덮는 숨김과 달리 그 요청 건만 끄는 장치다.

### 파생 (언제든 버리고 다시 만듦)

`message_features`, `thread_state`, `message_term_features`, `message_term_bags`,
`message_term_subject_delta`, `person_term_window`, `people_word_profiles`,
`distill_signals`, `ai_search`, `sync_state`

`reclean_backup` 은 파생이 아니다 — 절단 규칙 승격이 `new_content` 를 덮기 전의
원본이고, `sync` 는 이미 있는 메일을 건너뛰므로 **재수집으로 복원되지 않는다**.
`from_version` 이 '어느 버전 직전의 값인지'를 적는다(만료 후 다시 담긴 행은 최초
원본이 아니다). `RECLEAN_BACKUP_DAYS`(45일) 뒤 sync 의 프룬 훅이 지우며, 이 만료는
`image_retain_days` 설정과 무관하다. 복구 SQL 은 스키마 주석에 있다.

### 재수집을 피하는 장치

파생 테이블은 `ALTER`하지 않고 **드롭 후 재생성**한다(SQLite에 
`ADD COLUMN IF NOT EXISTS`가 없다). 재료가 전부 `messages`에 있으므로 Outlook을
다시 긁을 필요가 없다. 무효화는 **세 개의** 버전 키가 판단한다
(`clean_version` 은 앞의 둘을 캐스케이드로 무효화한다).

| 키 | 계산식 | 불일치 시 |
|---|---|---|
| `_feature_version()` | `FEATURE_VERSION` + `sha256(my_addresses + my_names)` | `message_features`·`thread_state` 재생성 → 전 메시지 재분류 → 행동 상태 재접기 |
| `_action_version()` | `sha256(ignore_senders + blocked_senders + subject_noise_strong)` | 본문·피처는 건드리지 않고 **행동 상태만 재접기** (1만 통 기준 약 9초 → 약 85ms) |

배정 규칙은 **"누가 그 값을 읽는가"**다. `classify_message`가 읽으면 feature 버전,
`_is_hard_noise`가 읽으면 action 버전, 질의 시점에만 읽으면(예: `external_allowlist`)
둘 다 아니다.

#### 인물 어휘 지도는 3단계로 따로 무효화한다

어휘 파이프라인은 재계산 비용이 단계마다 크게 달라, 위 두 키와 **별개로** 세 단계를
쓴다. 점수·표시 규칙만 바뀌었을 때 본문을 다시 토큰화하지 않으려는 것이다.

| 단계 | 키 | 무엇이 바뀌면 | 무엇을 다시 만드나 |
|---|---|---|---|
| ① 토큰 | `_term_feature_version()` = `WORD_FEATURE_VERSION` (+ 분석 창 검사) | 추출 규칙, `[dossier] window_weeks` | **본문 재토큰화** — `message_term_*`·`person_term_window` 전부 비우고 최근 창의 수신 본문을 다시 읽는다. 가장 비싸다 |
| ② projection | `_term_bag_version()` = sha256(`WORD_FEATURE_VERSION`, `WORD_BAG_VERSION`, `window_weeks`, 주소록 이름, 추가 불용어) | 가중·집계 방식, 이름·불용어 설정 | bag 재구축. 토큰은 그대로 쓴다 |
| ③ 표시 프로필 | `terms.profile_signature()` = `WORDMAP_VERSION` + sha256(위 둘 + 불용어 + 대조 집단 + `top_n` + 인물명 + 코퍼스 지문) | 점수·표시 규칙, 비교 대상 인물 집합 | 그 인물의 `people_word_profiles` 행만 재계산. 가장 싸다 |

①이 무효화되면 ②의 키도 함께 지워져 아래로 연쇄한다. 반대로 ③만 바뀌면 위 둘은
건드리지 않는다. **새 규칙을 넣을 때 어느 단계 상수를 올릴지가 곧 재계산 비용의
선택**이므로, 표시만 바꾸면서 `WORD_FEATURE_VERSION`을 올리면 불필요한 재토큰화를
전 사용자에게 강요하게 된다. `people_dossier`만 예외로 `ALTER` 경로를 쓴다 — AI 산출이라
재구성이 불가능하기 때문이다.

### 수집 불변식

- 청크 커밋마다 어휘 피처와 `last_sync` 워터마크를 **함께** 커밋한다 → 중간에
  죽어도 일관된 접두부가 남는다
- `sync_state`에는 **역할이 다른 두 시각**이 있다. `last_sync`는 수집한 메일의
  `sent_on` 워터마크라 새 메일이 0통이면 안 움직인다. `last_sync_checked_at`은
  **성공한 실행 시각**이라 0통이어도 전진하고 실패하면 전진하지 않는다. 화면의
  "동기화 HH:MM"은 뒤엣것이다 — 앞엣것을 쓰면 "방금 돌렸는데 시각이 그대로"가 된다
- `Store.basis_info()`는 사이드바가 **매 렌더** 부르므로 `stats()`를 쓰면 안 된다.
  `stats()`에는 `SUM(LENGTH(new_content))`가 있어 본문을 전부 훑는다(7.5만 통에서
  20ms 대 0.008ms). 인덱스로 끝나는 `COUNT(*)`와 키 조회만 한다
- `message_id UNIQUE` → 재실행이 멱등
- `PRAGMA synchronous=NORMAL` — DB가 다시 받아올 수 있는 캐시라 정당하다
- 전체 `VACUUM` 금지(단일 스레드 웹 서버가 멈춘다). `auto_vacuum=INCREMENTAL`만.
  단 그 PRAGMA 는 **새 DB 에서만** 건다 — 값이 이미 INCREMENTAL 이어도 재설정이
  쓰기 트랜잭션을 연다(실측)
- **읽기 경로는 한 줄도 쓰지 않는다**(2026-08-15). 웹은 요청마다 `Store` 를 열고,
  `ingest` 는 100통마다 커밋하며 그 사이 Outlook COM fetch 동안 쓰기 잠금을 쥔다.
  그래서 열기·조회 경로의 쓰기 한 줄이 곧 "화면이 멈춘다"가 된다 —
  `busy_timeout` 30초를 다 쓰고 `database is locked` 로 죽는다. **0행 UPDATE 도
  쓰기 트랜잭션이다**: 조건 없이 쓰지 말고 인덱스를 타는 읽기로 먼저 판별한다
  (`mark_thread_read`·`ingest_seq` 되메우기가 이 방식으로 고쳐졌다). WAL 이라
  읽기는 잠금과 무관하므로, 이 규칙만 지키면 sync 중에도 화면이 즉답한다
- **대기 예산은 "누가 기다려도 되는가"로 갈린다**(`Store` 상수). 열람 표시처럼
  미뤄도 되는 쓰기 `READ_MARK_WAIT_MS`=200ms(못 잡으면 넘기고 다음 열람에
  재시도, `skipped_read_marks` 로 센다) · 사용자가 누른 쓰기
  `UI_WRITE_WAIT_MS`=5s(단일 스레드라 길게 기다리면 **모든 화면이 함께**
  멈춘다 — 끊고 "잠시 후 다시 눌러 주세요") · 배경 잡의 정당한 쓰기
  `BUSY_TIMEOUT_MS`=30s. 셋의 순서가 곧 정책이라 테스트가 그 순서를 지킨다.
  실측(sync 가 쉬지 않고 커밋하는 중): 플래그 클릭 30초 뒤 `database is locked`
  → 5초 뒤 안내 문구, 그 사이 읽기 화면은 0.007–0.2초

### 번호 체계 — 날짜 + 15분 슬롯 (2026-08-13)

`messages.id`·`threads.id`는 SQLite가 매기는 순번이 아니라 **메일의 시각에서
계산한 11자리 정수**다.

```
id = YYMMDD × 100000  +  15분슬롯(0..95) × 1000  +  슬롯 내 순번(1..999)

2026-07-26 10:00 첫 메일 → 26072640001
```

**왜 이렇게 하나.** 종전에는 rowid(= 전체 코퍼스의 삽입 순서)였다. 그러면 수집
시작 날짜를 바꿔 다시 받을 때 앞이 잘린 만큼 뒤가 전부 앞당겨져, `vault/`에 박아
둔 참조(`weekly`·`review`의 `[#26072837001]`)가 **다른 메일을 가리킨다**. 오류가
아니라 오답이라 눈치채지 못한다.

번호를 시각에서 계산하면 **자기 데이터만으로 정해져** 남이 지워져도 구멍만 남는다.
데모 282통 실측 — 재구축 보존율:

| 그새 삭제된 양 | rowid | 날짜+하루순번 | **날짜+15분슬롯** |
|---|---|---|---|
| 수집 시작 날짜만 변경 | 0% | 100% | **100%** |
| 4% 삭제 | 0% | 78% | **99%** |
| 10% 삭제 | 0% | 58% | **98%** |

**정수인 것이 중요하다** — SQLite rowid 요건을 만족해 11개 FK 컬럼을 하나도 안
바꾼다. 표기도 정수 하나뿐이다(대쉬 `260726-018` 형태는 2026-08-13 폐지 — 슬롯
인코딩에서는 사람이 읽어 낼 뜻이 없어 형식만 둘로 늘렸다).

**슬롯이 차면 그날 안에서 다음 슬롯으로 흘린다.** 예외를 던지면 `_insert`를 뚫고
나가 `ingest`의 `_flush()`·워터마크 갱신을 건너뛰고, 다시 동기화해도 같은 메일에서
또 죽어 사용자가 손쓸 수 없다. 넘친 메일은 표시 슬롯이 실제 시각보다 뒤가 되는
것으로 값을 치른다. **다음 날로는 절대 굴리지 않는다**(다른 날 메일과 충돌).
그날(95,904건)을 다 쓰면 그때 예외다.

**`messages.ingest_seq` 는 신원이 아니라 '도착 순서'다.** id가 시각순이 된 뒤로
id는 "먼저 넣은 것"을 못 말한다. 그런데 mid-join 인용 보존(§6.1)은 "이 스레드에서
**내가 먼저 보유한** 메일"이 기준이고, 증분 캐시·`ask_basis`는 "그새 새 메일이
왔나"가 기준이다 — 둘 다 도착 순서다. 그래서 신원(id)과 도착 순서(`ingest_seq`)를
갈라 두었다. **id로 개수를 세거나 워터마크를 잡으면 안 된다** — 날짜 기반 번호는
차(差)가 개수가 아니고, 백필된 옛 메일은 워터마크보다 아래에 꽂힌다.

시각을 모르는 메일(Outlook이 `SentOn`/`ReceivedTime`을 안 주는 드문 항목)은
`000000` 버킷을 받는다 — 번호는 반드시 나와야 한다(id는 PK라 NULL이 없다).

## 5. AI 계층

### 계약 하나 — `review.ai_run`

```python
ai_run(cmd, prompt, timeout=300, retries=2,
       *, system_prompt=None, json_schema=None, effort=None,
       effort_flag=None, on_event=None, cancel=None) -> str
```

**프롬프트를 stdin으로 넣고 stdout을 받는다.** 그게 전부다. SDK도, API 키도,
HTTP 클라이언트도 없다. 인증·프록시·모델 관리는 `opencode`/`claude` 같은 CLI에
무임승차한다.

- 타임아웃·비정상 종료·빈 응답 → `AIError`, 2s·4s 백오프로 재시도
- 명령을 못 찾으면(`FileNotFoundError`) 재시도 없이 즉시 `AIError`
- 밖으로 나가는 예외는 셋: `AIError`(재시도 후 실패) · `AICancelled`(사용자 중지) ·
  `AIAuthError`(백엔드 인증 만료). 뒤의 둘은 `AIError` 하위가 **아니다** — 콜 단위
  graceful 삼킴(`except AIError`)을 전부 통과해 파이프라인 꼭대기에서 멈추기 위해서다.
  인증 만료 판정은 **백엔드 채널(stderr·CLI 오류 봉투)만** 본다 — 모델 stdout 에는
  사용자 메일에서 나온 문장이 실려, 판정에 넣으면 정상 응답이 오진된다
- `shutil.which`로 해석 — Windows의 npm `.cmd` 셰임 때문에 필요하다
- `encoding="utf-8", errors="replace"` — cp949면 이모지에서 죽는다
- claude 는 역할을 `--system-prompt` 로 분리 전달하고 `--tools ""`·
  `--no-session-persistence` 로 도구·세션 지속을 끄며, `--setting-sources
  user` 로 저장소 CLAUDE.md 주입(콜당 약 4k 토큰)을 차단한다. **setting-sources
  값은 반드시 `user`** — `""`(전부 제외)는 user 설정(`~/.claude/settings.json`)의
  env 까지 건너뛰는데, 그 env 가 모델 라우팅(별칭 해석·Bedrock 경유)을
  정의하는 환경에서는 `--model` 별칭이 다른 모델을 찾다 전 모델이 실패한다
  (2026-07-28 실기기 확정 — 실사고 원인). 그 밖의 stdin 어댑터는 같은 정보를
  `[SYSTEM]` 블록으로 prompt 앞에 붙인다. `--json-schema` 는 롤백 유지(JSON
  계약은 프롬프트 지시 + 관용 파서). **effort 는 opt-in 으로만 재개**(2026-08-02):
  `[ai.backends.<name>] effort_flag = "--effort"` 를 선언한 백엔드에만
  `<플래그> high` 가 붙는다 — 사고 원인은 `--setting-sources ""` 로 판명됐지만
  `--effort` 의 실기기 지원은 여전히 미검증이라, 미선언(기본)이면 argv 가
  종전과 같다. 플래그·값은 단일 토큰만 허용(cmd.exe 셔틀 보호). 실기기에서
  켜기 전 `diagnose` 로 1콜 검증을 권장.
- **`--system-prompt` 값은 한 줄로 접어서 보낸다(개행 금지).** Windows 의 npm
  CLI 는 `.cmd` 셔틀이라 실행이 cmd.exe 를 거치는데, cmd.exe 는 명령줄의 개행에서
  줄을 끊는다 — 여러 줄 값을 주면 첫 줄만 전달되고 **그 뒤 인자가 통째로 사라진다**
  (`--tools`·`--setting-sources`·스트리밍 플래그까지). 2026-07-28 실기기 확정:
  이 때문에 stream-json 플래그가 유실돼 주간 보고·분석이 전부 실패했다(같은 호출이
  개행만 접자 정상 수신). 리눅스는 execve 라 개행이 무해해 개발 환경에서는 드러나지
  않으므로 **플랫폼 분기 없이 항상 접는다** — 개발에서 검증한 것이 실기기에서 도는
  것과 같아야 한다. 같은 이유로 시스템 프롬프트 상수에는 cmd.exe 특수문자
  (`% & | < > ^ "`)를 넣지 않는다(회귀 테스트가 지킨다).
- 웹의 모든 백그라운드 잡(일간 회고·AI 검색·주간 보고·분석·인물 요약·메일
  동기화)은 **같은 대기 카드**(`web._job_wait_card`, prefix `rv/ai/wk/ask/dz/sy`)로
  그려진다 — 스피너·제목·실모델 배지·진행바(결정론 `단계 n/N` 또는 인디터미닛)·
  단계 문구·수신 줄·작성 중 초안·경과·중지. 관측되지 않는 슬롯(비스트리밍
  백엔드의 수신·모델)은 비고 CSS `.waitslot:empty` 가 그 줄을 숨긴다. 폴링은
  `app.js patchJob(tmp, host, prefix)` 하나로 슬롯만 제자리 패치한다(전체 교체는
  스피너·경과를 되감는다). 새 잡을 만들면 `_new_job`/`_job_start`/`_RUNNING_MARKERS`
  세 곳에 등록한다 — 마지막 것이 빠지면 JS-off 환경에서 그 화면만 안 넘어간다.
- 중지는 **스트리밍(claude) 경로에서만 즉시** 듣는다. 블로킹 경로는 진행 중인
  호출이 끝난 뒤 멈추므로 카드가 그렇게 말하고(`_cancel_hint`), 중지를 누른 뒤에는
  수신 줄이 '중지 요청됨'으로 바뀐다 — 안 그러면 버튼이 안 먹은 것처럼 보인다.
- 스트리밍 경로에서 **이벤트가 하나도 안 오면 원시 stdout 을 답으로 쓴다**
  (`plain_output` 으로 로그만 남기고 성공 처리) — 플래그 유실·구버전 CLI 로
  진행 표시를 잃는 것은 기능 실패가 아니다. 단 `{"error": …}` 오류 봉투는
  답이 아니므로 `AIError` 로 올린다.
- 실패는 `<home>/logs/ai_error.jsonl` 에 남는다(명령·exit·stderr/stdout 꼬리·
  소요·프롬프트 크기) — **재현 없이 로그에서 원인을 확인한다.** claude -p 는
  오류를 stdout 으로 내는 경우가 많아 stdout 꼬리도 오류 메시지에 싣는다.
  `[ai] error_log=false` 로 끈다.
- `on_event` 를 주면 **claude CLI 에 한해** `--output-format stream-json` 으로
  수신을 스트리밍하고 중립 이벤트를 흘린다 — `model`(init 의 실모델 ID) ·
  `phase`(thinking/writing) · `delta`(수신 문자 수, writing 은 텍스트 포함) ·
  `retry`. 반환값·오류 계약은 그대로다(결과는 여전히 완결 텍스트 하나).
  다른 백엔드는 이벤트 없이 기존과 동일하게 동작한다 — 웹 대기 화면(2a
  수신 표시 · 실모델 · 작성 중 초안 미리보기 · 30초 무수신 경고)이 이 이벤트의
  소비자다. 미리보기는 검증 전 초안임을 흐림+라벨로 명시한다.
- `cancel`(threading.Event) 이 켜지면 진행 중 프로세스를 죽이고
  `AICancelled` 를 올린다 — `AIError` 와 다른 타입이라 graceful 삼킴 경로
  (weekly `_ai`, 웹 폴백)를 타지 않고 파이프라인 전체가 멈춘다. 취소는
  실패가 아니라 사용자의 결정이므로 부분 결과를 저장하지 않는다.
  웹 대기 화면의 **중지** 버튼(`POST /weekly/cancel`·`/ask/cancel`)이 켠다.

이 계약 덕분에 백엔드는 교체 가능하다. `tools/bedrock_run.py`가 반대편에서
같은 계약을 구현한 예다 — 다만 **미유지다**(2026-07-28 이후 검증 없음, 쓰는 곳
없음). 설정 예시를 그 파일에서 뺀 이유는 하나다: 조리법이 머리말에 있으면
'지원 목록'처럼 읽히고, 붙여 넣는 순간 웹 설정의 AI 백엔드 상태에 올라와
[응답 시험]이 실제 과금 호출을 보낸다. 되살릴 때 확인할 전제는 그 파일 머리말에
남겨 두었다.

### 작업별 백엔드 라우팅

작업마다 비용·품질 요구가 달라 백엔드를 나눠 부른다. `config.toml`의 `[ai]` 항목이나
웹 **설정** 화면에서 바꾼다(설정 화면 변경은 `overrides.json`에 남아 재시작 불필요).

| 설정 키 | 기본 | 쓰는 곳 |
|---|---|---|
| `[ai] summary` | `sonnet` | 수확 · 디제스트 · 하루 요약 · **스레드 요약(버튼)** |
| `[ai] search` | `sonnet` | AI 검색 — 질의 번역 · 재순위 · 심층 읽기 |
| `[ai] ask` | `[ai] search` 상속 | **분석** — 조사 · 답변 작성 · 의미 검증 |
| `[ai] weekly` | `[ai] summary` 상속 | 주간 보고 — 본문 · 머리글 · 누락(3콜). 주 1회 무거운 호출이라 opus 지정 후보 |
| `[ai] default` | `internal` | 위로 라우팅되지 않는 호출 |

`ask`가 `search`를 상속하는 것은 호환 때문이다 — 분석 전용 키가 생기기 전에는 둘이
한 설정을 공유했다. 번역 위주인 AI 검색과 한 질문에 최대 12콜을 쓰는 분석은 요구가
다르므로, 필요하면 따로 지정한다. CLI `ask --backend`는 **그 실행 한 번만** 덮어쓰고
저장된 설정이나 사이드바 표시를 바꾸지 않는다.

저장된 답의 `scope.backend`는 **그 답을 실제로 만든 백엔드**다 — 나중에 설정을 바꿔도
과거 답의 기록은 그대로 남는다. `scope.model`(분석)과 주간 보고 푸터의 `모델 …`은
한 단계 더 간다 — 백엔드 *이름*(opus 등)은 움직이는 별칭이라, 스트리밍 init 이
알려준 **실모델 ID 실측값**을 남긴다(비스트리밍 백엔드는 빈 값).

### AI를 쓰는 곳과 실패 시 동작

| 기능 | 모듈 | AI 실패 시 |
|---|---|---|
| 하루 요약·스레드 요약 | `review.py` | 결정론 리뷰는 그대로 나온다 |
| 신호·암묵지 수확 | `distill.py` | `None` 반환, 워터마크 안 전진 → 다음 실행에 재시도 |
| 인물 요약 | `distill.py` | 기준 카운트 안 전진 → 재시도 |
| 분석(질의응답) | `ask.py` | `AIError`를 올려보내고 호출부가 **일반 검색으로 폴백** |
| 스레드 쟁점 분석 | `ask.py` | 분석과 동일 — `AIError` → 일반 검색 폴백 |
| 주간 보고 | `weekly.py` | 삼키고 결정론 뼈대만 |
| AI 검색 | `review.py` | 일반 검색 |

원칙은 하나다 — **결정론 경로는 항상 살아남는다.**

### AI 프롬프트에서 빠지는 것 — 숨긴 스레드

숨김(`hidden`)은 "조용히"라는 뜻인데, 종전에는 `weekly.collect` 만 걸렀다 —
숨긴 스레드의 원문이 롤링 요약·수확·분석·AI 검색·인물 요약 프롬프트에 그대로
실렸다. 이제 **AI 재료를 조립하는 모든 경로**가 `store.hidden_thread_ids()` 로
거른다(검색 후보·seed·정독·스레드 전개·본문 심사·도시에 재료·문체 표본·디제스트).

- **예외 하나** — 사용자가 그 스레드의 메일에서 직접 [분석]을 누른 경우
  (`ask(allow_tids=…)`). 명시 의도가 '조용히'보다 우선한다. 확장 검색이 잡는
  **다른** 숨김 스레드는 여전히 제외된다.
- **표시 축은 불변** — 결정론 보고 뼈대·메일함 숨김 탭·`store.search`(일반
  검색)는 그대로다. 제외는 AI 축이다.
- **한계**: 숨기기 **이전**에 만들어진 산출물(ask_cache 의 옛 답·기존 롤링
  요약·과거 주간 .md)은 소급 정화하지 않는다(재수집 강요 금지와 같은
  트레이드오프). 그리고 hidden 은 새 수신 메일이 오면 자동 해제되므로 영구
  기밀 장치가 아니다 — 발신자 단위 영구 제외(ai_exclude 목록)는 검토 후
  보류했다(2026-08-02 사용자 결정), 필요해지면 그때 설계한다.

### AI 프롬프트에 더해지는 것 — 노트·지식과 사용자 지침

- **내 노트 주입(2026-08-11)** — 사용자가 스레드에 직접 쓴 노트
  (`vault/notes`, 스레드 화면의 [내 노트])를 분석(ask·브리핑) 프롬프트에
  `[내 노트 — 문맥 전용, 인용 금지]` 블록으로 싣는다(`ask._notes_block`).
  선정은 결정론: 직접 지목(allow_tids — 메일·쟁점 분석) 스레드의 노트는 무조건,
  나머지는 질문 토큰 겹침 상위 3건, 겹침 0이면 생략, 숨긴 스레드 제외.
  '인용 금지'의 강제는 코드가 한다 — 노트 문장을 인용해도 검증(정독 본문
  대조)에서 떨어진다.
- **지식 주입(2026-08-14, §6.6b)** — 사람이 승인해 저장한 지식
  (`vault/knowledge/*.md`)을 같은 자리에 `[지식 — 문맥 전용, 인용 금지]`
  블록으로 잇는다(`ask._knowledge_block`, memory 문자열에 이어 붙여 프롬프트
  계약 불변). 선정은 노트와 같은 결정론(질문 토큰 겹침 상위 3건, 겹침 0이면
  생략), 참조 스레드가 전부 숨김이면 제외.
- **사용자 지침(`<home>/ai-rules.md`)** — 사내 용어·우선순위 같은 자연어
  지침. 종전 수확 한 곳에서 수확 + 분석(STEP·ANSWER) + 주간(WRITE·OVERVIEW)
  으로 확장. 검증 콜(VERIFY·REPAIR·VERIFY_REPORT)에는 넣지 않는다 —
  검증기의 "외부 지식 금지" 계약을 문맥 주입이 흔들면 안 된다.
  `init` 이 **주석만 든 템플릿**(`config._AI_RULES_TEMPLATE`)을 만들어 둔다
  (2026-08-21) — 형식 설명을 HTML 주석으로 써서 "주석은 AI 가 보지 않는다"를
  파일이 스스로 증명하고, 주석뿐이면 주입이 0자라 설치 직후 프롬프트가 바뀌지
  않는다. 제거 정규식이 비탐욕이라 설명문에 닫는 기호를 적으면 거기서 주석이
  끝나 나머지가 샌다 — 템플릿은 기호 대신 말로 쓰고, 테스트가 주입 0자를 잠근다.
  파일이 원본이고 편집은 외부 편집기로 — 노트·지식과 같은 태도라 설정 화면에
  편집 UI 를 두지 않았다.

## 6. 핵심 파이프라인

### 6.1 수집 시 본문 정제 (`clean.py`)

`Store._insert` 안에서 메시지마다:

1. **`extract_new_content`** — 인용 시작점을 찾아 자른다(대시+라벨 줄, `On … wrote:`
   계열 귀속줄 6개 언어, `_{10,}`, 헤더 블록). 헤더 블록 판정은 2단 게이트다:
   From 라벨(한·영·불·독·서·이·화·일·중, 전각 콜론과 `**굵은 라벨**` 포함) 뒤
   6줄(빈 줄 제외) 안의 후속 필드 수가 **3개 이상**이어야 자른다. 발신인 줄에
   메일 주소가 있으면 2개로 낮춘다 — 문서 머리·표에는 주소가 없다. 이 기준이
   한국 공문(발신/수신/참조/제목)·물류 구간표·번역 대조표가 잘리던 오탐을 막는다.
   귀속줄(`On … wrote:`·`…님이 작성:` 등 6개 언어)도 같은 줄에 주소가 있을
   때만 인정한다.
   규칙을 넓히면 `clean.CLEAN_VERSION` 을 올린다 → 다음 열기에서 저장된
   `new_content` 를 1회 소급 재절단하고(원본은 `reclean_backup` 에 보관, 45일)
   파생 캐시를 무효화한다. 재수집은 필요 없다.
   `>` 줄 제거 → 서명·법적 고지 제거(**본문 2줄은 반드시 남긴다**) → 빈 줄 정리.
2. **`sanitize_html`** — 허용 목록 기반 태그·속성 정제, 원격 이미지 차단
   (`data-blocked-src` 로 URL 보존 — [위험을 감수하고 보기] 화면에서 브라우저가
   직접 로드, §7.10).
   SVG 는 통째 삭제하되 "다이어그램 생략" 한 줄을 남기고(무흔적이면 "이미지가
   안 나온다"는 문의가 된다, 2026-08-15), 텍스트/마크다운 추출(`_SKIP_TAGS`)도
   svg·math 를 같이 건너뛴다 — 라벨 조각이 검색·AI 본문에 새지 않게.
   파서가 터지면 `<pre>` + 이스케이프 텍스트로 폴백. 인용 절단도 여기서 따로
   한다: 경계 태그(`<hr>`·`border-top` 스타일 div·`divRplyFwdMsg`·Mac 컨테이너)
   뒤에 From 라벨이 오면 **후보**로 잡고, 이어지는 청크에서 후속 필드 2개를
   확인해야 자른다(라벨 한 줄로는 안 자른다). 저장된 `message_html` 은 소급
   재절단 대상도 백업 대상도 아니라 여기서의 오탐은 영구 손실이기 때문이다.
   조판용 표(스페이서)는 자르지 않고 **표시만 남긴다** — 작성자가 단
   `role="presentation"` 을 보존하고, `border`/`cellpadding`/`cellspacing` 도
   그대로 둔다. 화면 CSS 가 그 신호를 보고 테두리·패딩을 뺀다(알림 메일이 빈
   테두리 박스로 보이던 문제). 자르지 않는 이유는 같다 — 여기서의 오탐은 되돌릴
   수 없고, 표시는 CSS 를 되돌리면 그만이다.
3. **`inject_inline_images`** — 2단계를 통과한 HTML에만, cid당 한 번만 임베드.
   **정제 뒤에 넣는 순서가 보안 조건이다** — 먼저 임베드하면 정제기가 걸러야 할
   표면이 base64 로 부풀고, 원격 `http` 이미지 차단(추적 픽셀)도 그 단계에 있다.

**표시용 HTML 은 수명이 따로 있다.** `image_retain_days` 가 지나면 sync 가
`message_html` 을 비운다 — 이미지가 있었으면 `<div class='imgstrip'>` 한 줄
배너로 대체하고("보존 기간 경과, Outlook 에서 확인"), 없었으면 통째로 버린 뒤
`VACUUM` 으로 공간을 회수한다. 표시는 `new_content` 텍스트로 내려앉는다.
**검색·AI 는 영향이 없다** — FTS 도 요약·수확·분석도 전부 `new_content` 기반이라
`message_html` 은 어느 지식 기능에도 안 쓰인다. 그리고 꼬리의 이미지 서명(로고·
명함 카드)은 저장이 아니라 **표시 시점**에 `hide_image_signatures` 가 한 줄로 접는다.

**중간 합류(mid-join) 예외.** 이 메일이 스레드를 처음 만들었다면
(`preserve_quotes=True`) 인용 사슬을 버리지 않고 `PRESERVED_MARK` 아래 그대로
붙인다. 스레드 중간에 참조로 들어온 경우 **그 사슬이 이전 대화의 유일한 사본**이기
때문이다.

- **판정은 "내 사서함 기준 첫 보유분"이다.** '대화의 진짜 첫 메일'은 관측할 수
  없지만 그건 필요하지도 않다 — 시간순 입력 하에서 `store._assign_thread` 가
  **새 스레드를 만드는 순간의 메일**이 정확히 그것이다. 보존 조건은 `새 스레드
  생성 + 인용 체인 존재` 둘뿐이다.
- **전제는 수집이 전역 시간순이라는 것이다.** 폴더를 차례로 훑으면(받은편지함
  전체 → 보낸편지함 전체) 폴더 안에서만 시간순이라, 내가 시작한 스레드의 백필에서
  상대 답장이 내 원 메일보다 먼저 들어와 **인용본을 보존해 버리는 오탐**이 났다.
  `OutlookComSource.fetch` 가 폴더별 스트림을 `heapq.merge` 로 병합해 이 가정을
  실제로 성립시킨다. 하위 폴더가 붙어 스트림이 N 개로 늘어도 같은 계약이다 —
  각 스트림이 자기 안에서 시간순이면 병합 결과는 전역 시간순이다(§6.7).
- 수용한 오탐 하나 — 30일 밖에서 재개된 스레드는 제목 매칭이 끊겨 새 스레드가
  되고 인용이 보존된다. 표시로는 맥락 복원이라 오히려 낫다.

**그 사본은 대화 턴으로 읽힌다 (2026-08-06).** 보존 사슬을 갖고 있으면서도 화면은
'이전 대화 (인용 보존)' 한 줄로 접어, 몇 턴이 누구 사이에 오갔는지도 안 보였다 —
실측 예: 스레드에 메시지는 3통인데 실제 대화는 5턴이고 앞 2턴이 그 덩어리 안에만
있었다. `clean.parse_preserved` 가 헤더(`보낸 사람/보낸 날짜/제목`, 한글·영문 ·
마크다운 변환본 모두)를 읽어 턴 목록으로 만들고, `preserved_label` 이 접힘
머리줄을 만든다 — `앞선 대화 2턴 — 강미래 선임 → 오태양 책임 · 07-31 ~ 08-01`.

- **기본은 접힌 채**다. 머리줄만으로 "내가 못 본 대화가 여기 있다"가 전해지므로
  주목 예산을 쓰지 않는다.
- **복원 턴은 메시지가 아니다.** DB 행이 없어 링크·앵커·검색 결과가 없다. 그래서
  링크를 주지 않고 `인용에서` 라고 출처를 밝히고 흐리게 그린다. 목록의 `[N통]` 도
  그대로 둔다 — 메시지 수는 안 늘었다.
- **파싱 실패는 보이지 않는다.** 못 읽으면 빈 목록이라 종전 화면 그대로다.
- **저장 HTML 은 렌더 시점에 갈아 끼운다**(`clean.retitle_qfold`). 접힘은 수집 때
  `message_html` 에 구워지므로 상수를 고쳐도 기존 메일은 안 바뀌고, 재수집은
  불변식(#5) 위반이다. `hide_image_signatures`·`add_dark_colors` 와 같은 자리다.
  HTML 층은 원본 서식을 지키느라 머리줄만 바꾸고, 턴 렌더는 텍스트 층에서 한다.

정제 철학: **과잉 제거보다 과소 제거가 낫다. 애매하면 남긴다.**

### 6.2 신호 판정 3층

```
L1  message_features   수집 시 1회, 메시지 단위 비트     (features.py)
L2  thread_state       증분 접기, 스레드 단위 집계        (store.py)
L3  actions.evaluate   질의 시 판정, 본문 재열람 없음     (actions.py)
```

- **문장 단위 게이팅.** 문장별로 판정한 뒤 OR한다(순서 무관). 한국어 맺음말
  "잘 부탁드립니다"가 요청 신호를 지배하지 않게 하려는 것이다. 단 "다시/재차/리마인드"는
  게이팅된 요청을 되살린다. "마지막 의도 채택" 방식은 그 맺음말 하나에 깨져서
  채택하지 않았다.
- **L2 는 스레드당 열린 요청 슬롯 1개**짜리 상태기계다(`store.fold_action`).
  최신 요청이 우선한다는 스레드 단위 도구의 철학을 그대로 따른 의도적 단순화이고,
  전이가 **순수 함수 하나**여서 증분 갱신·역순 삽입 refold·백필이 모두 같은 코드를
  지난다 — **증분 ≡ 전체 재계산**이 정의상 성립한다(무작위 순서 삽입 drift 테스트가
  지킨다). 열린 창 안에서 강도·기한은 단조 증가만 하고 `action_source_id` 만
  최신 요청으로 갱신한다.
- **슬롯을 닫는 것은 둘뿐이다** — 내 **실질** 발신(`++수신인 추가`·빈 본문 같은
  trivial 은 제외)과 명시적 철회("회신 불필요"). **상대의 완료 통보는 닫지 않는다** —
  `completion_after_action` 표시 후 MAYBE 강등까지다. 잘못 닫히면 조용한 실패가
  되는데 잘못 열려 있으면 눈에 보이기 때문이다(아래 비대칭 비용과 같은 이유).
- **비대칭 비용.** 놓치는 쪽(false negative)이 치명적이므로, 부정 규칙은 `NONE`이
  아니라 **`MAYBE`(접힌 확인 후보)**로 보낸다.
- 모든 `REQUIRED`/`MAYBE`는 사유 코드를 달고 다닌다(설명 가능성).
- 수신 대상 사다리 — 직접 수신·이름 지목·내 참여는 '회신 필요', 그룹·대량 발송·
  외부 발신은 '확인 후보'로 강등한다. 수신 50명 전사 메일의 "회신 바랍니다"가
  개인 액션 목록을 오염시키지 않는 장치다.

**엔진은 남기고 노출은 걷어냈다** (2026-07-30). 목록의 ↩/⏰ 탭·스레드 칩·`x` 키·
데일리 '지금 할 일'·개입 AI 분류(haiku 2콜)·CLI `act` 를 전부 제거했다 — 정규식
판정의 정밀도가 낮아 **상시 노출이 도구 신뢰를 깎았기** 때문이다. 판정 자체는
주간 보고의 '내 차례'와 누락 방지 백스톱 재료로만 남는다(거기서는 과잉 포함이
미덕이다). 시간 기반 사실인 정체 2종만 데일리 '참고'로 강등해 유지한다.
"이 메일이 뭘 요구하나"는 이제 온디맨드 [분석]이 답한다.

### 6.3 분석 — 근거 달린 질의응답 (`ask.py`)

검색은 "그 메일"을 찾아주고 끝나지만, 분석은 "그래서 결론이 뭐였지"에 답한다.
계획을 한 번에 확정하지 않고 **본 뒤에 다음을 정하는 라운드 루프**를 돈다.

```
라운드:  훑기(제목·발신·날짜·스니펫)
           → 판단(더 검색 / 이것들 정독 / 충분)
           → 정독(인용 제거 본문) → 반복
반전 검색: 호스트가 강제 — 이미 본 스레드 전개 + 변경·취소·최종 신호
답변 작성
의미 검증: 별도 AI 판정 — 주장이 인용에서 실제로 도출되는가
```

**모델이 도구를 자유롭게 호출하는 루프가 아니다.** 호스트가 실행과 상한을 강제한다
(`MAX_ROUNDS=6`, `MAX_BODIES=48`, `MAX_CALLS=12`). 답변·의미 검증·필요 시
검증 근거만 사용한 재작성까지 이 상한 안에서 끝낸다.

세 가지 답변 상태 — **확인됨 / 상충함 / 근거 부족**. 검증은 **강등만** 하고
승격하지 않는다. 인용 대조를 통과한 근거가 0이면 자동으로 근거 부족이다.

- **반전 검색**은 관련도 하한(tier ≤ 3)을 걸고, 안 본 스레드에서 새로 정독하는
  통수를 제한한다. 앵커에 단어를 덧붙이면 AND 매치가 되레 깨져 검색이 OR 폴백으로
  떨어지는데, 질문이 구체적일수록 무관한 메일이 쏟아지는 뒤집힌 특성이라 막아 둔다.
- 모델이 정독한 스레드는 최초·최신·결정·기한·철회·완료 메시지를 시간순으로
  펼친다. 최초 검색 후보에 이미 있던 최종 메일도 새 검색 결과가 아니라는 이유로
  건너뛰지 않는다.
- **의미 검증기 고장은 거부와 다르게** 다룬다. 호출 실패·응답 파손이면 인용 대조를
  통과한 근거를 남기고 `semantic_checked=False`로 알린다. 답변 본문은 구조화 근거로
  다시 쓴다(미검증 자유 서술을 내보내지 않는다).
**입력 예산 — 한 콜의 총량으로 묶는다** (2026-08-03). 손잡이는
`[ai] ask_max_input_tokens` **하나**이고 값은 곧 **백엔드 컨텍스트 창**이다
(기본 120,000 — Claude 기준. 0 = 제한 없음).

통당 상한으로 잡지 않는 이유: **총량을 못 묶는다.** 같은 3,000자 설정에서 3통을
읽으면 10K, 24통이면 75K로 그냥 늘어난다(실측). 사용자가 아는 값은 창 크기지
통당 자수가 아니고, 통당 자수를 정하려면 "몇 통 읽을지"를 미리 알아야 하는데
그건 조사가 끝나야 안다.

```
① 설정: ask_max_input_tokens (= 내 백엔드 창)
② 변환: 자수 예산 = 토큰 × chars_per_token   ← 추정은 여기 한 번뿐
③ 조립: 통당 예산 사다리(무제한→8000→…→300)로 프롬프트를 만들고
④ 실측: len(프롬프트) 이 예산에 들면 채택, 아니면 다음 사다리로  ← 정확한 측정
```

토큰은 셀 수 없다(stdlib only · 백엔드는 CLI). 그래서 추정은 ②에서만 쓰고
그 뒤는 조립 결과의 **정확한 문자 수**로 맞춘다 — 비율이 30% 틀려도 창의
70%나 130%를 쓸 뿐 넘기지 않는다. `chars_per_token` 기본 1.0은 보수적이다
(한국어는 대략 1자당 0.7–1.5토큰).

**라운드는 총예산의 25%**만 쓴다. 정독 블록은 이후 STEP 라운드마다 + 답변 콜에
다시 실려 본문 한 글자가 총 송신 **3.2자로 증폭**되는데, 라운드는 "더 읽을까/
이제 답할까"만 정하면 되기 때문이다. 전문이 필요한 것은 답변 콜 하나뿐이다.

실측(기본 120,000토큰, 통당 5,000자 원문):

| 정독 | 답변 프롬프트 | 예산 대비 |
|---|---|---|
| 3통 | 16,036자 | 13% (사실상 전문) |
| 12통 | 61,582자 | 51% |
| 24통 | 97,928자 | 82% |

통수가 늘면 통당 몫이 자동으로 준다. 창을 20,000으로 낮추면 3·12·24통 모두
16K 안팎(80%)으로 수렴한다.

- **절단은 앞뒤를 나눠 담는다**(`clean.smart_truncate`) — 업무 메일은 앞에
  인사·배경, **뒤에 결론과 요청**이 온다. 앞에서만 자르면 정작 필요한 쪽이
  날아간다: 통당 2,200자 16통 실측에서 **결론 생존 0통**이었고, 같은 예산으로
  앞뒤를 나누자 **16/16**이 남았다(비용 0). 중략은 `…(중략 — N자)…`로 **표시**한다 —
  종전 산문 절단은 표시가 없어 모델이 조각을 전문으로 믿었다. **표는 행 경계를
  지켜 자른다** — 맹목 슬라이스는 '온전해 보이는 반쪽 표'를 만든다. 이 함수는
  분석·수확·주간·AI 검색·인물 요약·**일간 머리글**(2026-08-15 합류) 여섯 경로가
  **공유**하므로 한 곳을 고치면 전부에 적용된다.
- **부분 열람을 밝힌다** — "이 스레드 20통 중 12통 열람". 조각을 보고 있다는
  사실을 알아야 모델이 "더 읽자"를 고를 수 있다. **롤링 요약을 주입하는 안은
  철회했다**: 대개 존재하지 않고(자동 회고는 `ai=False`), 더 약한 백엔드가 쓴
  산출이며, 인용 검증을 통과할 수 없어 근거가 못 된다. 지어낸 요약보다 "덜 봤다"는
  사실이 정직하고 비용이 0이다.
- **검증기는 전문을 본다** — `_quote_ok`는 `read[mid]["body"]`(자르지 않은 원문)와
  대조한다. 절단은 프롬프트 조립에서만 일어난다. 그래서 절단이 심하면 모델이
  **답을 알면서 인용하지 못해** '근거 부족'으로 강등되던 비대칭이 있었다.
**답변의 형태 — 메일을 다시 열지 않게** (2026-08-03). 사용자 지적: "답변이 너무
담백해서 내용 확인을 위해 메일을 다시 읽게 된다." 원인이 둘이었다 — 인용이
조각이라 조건·전제가 안 보였고, `answer` 가 2–4문장으로 묶여 수치·조건이 빠졌다.

- **인용의 앞뒤를 코드가 붙인다**(`clean.quote_context`). 인용은 이미 원문의
  연속 부분 문자열임이 검증된 값이라 **위치를 찾아 앞뒤를 그대로 복사**하면
  된다 — 모델이 문장을 더 만들지 않으므로 **환각 위험이 0**이다. 대조가 공백을
  무시하므로 정규화 인덱스 ↔ 원문 인덱스 대응표로 위치를 되찾고, 문장 경계로
  다듬는다. 방향이 중요하다 — 앞은 pad 안의 **가장 이른** 경계부터, 뒤는 **가장
  늦은** 경계까지다(가까운 경계로 자르면 9자만 늘어 쓸모가 없다). 폭은
  `[ai] quote_context_chars`(기본 120): 실측 100 이면 폴백 조건까지 들어오고
  250 은 과하다. 문맥은 **표시용**이라 줄바꿈을 접는다.
- **결론이 구조로 올라온다** — `headline`(한 줄 결론)과 `claims[].role`
  (결론·근거·배경). 종전에는 결론이 문단 첫 문장에 묻혀 읽어야 알았다.
  headline 은 **검증 통과 claim 이 0이면 코드가 비운다** — 근거 없는 결론을
  내지 않는다.
- **`open[]`** — 메일에 명시된 열린 것. `claims` 와 **같은 인용 검증**을 탄다.
- **`answer` 에서 메일 번호를 뺀다** — "(2026-07-26, #271)" 이 문장 안에도 있고
  claims 에도 있어 같은 것을 두 번 읽었다. 길이는 3–6문장이고, guide 가 있으면
  guide 의 형식을 따른다(종전 "2–4문장" 규칙은 3–4개 절을 지시하는 브리핑·메일
  분석 guide 와 **모순**이었다).
- **`claim.text` 는 라벨이 아니라 문장** — 의미 검증이 실패하면 폴백
  (`_safe_answer`)이 claim.text 를 이어 붙이므로, 폴백 답변까지 함께 좋아진다.
- **`REPAIR` 도 같은 규칙을 든다**(2026-08-04). 의미 검증이 answer 를 떨어뜨리면
  `_repair_answer` 가 검증된 근거만으로 다시 쓰는데, 여기가 예전 "2–4문장" 규칙을
  들고 있어 재작성될 때마다 답이 종전 톤으로 되돌아갔다. 실기기 첫 조사(sonnet)
  에서 **바로** 이 경로를 탔으니 드문 분기가 아니다. 재작성이 쓸 수 있는 재료는
  `text`·`date`·`quote` 뿐이고 결과를 같은 검증기에 다시 태우므로, 조건·수치는
  **인용 안에 있는 것만** 쓰라고 적었다 — 더 요구하면 재검증에서 통째로 떨어진다.
- **"기준" 줄은 코드가 만든다** — 근거의 시간 범위·정독 통수·덜 본 스레드.
  모델에게 묻지 않는다(자기가 뭘 안 봤는지는 코드만 정확히 안다).
- 프롬프트는 **자료를 앞에, 과업을 뒤에** 둔다. 예산 모델로 근거가 100배
  길어졌으니 생성 지점에서 먼 지시는 힘을 잃는다.
- 새로 생긴 절단 마커를 위해 **"`…(중략)…` 을 가로질러 인용하지 마라"** 를
  명시한다 — 원문에 그런 연속 문자열이 없어 그 항목이 통째로 버려진다.

- **캐시 키**에 `MAX(ingest_seq)` 기준선이 들어가 새 메일이 오면 자연히
  무효화된다. 옛 답은 지워지지 않고 "이후 새 메일 N통"으로 낡음을 알린다.
  **`MAX(id)` 가 아닌 이유**: 번호가 날짜 기반이라(§4 '번호 체계') 백필된 옛 메일이
  들어와도 `MAX(id)` 는 안 움직인다 — 새 메일이 왔는데 옛 답이 유효한 채로
  남는다. '이후 새 메일 N통'도 두 번호의 차가 아니라 `COUNT(*)` 로 센다.
- 이어 묻기는 모델 세션이 아니라 **매번 다시 조립한다** — 이전 문답과 정독 목록을
  프롬프트에 실어 보낸다. 백엔드 교체 가능성과 재현성을 지키기 위해서다.

### 6.4 일간 회고 — 오늘 하나와 어제 대비 (`review.py`)

주간이 '기간의 지도'라면 일간은 **오늘 판단이 필요한 것**만 남긴다.

```
Executive Summary(최대 3건) → 내 약속 → 변화(어제 이후) → 오늘 확정·변경 → 오늘 흐름 → 참고(접힘) 
```

- **Executive Summary** — 후보 선정은 결정론이다(**오늘 활동한 스레드** 중
  `_worth_reporting` 통과분, 상태판 `score` 상위 **최대 3건** — `HEADLINE_TOP`).
  문장만 AI 가 쓰고, 주간과 **같은 문체 표본**을 쓴다. 고를 만한 것이 없으면
  호출하지 않는다.

  **1건에서 3건으로** (2026-08-22). 8/15 의 '한 건을 중심으로 한 문단' 계약은
  "3~5문장으로 전부 훑던" 요약이 경과 나열이 되는 **문체 문제를 건수 제한으로 푼
  과교정**이었다. 하루에 중요한 일이 둘 이상인 것이 정상인데 둘째부터는 그냥
  사라졌고, 1등 자리 하나를 관여도 점수가 독점하니 "내가 많이 답한 것"이 올라온다는
  사용자 관찰이 나왔다(데모 실측: reply 7회 스레드가 '방식 결정 필요'를 52:23 으로
  눌렀다). 나열을 막는 장치는 건수가 아니라 **문장 규칙**이라는 것이 주간
  보고(OVERVIEW — 그때 최대 5건·건당 한 문장)의 답이었고, 일간만 거기서 갈라져
  있었다. 뒤이어 주간도 같은 방향으로 맞췄다(§6.5 — 7건·건당 두세 문장).
  - **모양**: 후보마다 불릿 하나(굵은 제목 + `#번호`), **불릿 하나는 줄바꿈 없는 한
    덩어리**(길어도 다섯 문장), **높임말**, 한 문장에 사실 하나. 렌더러는 들여쓴
    연속 줄만 같은 항목으로 붙이므로 모델이 줄을 바꾸면 목록이 끊긴다 —
    `_normalize_exec` 가 출력의 딸린 줄을 그 불릿 줄에 이어 붙인다.
  - **순위 기준은 상태판 `score` 하나다.** 머리글 전용 보정층(핑퐁 상한·열린 상태
    가산)을 잠깐 뒀다가 걷어냈다(사용자 결정) — 기준이 둘이면 주간과 일간이 다른
    순서를 말하고, 어느 쪽이 맞는지 판정할 근거가 없다. 점수를 손볼 일이 있으면
    `weekly` 의 그 식을 고쳐 양쪽에 함께 적용한다.
  - **재료는 건수와 무관하게 건당 6통 × 2,000자**다. 여럿이라고 줄이면 결론이 먼저
    잘린다 — 콜 수는 2 로 그대로다.
  - **남은 것**: 관여도(`replies` 무상한 ×4)가 순위를 지배하는 구조는 그대로다.
    데모 사흘 관찰로는 닫히는 중인 스레드가 상위를 오래 차지했지만, 값을 정할
    근거(실메일 라벨)가 없어 손대지 않았다. 내용 중요도 축도 사실상 없다 —
    `has_decision` 은 이름과 달리 **"결정해 달라"** 를 잡는 요청 감지기고
    (`features.DECISION_RX`), "확정합니다" 같은 결과 통보는 못 잡는다(데모 283통 중
    10통). 감지기가 먼저지 가중치가 먼저가 아니다.

  **여기에 투자를 더 한다** (2026-08-15). 사람이 가장 먼저 읽는 절인데 회고 콜의
  1/13 이었다. 셋을 바꿨다.
  1. **재료 절단을 고쳤다.** 종전에는 메시지당 앞 400자 맹목 슬라이스여서, 업무
     메일의 결론(뒤)이 날아갔다 — 같은 실수를 이미 실측으로 확인하고
     (`clean.smart_truncate`, 결론 생존 0/16 → 16/16) 다섯 경로가 공유하게 만들어
     뒀는데 **이 절만 그 다섯에서 빠져 있었다.** 이제 앞뒤를 나눠 담고(중략 표시),
     예산도 콜 1회짜리 절에 맞게 올렸다(400자 → 1,000자 · 4통 → 6통). 평탄화는
     **절단 뒤에** 한다 — 순서가 바뀌면 표 행 경계 보호가 개행을 잃어 무력해진다.
  2. **후보 범위를 넓혔다.** 종전엔 '오늘 내가 보낸 스레드'로 좁혀, 상대가 던진
     결정 요청·기한 임박 건은 그날 내가 회신하지 않았다는 이유만으로 후보에조차
     못 들었다 — 정작 그런 날이 머리글이 가장 필요한 날이다. 관여도 필터는
     그대로다: 상태판(`now`)이 이미 내가 발신·언급·직접수신한 스레드만 담는다.
  3. **2패스로 만든다** — 초안 1콜 → 같은 재료로 고쳐 쓰기 1콜(`EXEC_REVISE`).
     고쳐쓰기에도 **재료를 다시 준다**(초안만 주면 없는 사실로 매끄럽게 만든다).
     되면 좋은 것이지 필수가 아니라, 2패스가 실패하거나 비면 **초안을 그대로
     쓴다** — 잃는 것은 '조금 더 나은 문장'이지 머리글 자체가 아니다.

  모델·effort 는 안 올렸다(`[ai] summary` 공유 유지) — 재료와 범위가 병목이었다.
- **AI 를 안 돌린 리포트는 이 절을 내지 않는다.** 기본 일간은 `ai=False` 로 자동
  생성되므로, 절을 내면 매일 첫 줄이 '없음'이 된다.
- 비었을 때의 문구는 상황을 가른다(`review.EXEC_EMPTY`) — 올릴 것이 없으면
  "특이사항 없음", 호출이 실패하면 "받지 못했습니다", 주간의 근거 검증에서
  떨어지면 그렇게 적는다. **실패를 '없음'이라 말하면 거짓이다.**
- **내 약속**(`promises.py`) — 내가 직접 쓴 확정 어미만. 보존 인용(mid-join)은
  떼고 본다: 안 떼면 남이 쓴 문장이 '내 약속'으로 올라간다.
- **변화** — 어제 상태판을 다시 계산해 달라진 것만(`review.state_shift`).
  상태판은 주간 엔진을 `report_extras=False` 로 빌려 쓴다(보고서 전용 계산 생략).
  각 줄에 **마지막 메시지의 발신자 + 첫 문장 발췌**를 붙인다 — "왜 이게 내
  차례가 됐지"를 스레드를 열지 않고 확인하려는 것이다(2026-08-03). **인용이
  아니라 발췌**라고 부른다 — AI 가 고른 근거가 아니라 코드가 뗀 문장이라,
  이 저장소는 둘을 같은 이름으로 부르지 않는다. `store` 를 안 넘기면 종전 그대로다.
- AI 회고 분석은 '참고'(접힘) **앞**에 온다. 뒤에 두면 그 접힘 안으로 들어간다.

#### AI 산출은 파일 밖에도 남긴다

데일리 md 는 재생성마다 **통째로 덮어써진다**(`notes.write_daily`). 웹은 새 메일이
들어오거나 서버가 다시 뜨면 결정론 회고를 배경에서 다시 만드는데
(`web._maybe_auto_review`, `ai=False`), 그때 사용자가 돈 주고 받은 AI 절이 파일에서
조용히 사라졌다 — 재현: AI 회고 → 서버 재시작 → 홈 1회 조회 → `## Executive
Summary` 증발. 통계의 **기억 커버리지**가 바로 그 절 유무로 '지식이 쌓인 날'을
세므로(`report._AI_DAILY_MARKS`) 지난 기록까지 함께 거짓이 됐다.

- `run_ai_layer` 가 산출을 `sync_state` kv 에 날짜별로 남기고
  (`daily_ai:<date>` — 머리글·상태·수확·흐름의 AI 한 줄), `deterministic()` 이
  다시 얹는다(`review.restore_ai_layer`). **되읽기지 재호출이 아니다** —
  AI opt-in 불변식은 그대로고 결정론 경로의 호출 수는 0 그대로다.
- 새 표를 만들지 않는다(`sync_state` 는 어느 DB 에나 이미 있다) → 재수집 불필요.
- 이 장치 이전에 만든 파일은 md 의 `## Executive Summary` 절에서 한 번 구제한다
  (`_exec_from_file`). `- 특이사항 없음` 같은 `EXEC_EMPTY` 문구는 본문이 아니라
  **상태**로 되살린다 — 안 그러면 실패·미실행 구분이 무너진다.
- 같은 날 **두 번째 수확은 새 메일분만** 돌아온다(`last_harvest` 워터마크가 이미
  앞서 있다). 그것으로 덮으면 '오늘 확정·변경'이 통째로 사라져서, AI 회고를 한 번
  더 눌렀다는 이유로 오늘 확정된 것이 화면에서 없어졌다 → `_merge_harvest` 로
  합친다. 머리글도 **재실행이 실패했다고 이미 받아 둔 요약을 지우지 않는다.**

#### 스레드 진단은 회고가 아니라 스레드 화면에서 만든다 (2026-08-15–16)

회고 콜의 대부분이 스레드 요약 갱신이었는데(실측 13콜 중 11) **회고가 그 산출을
거의 쓰지 않았다** — 머리글은 원문을 직접 읽고(§6.4), 지식 md 는 저장 시 전문으로
다시 쓰며(§6.6b), 주간·AI 검색은 원칙상 요약을 재료로 안 쓴다(§6.5·§6.3). 남은
소비처는 사람이 읽는 스레드 화면과, 수확·디제스트의 문맥 보조뿐이었다.

- **만들어지는 곳은 스레드 화면의 버튼 하나**(`review.diagnose_thread` →
  `web._diag_job`). 인물 요약이 2026-07-29 에 간 길과 같다. 회고 콜은 활동량과
  무관하게 **4콜 고정**이 됐다.
- **버튼은 문턱을 면제한다**(`force=True`) — 길이·노이즈·공지·숨김 필터를 전부
  건너뛴다. 누른 것이 곧 명시 의도이고, 안 그러면 눌러도 아무 일이 없는 조용한
  실패가 된다(숨김 스레드에서 [분석]을 직접 누른 경우와 같은 판례).
- 증분 가드(`summary_msg_count`)와 저장은 그대로다 — 두 번째 누름은 새 메일분만
  반영한다. **날짜 창 스윕**(`_summary_window`·`refresh_summaries`·`last_summary`)
  은 삭제했다: 단일 스레드 갱신만 남으면 쓸 데가 없고, 남기면 다시 걸리게 된다.
- 잃는 것은 "즉시 보이던 것이 눌러야 보이게 되는 것" 하나다. 원재료(`new_content`)
  는 프룬 대상이 아니므로(§6.7 프룬은 표시용 HTML 만) 언제든 다시 만들 수 있다.

**요약이 아니라 진단이다** (2026-08-16). 사용자 확정: *"무엇이 정해졌냐보다 지금
문제가 뭐고 어떤 방향이 있나가 필요하다. 안건 종료 여부는 분석에 필요하지만 아주
중요한 내용은 아니다."* 그래서 사실 정리(요지)를 흡수하고 무게중심을 판단으로
옮겼다 — 확정 사실은 `배경` 슬롯으로 내려갔다. 재료는 **전문을 다시 읽는다**
(`_diagnosis_material` — 최근 40통, 총예산 60,000자를 통당 800–3,000자로 나눠
`smart_truncate`, `THREAD_DIAGNOSE`).

| 슬롯 | 답하는 것 | 코드가 대조하는 것 |
|---|---|---|
| `정리` (1) | 사안·현재 위치·관건을 두세 문장으로 | — (판단) |
| `문제` (≤3) | 지금 걸려 있는 것 | **근거가 원문에 있는가** |
| `원인` (≤2) | 왜 그렇게 됐는지 (구조적이면 그렇게) | — (판단) |
| `방향` (2–3) | 택할 수 있는 길 + 얻는 것/잃는 것/되돌리기 | — (판단) |
| `먼저 할 일` (1) | 내가 먼저 할 것 하나 | — (판단) |
| `배경` (≤2) | 이미 정해져 다투지 않는 것 | **근거가 원문에 있는가** |
| `모르는 것` (≤2) | 이 판단을 뒤집을 수 있는 빈칸 | — (선언) |

- **검증은 값이 싼 축에만 건다** — `문제`·`배경` 줄의 근거만 원문과 대조한다
  (`distill._QuoteChecker`, 수확과 같은 관문). 통과 못 한 줄은 버린다.
- **판단 슬롯에는 인용을 요구하지 않는다.** 여러 통을 엮은 문장은 원문에 그대로
  있을 수 없어, 강제하면 종합 자체가 깎인다. 그래서 서술과 근거를 줄 안에서
  분리했다(`문제: <종합 문장> | 근거: "<원문 조각>"`).
- **검증할 수 없는 산출은 '기각 가능한 모양'으로 낸다.** 코드가 못 거르면 거르는
  것은 사람이다 — 그러려면 3초 안에 판정할 수 있어야 한다. 방향마다 얻는 것·잃는
  것·되돌릴 수 있나를 달고, 판단을 뒤집을 조건은 `모르는 것`으로 선언한다.
  "좋은 것 같습니다" 류는 채택도 기각도 못 해서 최악이다.
- **문제가 없으면 문제·원인·방향을 비운다.** 잘 굴러가는 사안에 억지 문제를 만들면
  분석 전체를 못 믿게 된다 — 이 실패는 조용해서 더 비싸다.
- **정리는 화면에서 슬롯 행이 아니라 한 문단**으로 그린다(`.dxlead`) — 라벨 열에
  밀어 넣으면 두세 문장이 좁은 칸에서 접혀 읽기가 나빠진다.
- 저장 형식 = 프롬프트 형식 = 표시 형식(`parse_diagnosis`/`fmt_diagnosis`) — 한 곳
  에서 정의한다. `rolling_summary` 컬럼을 그대로 쓰므로 **스키마 변경이 없다.**
- **관련 스레드를 함께 싣는다**(`related_threads` — 제목 특징어 검색 + 상대방
  참여 스레드, 최대 4개). 시야를 스레드 하나 밖으로 넓히는 자리다: "이건 세 번째
  같은 문제"·"저쪽 스레드 날짜와 어긋난다"는 한 스레드 안에서 나올 수 없다.
  실측에서 관련 스레드가 붙자 *"PDK 1.3 표준셀 타이밍 모델 변경이 이번 STA 에
  반영된 기준인지 — 미반영이면 버퍼 물량 산정이 무효"* 라는 지적이 나왔다.
  **원문 발췌만 싣는다**(관련 스레드의 진단은 파생물이라 넣지 않는다), 근거 인용은
  대상 스레드에서만 딴다(관련 스레드 문장은 검증에서 자동으로 떨어진다).
- **모델은 `[ai] diagnose`(기본 opus)로 따로 라우팅한다.** 사람이 누를 때만 도는
  1콜이고, 실측에서 opus 가 sonnet 보다 **싸고 빨랐다**(진단 1건: opus $0.23/70초
  vs sonnet $0.32/190초 — sonnet 이 사고를 오래 해 출력 토큰이 4배). 품질도
  opus 가 나았다: 폴백 착수 시점 누락·산정 범위 누락을 sonnet 은 못 짚었다.
  **그래서 이 백엔드는 따로 확인해 줘야 한다** — 쓰는 CLI 가 opus 를 못 부르면
  이 버튼만 실패하는데, 그 사실이 클릭 뒤에야 드러났다(2026-08-19 신규 설치
  점검). 이제 `doctor` 가 역할 다섯을 다 이름으로 보여 주고, `mailkb diagnose`
  가 **역할이 쓰는 백엔드마다** 실제 호출을 1회씩 넣는다.
- **진단은 다른 프롬프트의 재료가 되지 않는다.** 수확·디제스트·인물 요약은 진단을
  아예 받지 않는다(2026-08-16 에 마지막 고리를 끊었다 — 중간 단계로 '근거 꼬리만
  떼서 넣는' `diagnosis_context` 를 뒀다가, 서술도 같은 파생물이라 함께 삭제했다).
  이유는 토큰이 아니라 **근거 오염**이다 — 파생물을 그 스레드의 산출을 만드는
  프롬프트에 넣으면 요약의 요약이 된다(§6.5 주간이 이미 금지한 것과 같은 계열).
  넣었을 때 실제로 나타나는 증상 셋:
  1. **수확이 진단의 근거를 자기 근거로 옮겨 적으면 검증을 통과한다** — 그 문장은
     실제로 그 스레드 본문에 있기 때문이다. 지난주 결정이 '오늘 확정·변경'에 다시
     오르고 같은 암묵지 후보가 반복된다. 인용 검증은 "원문에 있나"만 보지 "오늘
     온 메일인가"는 안 보므로 **코드가 못 막는 종류의 오염**이다.
  2. 디제스트는 스레드당 200자만 받는다 — 파생물이 그 자리를 채우면 '오늘 흐름'
     한 줄이 어제 문장의 복창이 된다.
  3. 인물 요약은 그 사람이 **직접 쓴** 문장만 근거로 인정하므로, 베낀 인용이 남의
     문장이면 그 줄이 조용히 탈락한다(오류 없이 브리핑만 얇아진다).
- **디제스트는 항상 그날 원문을 쓴다**(`_today_lines`, 2026-08-16). 종전 폴백
  `lead`(마지막 메일 첫 문장)는 "검토 완료했습니다." 같은 인사말을 잡았다 —
  요약이 회고에서 빠진 뒤 대부분이 이 폴백으로 떨어져 **싸다는 이유로 둔 자리가 곧
  품질 손실**이 됐다.
- 진단은 검색 색인 대상이 아니다(FTS 는 `subject`·`new_content` 만) — 형식이
  바뀌어도 검색 결과는 변하지 않는다.
- **옛 산문 요약은 그대로 보인다** — `parse_diagnosis` 가 한 줄도 못 잡으면 종전
  `[누적 요약]` 경로로 출력한다. 갱신을 누르는 순간 새 형식이 된다.
- 기존 **쟁점 분석**과 겹치지 않는다: 이쪽은 *지금 뭐가 문제고 어디로 가나*
  (전문 1콜, 스레드에 하나, 갱신됨), 쟁점 분석은 *쟁점별로 누가 무슨 입장인가*
  (조사 라운드 + 정독, 분석 이력에 누적, 이어 묻기). 화면 이름은 2026-08-18 에
  **현안 브리핑**이 됐다(아래) — 코드의 `diagnose*` 는 그대로다.

#### 판정 — 회사 PC 3차 실측 (2026-08-18)

표본을 최근 활동순으로 바꾸고 재료 예산을 푼 뒤 같은 절차를 다시 돌린 결과다.

| | 1차 | 3차 |
|---|---|---|
| 문제 | 21개 | 17개 |
| 기각 | 12개(57%) — **전부 "지금은 해소됨"** | **1개(6%)** |
| 근거 검증 탈락 | 0 | 0 |
| 남는 유효 문제 | 9개 | **16개** |

**진단은 쓸 만하다**가 판정이다(과탐 기준 20% 이하). 1차의 57%는 진단의 결함이
아니라 **표본이 죽은 스레드였던 것**과 **통당 800자 절단**이 겹친 결과였다.

**토큰 우위는 예산을 풀면서 상당 부분 반납했다** — 같은 14통 스레드에서 실제 콜
입력이 minerva 45,906 vs raw 54,184 토큰으로 **15% 적을 뿐이다**(재료만 비교하면
2.4배). 예산을 3,000자로 키운 대가이고, 관련 스레드까지 함께 싣기 때문이기도
하다(우리 쪽이 **더 넓게** 본다 — 동등 비교가 아니다).

그래서 이 도구의 우위를 토큰으로 말하지 않는다. 남는 것은 **결정론 계층·인용
검증·색인·이력**이고, 토큰 절감은 그 부산물이다.

#### 재료 예산과 생략 신고 — 회사 PC 2차 실측 (2026-08-18)

- **통당 800자 고정을 총예산 분배로 바꿨다**(`_DIAG_TOTAL = 60,000자`, 통당
  800–3,000자). 회사 실측에서 *"인용 포함 원문이 우리 재료가 놓친 구체 사실
  (인명·수량)을 하나 더 잡았다"* 가 나왔는데, 인용 제거보다 **이 절단**이 유력한
  범인이었다 — 업무 메일은 통당 1–2천 자가 흔해서 800자면 절반 넘게 버린다.
  진단은 스레드 하나에 1콜이라 예산을 키워도 감당된다(19통 → 통당 3,000자,
  40통 → 1,500자).
- **잘린 사실을 진단이 신고한다.** 재료 앞의 "앞선 N통 생략"이나 본문의
  `…(중략 — N자)…` 를 보면 `모르는 것`에 적으라는 규칙을 넣었다(§6.3 분석의
  "부분 열람을 밝힌다"와 같은 태도 — 조각을 전문으로 믿지 않게). 45통 합성
  스레드로 확인: 앞쪽에만 심은 사실이 잘려 나가자 지어내는 대신 *"앞선 5통
  (생략분)에 일정·범위의 전제가 되는 결정이 있는지 확인 필요"* 로 신고했다.
- **인용 제거의 절감은 코퍼스가 정한다 — 실환경 평균 2.4배**(2026-08-18 회사 PC
  `bench_diagnose --sizes`). 데모 합성 코퍼스의 7.7배(긴 스레드 33배)는 회신마다
  전체를 인용하는 **최악의 경우**로 만든 값이라 과대평가다. 개별 스레드로는
  9%밖에 안 줄어드는 것도 있다. **절감은 자랑거리가 아니라 관측값**이다.
- **확인된 것: 잃은 사실의 범인은 인용 제거가 아니라 우리 절단이었다.**
  통당 예산을 풀자 "원문만 잡던 구체 사실(인명·수량)"이 돌아왔다(회사 PC 재측정).
  그래서 같은 병이 있을 자리를 함께 손봤다 — **머리글도 통당 1,000 → 2,000자**
  (1콜에 6통뿐이라 총량이 작다). 남은 후보는 수확(`_CAP_BODY = 1000`)과 인물
  요약 발췌(`_CAP_EXCERPT = 600`)인데, 수확은 한 콜에 40스레드를 담아 총량이
  커서 **실메일 측정 뒤에** 손댄다(창 확대는 이미 역효과가 나온 전례가 있다).

#### 진단은 스냅샷이다 — 회사 PC 첫 실측 (2026-08-18)

실메일 8스레드 진단: **문제 21개 · 사용자 기각 12개(57%) · 근거 검증 탈락 0**.
숫자만 보면 과탐 같지만 **기각 사유가 전부 하나였다** — *"그때는 맞는 지적인데
회의·결정·프로젝트 종료로 지금은 해소됐다"*. 지어낸 것은 없었다. 즉 정확도
문제가 아니라 **신선도 문제**다. 그래서 셋을 고쳤다.

- **표본을 최근 활동 우선으로**(`cli._pick_threads`). 종전 정렬은 통수·본문량이라
  '크지만 이미 끝난' 스레드를 골랐다 — 진단이 가장 불리한 표본이었다.
- **재료에 경과일을 싣는다**(마지막 메일 이후 7일 이상이면 한 줄). 프롬프트에도
  규칙을 더했다: 그 기간에 해소됐을 법하면 `문제`가 아니라 `모르는 것`으로.
- **화면이 낡음을 먼저 말한다** — 카드 머리의 `마지막 메일 N일 전`(결정론 값,
  7일 이상일 때만). 모델 협조에 기대지 않고 사용자가 3초 안에 판정하게 하는 쪽이
  더 확실하다. 늘 붙이지는 않는다 — 상시 경고는 배경음이 된다.
- **재는 방법도 고쳤다**: 기각을 **(A) 지금은 해소됨 / (B) 애초에 문제 아님**으로
  갈라 센다. 둘을 합쳐 세면 이번처럼
  "57% 과탐"이라는 잘못된 결론이 나온다. 프롬프트를 조여야 하는 신호는 B 뿐이다.

같은 실측에서 **벤치 도구의 전제가 틀린 것도 드러났다** — 저장 HTML 은 스레드
첫 메일만 인용을 보존하므로(`store: preserve_quotes=t_created`) 실환경 DB 로는
'인용 포함 원문'을 복원할 수 없다. 억지로 돌리면 두 재료가 비슷하다는 거짓 결론이
나온다. 이제 복원 실패를 감지해 건너뛰고, 크기 비교는 **AI 없이** 수집 때 저장한
`messages.raw_chars` 로 한다(`bench_diagnose --sizes`). 데모 기준 전체 7.7배,
긴 스레드는 25–39배.

#### 역할 → 백엔드 해석은 config 한 곳에서만 (2026-08-19)

새로 설치한 PC(claude CLI 하나)에서 `doctor` 가 이렇게 말했다:

```
● 통과  sonnet (summary·search) claude → …
▲ 주의  internal (ask·weekly) opencode — PATH 에 없습니다
```

**둘 다 틀렸다.** `ask` 는 `search` 를, `weekly` 는 `summary` 를 상속하므로 실제로는
넷 다 sonnet 을 부른다. doctor 가 미설정 역할을 `[ai] default` 로 채우는 자기 규칙을
갖고 있었던 탓이다(`cfg.opt("ai", role) or cfg.ai_default`). 첫 사용자가 "분석은 못
쓰는구나"로 읽는 자리다 — 웹의 첫 화면이 분석이다. 반대로 **현안 브리핑이 쓰는
`diagnose`(기본 opus)는 어느 점검에도 없었다.**

- **해석은 `Config.backend_for(role)` 하나.** 상속 규칙(ask→search, weekly→summary)이
  엔진과 doctor 두 곳에 있으면 반드시 갈라진다. `weekly` 와 웹 설정 화면도 이 함수를
  쓴다. 규칙을 다시 인라인하지 못하게 테스트가 소스를 본다.
- **doctor 는 역할 다섯을 사람 말로 보여 준다** — `sonnet (요약·회고·AI 검색·분석·주간)`
  · `opus (현안 브리핑)`. 백엔드 이름만 찍으면 무엇이 안 되는지 알 수 없다.
- **`mailkb diagnose` 는 역할이 쓰는 백엔드마다 시험 호출 1회.** 종전에는 `default`
  하나만 불러서, opus 를 못 쓰는 CLI 를 끝까지 못 잡았다. `--backend` 를 주면 하나만
  부른다(평가 루프에서 비용이 늘지 않게).
- **`[ai] default` 기본값을 `internal`(opencode) → `sonnet` 으로.** 이 값이 실제로
  쓰이는 곳은 역할 라우팅이 없는 호출뿐인데, 설치 기본이 안 깔린 CLI 를 가리키고
  있으면 경고가 계속 남는다. 쓰는 CLI 하나로 맞춘다.

같이 고친 이름: 웹 설정의 `진단 백엔드` → **현안 브리핑 백엔드**, 인물 토스트
`다른 인물 진단이 진행 중` → `다른 인물 브리핑이 진행 중`, 설정 템플릿 주석의
`스레드 진단(스레드 화면 [분석] 버튼)` → `현안 브리핑(… [현안 브리핑] 버튼)`.
**템플릿은 사용자 파일로 복사돼 나가므로** 이름 회귀 테스트가 그것도 본다.

#### 브리핑 접기 — 첫 문장만 남긴다 (2026-08-19)

슬롯을 다 채운 브리핑은 화면을 통째로 먹는다. **실측**(상한을 다 채워 렌더):
분석 블록 **1,988px = 뷰포트의 266%**, 첫 메일까지 **2,195px 스크롤**. 평소에는
문제가 없다(회사 실측 카드 244자, 데모 인물 브리핑 147자) — **비대칭이 설계의
전제다**: 평소를 건드리지 않고 나쁜 날만 막는다.

- **첫 문장(`정리`)은 늘 보이고 나머지 슬롯을 접는다**(`<details class='dxmore'>`,
  스레드·인물이 같은 렌더러라 동시에 적용). 요약줄은 **무엇이 몇 개** 숨었는지
  말한다(`자세히 — 문제 1 · 원인 1 · 방향 2 · 그 외 2줄`) — '자세히'만 있으면
  펼칠지 말지 판단할 근거가 없다.
- **접을 것이 2줄 이하면 접지 않는다.** 컨트롤이 내용보다 크면 손해다.
- **상태는 스위치 하나**만 기억한다(`localStorage: mailkb.brief.open`, 기본 접힘).
  스레드마다 기억하면 "왜 이것만 접혀 있지"가 되고 상태가 스레드 수만큼 는다 —
  사용자 결정은 '기억하되 하나로'였다.
- **방금 만든 것은 접지 않는다.** 폴링 완료 주입 직전에 1회 강제 펼침(기억값은
  그대로). 2026-08-01 에 "눌러서 얻은 AI 절이 접힌 채 묻힌" 판례가 있다.
- **인쇄는 항상 펼침**(`beforeprint` 에서 열고, 그때는 저장하지 않는다). 찾기는
  크로미움이 접힌 `details` 를 자동으로 펼치지만 다른 브라우저는 보장이 없다.

#### 인물 축의 같은 계약 — 인물 현안 브리핑 (2026-08-18)

스레드에서 통한 슬롯 계약을 **사람 축으로 한 번 더** 돌렸다(`PERSON_DIAGNOSE`).
사용자 요구는 *"이 사람과 지금 걸린 게 뭔가"* 였고, 기존 인물 화면에는 그 답이
없었다 — 프로필(이 사람이 맡은 일·일하는 방식)은 사람을 설명하지 사안을 짚지
않고, 심층 분석은 수 분이 걸린다.

- 재료는 **그 사람과 주고받은 최근 스레드 원문**이다(`_person_material` — 총예산
  분배, 통당 600–2,000자). 스레드 쪽과 같은 이유로 고정 절단을 쓰지 않는다.
- **프로필도 재료가 아니다** — AI 산출은 다른 프롬프트에 넣지 않는다(위 '근거
  오염'과 같은 규칙). 사람 축이라고 예외를 두면 그 자리부터 요약의 요약이 된다.
- 저장은 `sync_state` kv(`person_diag:<주소>`) — 인물에는 `rolling_summary` 같은
  칸이 없고, 이것 하나 때문에 스키마를 늘리지 않는다(불변식 5).
- 심층 분석(조사 엔진)과 나눠 쓴다: **브리핑은 1콜/수십 초**로 매번 눌러도 되는
  것이고, 심층 분석은 **수 분·최대 12콜**로 작정하고 파는 것이다.

#### 화면 이름과 배치 — 프로필 · 현안 브리핑 · 심층 분석 (2026-08-18)

인물 화면에 AI 버튼이 셋(요약·진단·대화 분석) 나란히 서자 **아래에 무엇이 무엇인지
설명하는 문단이 필요해졌다 — 그것이 배치가 틀렸다는 신호였다.** 사용자 제안대로
이름을 산출물로 바꾸고, 배치 원칙을 하나 세웠다: **기능은 자기 산출물 옆에 둔다.**

규칙은 한 줄이다 — **제목 아래에는 그 제목의 결과가 있다.** 그래서 셋이 같은 모양의
카드가 됐다(2026-08-18 2차, 사용자: *"UX 도 미니멀리즘. 보면 의미를 알 수 있고, 각
제목에 따른 AI 결과가 나왔으면"*). 버튼 줄도 설명 문단도 없다.

| 카드 | 무엇 | 만드는 자리 |
|---|---|---|
| **현안 브리핑** | 지금 걸린 것과 먼저 할 일(1콜) | 카드 머리 `다시 만들기` |
| **심층 분석** | 조사 라운드로 파는 큰 분석(수 분) | 카드 머리 `다시` · 전문은 링크 |
| **프로필** | 이 사람이 맡은 일·일하는 방식 | 카드 머리 `다시 만들기` |

- **아직 없는 카드도 자리를 지킨다** — 제목 + "무엇을 얻는지" 한 줄 + 만드는 버튼.
  화면이 스스로를 설명하므로 아래에 붙이던 안내 문단이 필요 없다.
- **심층 분석은 저장된 최신 결과를 직접 집어 온다**(`_person_analysis` — ask_cache 의
  키 `…@<basis>~<주소>` 로 조회, `_thread_analyses` 와 같은 관례). 종전에는 링크만
  있고 산출은 분석 대화록에만 있어서 **화면만 봐서는 이 기능이 무엇을 주는지 알 수
  없었다.** 카드에는 한 줄 결론까지만 싣고 전문은 링크로 보낸다.
- 낡음 문법은 쟁점 분석과 같다 — 날짜·경과일과 `이후 새 메일 N통`
  (`store.person_msg_count(since_seq=…)`, 도착 순서는 `ingest_seq`).

**AI 진입은 어디서나 버튼이다**(2026-08-18 2차, 사용자 지적) — 카드 머리 액션만
밑줄 링크였는데, 진입 모양이 다르면 같은 종류의 일로 안 보인다. 전부
`aibtn ghost compact`(쟁점 분석 진입과 같은 모양)로 맞췄다.

**그리고 무게는 버튼 두 종류로 가른다**(2026-08-18 3차, 사용자 제안). 규칙 한 줄:

> **채움(색 반전)은 화면을 채우는 큰 AI 작업에만.** 나머지 AI 진입은 빈 배경.
> 단 **행마다 반복되는 컨트롤은 제외**한다 — 그래서 채움은 **화면당 최대 하나**다.

'화면을 채우는'이 뜻하는 것 둘: **분석 페이지를 여는 진입**(쟁점 분석·인물 심층
분석·신규 분석)과 **그 화면 자체를 갈아 끼우는 큰 작업**(AI 검색·주간 보고).
1콜짜리(현안 브리핑·프로필)와 행 반복 컨트롤(메일 머리 [분석])은 빈 배경이다.

**비용은 아직 없을 때만 말한다**(2026-08-19). 인물의 빈 카드가 쓰던 관례
(`AI 1콜` · `수 분 · 최대 12콜`)를 스레드 첫 진입에도 붙였다 —
`쟁점별 입장까지 보기 · 수 분`. 한 번 만들고 나면 꼬리가 사라지므로 **자주 쓰는
사람 화면에는 글자가 늘지 않는다.** 툴팁은 마우스를 올려야 보이고 터치·키보드에선
안 보여 그 자리를 대신하지 못한다. 꼬리는 색이 아니라 **투명도**로 낮춘다
(`.aibtn .cost`) — 채움 버튼의 파란 배경에서 회색은 대비가 무너진다.

**같이 검토하고 기각한 둘**(사용자 확정): ① 스레드 브리핑에도 `AI 추정` 칩 —
머리줄의 `[현안 브리핑]` 이 이미 그 역할을 하고, 칩이 늘면 머리줄만 길어진다.
② 화면을 떠나는 `쟁점 분석 보기` 에 `→` — 지금 `→` 는 두 곳뿐이라 뜻이 살아
있는데, 늘리면 닳는다. **기각도 기록해 둔다** — 다음에 같은 제안이 올라올 때
같은 논의를 반복하지 않기 위해서다.

새 스타일을 만들지 않은 것이 이 규칙의 핵심이다. `채움`(`aibtn`)은 이미 `신규
분석`·`AI로 다시 찾기`·`보고 만들기` 셋에 쓰고 있었고, 그 셋이 전부 "화면을 채우는
큰 AI 작업"이었다 — 규칙은 새로 만든 것이 아니라 **있던 관례에 이름을 붙인 것**이다.

'반복 제외' 단서는 자의적 예외가 아니다. 메일 머리의 `분석`은 스레드당 14개까지
늘어나고, 전부 채우면 **본문보다 버튼이 먼저 읽힌다**(시안 실측). 행 단위로
반복되는 컨트롤을 강조하지 않는 것은 일반 원칙이고, 이 단서를 넣으면 기존 채움
세 곳과 정확히 같은 패턴(화면당 하나)이 된다.

무텍스트 신호로 검토했다가 접은 것들: 시계 글리프(`◷` — 흐리면 안 보이고, 진하면
`✦` 와 아이콘 둘이라 산만), 화살표(뜻이 '이동'이라 무게가 아님), 2차를 회색으로
낮추기(**비활성으로 오독**). 강도 표시가 필요한 자리는 결국 **선택지가 나란히
놓인 두 곳**(스레드 액션 줄·인물 카드 셋)뿐이라, 거기서 대비만 주면 충분하다.

같이 고친 라벨: 스레드의 `다시` → **`쟁점 분석 다시`**. 바로 왼쪽이 `브리핑 갱신`
이라 무엇을 다시 하는지 알 수 없었다(사용자 보고). 반면 인물 심층 분석 카드의
`다시`는 **그대로 둔다** — 카드 제목이 이미 대상을 말하므로 이름을 붙이면 같은
말이 두 번 나온다.

UI 에서 '진단'이라는 말은 없앴다 — 코드의 `diagnose*` 는 그대로라 **내부 이름과
화면 이름이 다르다**(주석에 적어 둔다). 스레드 화면도 같은 이름을 쓴다:
`[현안 브리핑]` 슬롯 + `브리핑 갱신`, 더 필요하면 쟁점 분석.

**버튼 이름을 부르는 곳은 `web.py` 만이 아니다**(2026-08-19 문서 점검). 첫 정리는
웹만 훑어서 `cli.py` 의 `--help`(`thread-diag`·`person-diag`)와 실패 메시지,
`review.diagnose_person` 의 docstring 이 **없는 버튼**을 계속 가리키고 있었다 —
가이드 문서는 이미 고쳐진 뒤였다. 이제 회귀 테스트가 세 파일을 함께 본다
(`test_ui_strings_use_the_current_names`: `web` · `cli` · `review`).

**길이도 함께 조였다** — 사용자 지적은 *"내용이 너무 길고 글의 가독성도 떨어진다"*
였다. 개수(원인 3→2 · 배경 3→2)와 줄 상한(400–600 → 180–320자)을 낮췄다(최대
6,000 → 3,000자). **상한은 자르기만 할 뿐 문장을 짧게 만들지 못하므로** 프롬프트에도
못 박았다 — "한 줄은 한 문장, 40–80자". 실측 카드 244자.

**이 정리 과정에서 마크업·CSS 버그 둘이 드러났다.**
- `<p>` 안의 `<form>`: HTML 파서는 `<p>` 를 **먼저 닫는다** — "아직 없습니다 —
  [만들기]" 한 줄이 두 덩어리로 갈라져 보였다. 카드 빈 자리는 `<div>` 로 바꿨고
  회귀 테스트가 인물 화면의 `<p>…<form>` 을 금지한다.
- 슬롯 CSS 가 `.analysis` 안에 갇혀 있었다 — 인물 카드는 같은 마크업을 `.dcard`
  안에 그리는데 선택자가 스레드 화면에만 걸려 있어 **라벨 열이 통째로 안 먹었다**
  (한 덩어리로 보였다. '가독성이 떨어진다'의 절반은 이것이었다).

**폴링 버그도 하나 드러났다.** 다 만들어져도 화면이 안 바뀌었다 — 인물
화면은 **좌측 패널**인데 스레드 쪽 훅을 복사하며 우측만 보고 있었다(진행 마커는
좌측에 있었다). 새 배경 잡을 붙일 때는 `_RUNNING_MARKERS` 등록만이 아니라
**어느 패널에서 도는지**(상태 라우트의 `pane`, `app.js` 판정표)를 함께 확인한다.

#### 몇 콜을 썼나 — 회고 화면의 계측 (2026-08-15)

AI 회고 한 번은 **4콜 고정**이다 — 수확 1 · 디제스트 1 · 하루 요약 2(2패스).
그날 활동 스레드가 몇이든 안 변한다. 2026-08-15 이전에는 스레드 누적 요약
갱신이 여기 있어서 `N + 3`콜이었고(실측 13콜 중 **요약이 11콜**), 그래서 어느
단계에 썼는지 보이도록 단계별 내역을 함께 센다. 세는 것은 **콜 수와 토큰뿐**
이다(비용은 아래).

- 재료는 이미 흐르고 있던 진행 이벤트다. `ai_run` 이 시도마다 `{"ev": "call"}` 을,
  스트리밍 경로가 result 봉투에서 `{"ev": "usage", …}` 를 흘리고
  (`review._usage_of` — AI 검색 계측과 **같은 합산식**: 입력 = 신규+캐시생성+캐시읽기),
  `run_ai_layer` 가 `on_event` 를 감싸 `det["ai_meter"]` 에 모은다.
- **콜 수는 백엔드와 무관하게 세진다**(call 은 블로킹 경로에도 흐른다). 토큰은
  claude 스트리밍 봉투에서만 오므로, 없으면 **그 항목만 빠진다** — 0 을 찍으면
  '공짜'로 읽힌다.
- **비용($)은 안 보여준다** (2026-08-15 사용자 확정). 봉투의 `total_cost_usd` 는
  토큰 × **API 정가** 환산이라(실측 역산으로 확인), 구독(Max/Pro)으로 쓰는 이
  도구의 실제 지불액이 아니다. 정확하지 않은 숫자를 돈 단위로 내면 옆에 있는
  콜 수·토큰까지 같이 못 믿게 된다. `meter` 에 담지도 않는다 — 화면에 안 쓰는
  값을 보관해 두면 나중에 '있으니 보여주자'가 된다. (AI 검색·분석 화면의 `$`
  표시는 이 결정 이전부터 있던 별개 자리다.)
- 재시도도 콜이다(시도 단위로 센다). 실패한 호출이 화면에서 공짜로 보이면 안 된다.
- 보이는 곳 셋: 진행 카드의 `· 호출 N회`(요약 단계가 왜 긴지 보인다) · 완료 flash ·
  **일간 회고 화면 하단**(`review.fmt_meter`). 앞의 둘은 휘발이라, 날짜별 비교는
  `save_ai_layer` 가 kv 에 함께 보관한 **마지막 AI 실행분**으로 한다. 계측만 남은
  실행(AI 가 전부 실패)도 보관한다 — 산출이 없다고 비용이 없던 것은 아니다.
- **CLI(`review --ai`)에는 안 붙는다.** `on_event` 를 안 넘기는 경로인데, 계측을
  붙이자고 넘기면 claude 백엔드가 스트리밍 경로로 바뀐다(`ai_run` 의 stream 게이트)
  — 계측 하나 때문에 CLI 인자 구성을 건드리는 것은 2026-07-28 사고 계열이다.
  터미널에는 계측이 없다(요약 품질 로그 `summary.jsonl` 은 그 요약 단계와
  함께 2026-08-15 에 사라졌다).

### 6.5 주간 보고 — 원문에서 다시 만드는 델타 (`weekly.py`)

기본 범위는 **최근 1주**다. 기간 내 내가 관여한 스레드 중 내 차례·막힘·결정·기한을
우선해 **재료 예산(`MATERIAL_BUDGET` 75,000자)** 안에 들어오는 만큼을 한 번에 읽는다.
건수 상한이 아니라 크기 예산인 이유는 §6.5a 에 있다.

**누적 요약과 데일리는 재료로 쓰지 않는다.** 사실·상태·중요도·후보 선별을 전부
원문에서 다시 하고, '기간 전 상태'도 그 시점 이전 원문으로 복원한다. 요약의 요약은
오차가 쌓이는데 주간은 그 오차가 가장 비싸게 드러나는 자리다.

```
콜1 기간 내 원문 전체 → 토픽 + 서술      콜2 서술 → 머리글·해석      콜3 남은 것 → 누락
```

보고서는 **상태판이 먼저**다(2026-08-01 재구성 — 진행 항목이 같은 무게로 나열되면
읽고 나서 무엇을 해야 할지가 남지 않았다).

```
Executive Summary(최대 7건) → 내 차례 → 막힘 → 기한 → 지난 차수 점검 → 토픽 서술 → 그 외
```

개수 제한은 절마다 다르다 — **일부러 그렇다**.

| 절 | 상한 | 왜 |
|---|---|---|
| Executive Summary | `EXEC_TOP` 7 | 일간 3건과 짝을 맞춘 값(2026-08-22 사용자 결정). **`MAX_TOPICS` 와 함께 움직인다** — 요약 항목은 토픽 서술에서 나오므로 토픽이 적으면 항목을 못 채운다. 상한이지 목표가 아니다(실측: 조용한 주는 5건에서 멈췄다) |
| 내 차례 · 막힘 · 지난 차수 점검 | `WEEKLY_TOP` 5, 나머지 '외 N건' | 중요한 것 먼저 |
| 기한 | `CALENDAR_TOP` 20 | 놓치면 곤란한 것이 섞여 있어 오래 상한이 없었다. 주 2,000통 실측에서 113건 → 인용까지 226줄이 되어 읽을 수 없는 벽이 됐다(2026-08-23). 날짜순이라 **임박한 것부터** 남고, 정보성은 '중요도 낮음' 표시로 낮춘다 |
| 그 외 | `REST_TOP` 20, 나머지 '외 N건' | 훑어보는 자리 |

**시간은 스레드 수가 아니라 기간에 붙는다.** 실측(sonnet, 3콜 재설계 뒤 2026-08-24):

| 조건 | 관측 | 범위 |
|---|---|---|
| 1주 · 36스레드 | 458 · 538 · 623초 | 7.6~10.4분 |
| 2주 · 50스레드 | 873 · 1,555초 | 14.6~25.9분 |
| 1주 · **777스레드**(주 2,000통) | 517초 | 8.6분 |

스레드가 20배여도 8.6분인 이유는 재료 예산이 프롬프트를 묶기 때문이고, 기간이
곱절이면 시간이 곱절인 이유는 **산출량**이 늘기 때문이다(1주 41KB → 2주 48KB 로
재료는 +17% 인데 토픽 불릿이 46 → 65~76). 시간은 출력량에 비례한다(실측 25자/초).

**같은 프롬프트가 2.2배까지 흔들린다** — 2주 본문 콜이 616초와 1,363초였고, 느린
쪽이 산출은 오히려 적었다. 그래서 안내는 값이 아니라 **범위**이고, 기간에 따라
달라진다(`web._weekly_eta(weeks)` — 주당 8~13분, 만드는 자리는 여전히 하나다).
안 말하면 멈춘 줄 알고 중지를 누른다. 배경 잡이라 화면은 막지 않는다.

**요약 항목의 문체는 일간 머리글과 같은 계약이다**(2026-08-22). 항목 하나는
줄바꿈 없는 한 덩어리(보통 두세 문장, 필요하면 다섯) · 높임말(합니다체) · 한 문장에
사실 하나. 종전 "한 문장(80자 내외)" 은 수치와 조건을 잘라 냈다 — 같은 주를 두 설정으로
돌린 실측에서 CVE 번호·CVSS·미대상 물량·승인 금액이 신규 판에만 남았다. 높임말을
규칙으로 못 박은 이유도 실측이다: 예시만 있던 종전 프롬프트는 차수마다 평서체와
합니다체를 오갔다. 항목 절단 상한도 200 → 600자로 올렸다(두세 문장이 잘리던 값).

가벼운 건(회식·사무용품)을 빼는 `review._worth_reporting`(일간과 공유)은
**상태판 버킷(내 차례·막힘)에만** 걸린다. 기한·지난 차수 점검·그 외는 안 걸린다 —
기한은 놓치면 곤란하고, 지난 차수 점검은 내가 한 말이 기준이기 때문이다.
그 판정의 '기한'은 환산된 날짜가 아니라 `has_deadline` 개수라, "금요일까지"가 든
가벼운 메일도 통과한다(알려진 느슨함).

- 최종 항목은 `thread_id`만이 아니라 **`message_id` + 연속 원문 인용**으로 고정한다.
- `mine=true`는 해당 메시지가 내 발신일 때만 통과한다.
- 인용 검증은 **코드가 한다**(`_keep`). 그 위에 얹었던 별도 AI 의미 검증 단계는
  없앴다(2026-08-23) — 실측 3회 중 2회가 240초 타임아웃으로 죽었고, 살아난 1회가 한
  일은 머리글을 통째로 지운 것이었다. 더 나쁜 것은 **타임아웃이 보고서를 더 그럴듯하게**
  만든다는 점이다: 검증이 건너뛰어져 걸러질 문장이 그대로 남는다.
- 누적 요약·데일리 요약은 사실·상태·중요도·후보 선별에 쓰지 않는다.
- 기간 이전 상태도 현재 누적 요약이 아니라 **기간 이전 원문 마지막 3통**으로 복원한다.
- 직전 주간보고는 표현 중복 회피용 참고일 뿐, 사실 근거나 누락 판단에 쓰지 않는다.
- AI 실패 시에도 결정론 목록을 담은 보고 파일은 남는다.

#### 6.5a 왜 7단계 17콜에서 3콜로 갔나 (2026-08-23)

종전 구조는 재료를 8스레드씩 잘라 카드를 뽑고(`CARD`), 토픽을 묶고(`GROUP`),
토픽마다 서술하고(`WRITE`), 총평·누락·의미검증·해석을 각각 불렀다. 17~20콜에
25~29분이 걸렸다. 버린 근거는 전부 실측이다.

**① 쪼갤 이유가 용량이 아니었다.** 한 주 재료는 7KB(주 80통)~70KB(주 2,000통,
전체 777스레드) 뿐이다. 그런데 17콜이 같은 재료를 **6.5배(43,678자)** 로 부풀려
보내고 있었다 — 단계마다 겹치는 문맥을 다시 실어서다.

**② 모델이 한 번에 전체의 1/5만 봤다.** 카드 배치가 8스레드라 앞 조각을 기억하지
못한 채 묶고 썼다. 같은 사안이 다른 토픽으로 갈라지거나, "B0" 같은 이름표로 서로
다른 6건이 한 덩어리가 됐다.

**③ 출력의 61%가 보고서에 실리지 않았다.** 시간은 입력이 아니라 **출력량**에
비례한다(실측 25자/초 · 최소 콜 왕복은 6초 이내). 카드 5콜이 22,500자를 뱉는데
그건 중간 산출물이라 보고서에 한 글자도 안 들어간다 — 카드에만 15분이 갔다.

**④ 그 카드가 통째로 폐기되고 있었다.** `CARD` 출력 규격은 `tid` 를 스레드 항목에만
실었는데 검증기 `_keep` 은 항목마다 `tid` 를 요구했다. 실제 응답 23건 → 통과 0건.
폴백(마지막 문장 하나)이 조용히 대신 들어갔고, 서술 단계는 카드가 아니라 원문을
직접 읽으므로 보고서가 멀쩡해 보였다. 불변식 4(우아한 실패)대로 **조용히** 나빠진
자리다. 지금은 토픽이 스레드를 하나만 지목하면 코드가 `tid` 를 채운다(`_with_tid`).

**결과.** 3콜 8~9분(3.5~4.3배), 인용 검증 통과율 92%대 → 100%, 토픽 불릿 동등
(62 대 64), 커버는 오히려 넓다(44 대 37).

**머리글을 본문과 다른 콜로 뺀 이유**는 문체다. 한 콜에서 쓰게 하면 모델이 서술을
다 쓴 뒤 남은 힘으로 머리글을 몰아 써서 계약을 어긴다 — 실측(데모): 한 콜이면
불릿당 1.4문장·절 잇기 0.3회, 분리하면 **2.7문장·0.1회**. 계약이 요구하는 "한
문장에 사실 하나"가 여기서 갈렸다. 해석 층도 서술을 재료로 쓰는 비인용 판단이라
같은 콜에 싣는다.

**후보를 건수가 아니라 재료 크기로 자르는 이유.** 종전 상한 64 는 카드 콜을 8개로
맞추려던 값(64÷8)이라 카드가 사라지자 근거가 없어졌다. 주 2,000통(777스레드)
실측에서 상한 64 는 커버 37, 상한 150(재료 76KB)은 44 였다. 반대로 전부(340KB)
넣으면 커버는 그대로인데 입력 토큰만 4.5배다 — **예산은 품질 규칙이 아니라 비용
상한이자 예측 가능성 장치**다. n=2~3 실측이라 그 이상은 주장하지 않는다.

**규모의 한계는 콜 수로 풀리지 않는다.** 주 2,000통이면 관여 스레드가 777건이고
그중 '내 차례·막힘·결정·기한'만 316건인데 보고서는 토픽 7개다. 6%를 고르는 일이라,
그 규모에서는 보고서 형태(프로젝트별 분할 등)를 다시 보는 것이 답이다.

**차수 잇기.** 주간 보고가 이전 차수와 이어지지 않아 지난번에 내가 한 약속을
아무도 다시 보지 않았다. 세 갈래로 잇는다(2026-08-01).

- **열람** — 웹 기억 › 주간 보고에 ◀▶ 인접 차수 이동. 주간 파일은 생성한 날만
  있어 간격이 불규칙하므로 날짜 산술이 아니라 **목록의 앞뒤 원소**를 가리킨다.
- **지난 차수 점검** — 새 표를 만들지 않는다. 약속은 내 발신 원문에서 나오므로
  `promises.review_period`가 지난 차수 창으로 **다시 계산**한다(일간의 '어제 대비'와
  같은 수법). 창은 **저장된 보고서 두 개 사이**다 — 직전 보고의 종료일이 끝,
  그 앞 보고의 다음 날이 시작(`weekly.report_rounds`). 앞 보고가 없으면 그때만
  같은 `weeks` 로 되짚는다. 이번 창에서 `weeks*7`일
  되짚으면 안 된다: 주간 파일은 생성한 날만 있어 간격이 불규칙해서, 07-25에 낸
  보고를 07-29에 열면 두 차수 전을 가리키고 그 사이 약속이 어느 창에도 안 잡힌다
  (2026-08-01 적대 검토 실측). 후속 판정은 "그 뒤 내가 그 스레드에 보냈나" +
  웹의 '처리함'뿐이고, **'안 지켰다'고 쓰지 않는다** — 다른 스레드나 메일 밖에서
  처리했을 수 있다.
- **머리글의 근거** — `board_facts`(코드가 센 카운트 + 지난 차수 점검 결과)가
  총평이 '지난 차수 대비'를 쓸 수 있는 **유일한** 사실 근거다. 이전 보고의
  **문장**은 여전히 머리글에 넣지 않는다.
- **문체 표본** — 내가 쓴 보고성 메일 최근 2건(제목이 보고성 + 본문 400자 이상,
  최근 400통 안)을 머리글 프롬프트에 **어조 참고 전용**으로 넣는다. 선정은
  결정론이다(고르는 일까지 AI 에게 맡기면 중요도 판단이 표본 쪽으로 샌다).
  사실 오염은 라벨 · 규칙문 · 총평 검증(`summary_supported`) 세 겹으로 막는다.
- **머리글 few-shot** (2026-08-03) — "경과 나열이 아니라 판단이 서는 문장"이라는
  지시는 원래 있었는데 **예시가 없어 잘 안 지켜졌다.** 좋은 예 3 + 나쁜 예 1을
  `OVERVIEW` 에 박았다(전부 가상값이고 "형태만 참고, 사실을 가져다 쓰지 마라"를
  함께 적는다). 프롬프트만 고치면 되는 가장 싼 개선이다.

**리포트 '처리함'.** 회의·구두처럼 메일 밖에서 처리한 항목은 다시 올라오면
안 된다(사용자 확정 2026-08-01: "한번 처리하면 다음 판단에는 잡히지 않아야 해").

- 리포트 마크다운의 해당 줄 끝에 `<!--done:종류:키-->` 표식을 넣는다. HTML 주석이라
  다른 뷰어·편집기에서는 보이지 않고, 웹(`_md_inline`)만 **처리함** 버튼으로 바꾼다.
  키를 본문에 심는 것은 **화면에 보이는 그 항목**을 정확히 가리키기 위해서다 —
  화면에서 다시 계산하면 그 사이 들어온 메일 때문에 목록이 달라진다.
  표식은 **줄 끝에 붙은 것 하나만** 신뢰한다. 이스케이프를 지난 형태로 잡으면
  메일 제목에 심은 표식이 가짜 버튼을 만든다(2026-08-01 적대 검토 실증).
- 종류는 `promise`(내 약속) · `stalled`(정체·막힘) · `deadline`(기한) ·
  `shift`(변화, 2026-08-11). 키가 일간·주간 공통이라 **한 번 접으면 양쪽에서
  빠진다** — `stalled` 는 스레드 번호로, `promise`·`deadline` 은 원문 문장으로
  만든다.
- 제외는 **결정론 단계**에서 한다(`review.deterministic` · `weekly._calendar` ·
  `weekly._bucket` · `promises.extract`). 렌더에서 빼면 다음 판단에 다시 올라온다.
- **예외: `shift` 는 그날 스코프다.** 변화 절은 어제 대비 차이라 내일이면 자연
  소멸하므로, 접기는 영구 억제가 아니라 "이 변화를 인지했다"는 그날의 화면
  정리다. 키에 날짜·구획(`Store.report_key("shift", tid, 날짜, 구획)`)이 들어가
  몇 주 뒤 같은 스레드의 **새** 변화는 다시 보이고, 결정론 단계 필터링 없이
  렌더(`_apply_done`)에서만 뺀다. '풀린 것'엔 버튼을 달지 않는다 — 처리할 일이
  아니라 좋은 소식이다.
- 이미 **저장된** 리포트에서도 그 줄을 빼고 절의 `(N건)` 을 다시 센다
  (`web._apply_done`). 파일은 다시 만들어지지 않으므로 화면에서 세야 한다.
  남은 항목이 0이면 절을 통째로 뺀다.
- 되돌리기는 리포트 하단 접기(`처리함으로 접은 항목`)에 남는다 — 접힌 채로 잊히면
  '사라진 것'과 구별되지 않는다. 저장은 `report_done` 표(`kind`+`key_hash` PK).
- **알려진 한계**: `CLEAN_VERSION` 이 올라 본문이 재절단되면 `promise`·`deadline`
  키가 달라져(그 문장이 절단 경계에 걸릴 때) 접은 항목이 되살아날 수 있다.

### 6.5b 내 노트 — 스레드에 직접 쓰는 기록

노트는 **스레드당 md 파일 하나**(`vault/notes/<제목>-<tid>.md`)다. 메일함과
스레드 목록은 둘 다 같은 스레드 화면을 열므로 진입점이 둘로 보였을 뿐, 노트는
처음부터 스레드 단위였다.

**파일이 원본, DB는 색인**이라는 계약은 웹 편집기가 생겨도 그대로다 — 웹은
외부 편집기와 같은 자격의 편집자 하나일 뿐이다. 그래서 쓰기 전에 열어 본
시점의 mtime을 대조하고(`base` 필드), 다르면 **덮어쓰지 않는다**. 사람이 쓴
글을 코드가 말없이 지우지 않는다는 것이 이 기능의 전제이고, 자동 저장을 두지
않은 이유도 같다(2026-08-11 사용자 확정).

- **화면에 보이는 것 = 파일의 본문**이다. frontmatter(meta)만 화면에서 감춘다
  — 외부 도구로 파일만 열었을 때 어느 스레드인지 알 길이 그것뿐이라 파일에는
  남긴다. 그래서 `note_body(파일)` == 편집 상자 == `notes.content` == 검색에
  걸리는 문장이 모두 같다.
- **비우고 저장 = 삭제**(파일 unlink + 색인 정리). 앱 안에서 노트를 정리할
  유일한 길이고, 편집기 하단 안내와 같은 규칙이라 별도 삭제 버튼을 두지 않는다.
- 템플릿은 사람 절만 갖는다(`## 요지` · `## 결정과 근거`). 종전의 AI 누적 요약
  사본·메일 타임라인은 스레드 화면이 더 잘 보여주는 중복이었고 위 등식을
  깨뜨려서 뺐다. 구 파일 호환 필터(`_MACHINE_HEADINGS`)는 유지한다.
- 저장 액션은 `/thread/<tid>/note-save` 하나뿐이다(`perform_action`의 스레드
  블록이 세 토막 경로만 받는다). `base`가 없으면 우리 폼이 아니므로 아무것도
  하지 않는다 — `parse_qs`가 빈 값을 키째로 버려서 '빈 저장'과 '엉뚱한 POST'를
  구별할 표식이 그것뿐이다.
- 저장 직후의 색인은 `reindex`가 아니라 **직접 쓴다**: 같은 파일을 연달아
  저장하면 파일시스템 시각 해상도 안에서 mtime이 같아 증분 색인이 옛 본문에
  머물 수 있다(2026-08-11 테스트가 실측).
- 미저장 이탈은 app.js가 한 번 묻는다(`noteLeaveOk`). `beforeunload`는 여기서도
  쓰지 않으므로(신뢰 불가) **창 닫기·브라우저 뒤로는 못 잡는다.**

### 6.6 일간 수확 — 인용 대조라는 관문 (결정 원장은 2026-08-14 폐지)

```
distill.harvest(AI 1콜) → 델타 · 인물 신호 · 프로젝트 신호 · 암묵지 후보
                              └ 전부 원문 인용 대조를 통과해야 남는다
```

`distill.harvest`가 추출한 항목은 **반드시 `quote`를 달아야** 하고, 그 문자열이
스레드의 `new_content`에 (공백 무시) 실제로 있는지 대조해 통과한 것만 남는다
(`_QuoteChecker`). AI는 제안만 하고, 남길지는 사람이 정한다(§6.6b).

**대조 대상은 신규 작성분뿐이다** — 보존 인용(mid-join)은 뺀다(2026-08-06).
그 블록은 남이 주고받은 글을 옮겨 실은 것이라, 그대로 대조하면 **A 가 쓴 문장을
B 의 발언으로** 기록에 올릴 수 있다(실측: 오태양 책임의 「sync_for_cpu 훅 호출은
UMD 책임입니다」가 강미래 선임 메일 안에 있어도 통과했다). 인물 요약 쪽
(`_PersonQuoteChecker`)은 처음부터 이렇게 하면서 "발화자 오귀속 차단"이라고
적어 두었는데 수확 쪽만 빠져 있었다 — 지금은 같은 `_QuoteChecker` 가 발신자
제한만 옵션으로 갖는다.

수확은 성공했을 때만 `last_harvest` 워터마크를 전진시킨다. 소급 상한은
`[ai] summary_max_days`(기본 **1일** — 오늘만, 요약과 공유)이고, 며칠 건너뛴 뒤
소급하려면 그 값을 늘린다.

"이미 보고한 것 반복 금지" 재료(`_recent_delta`)는 **어제 데일리 md 의 확정·변경
절**을 읽는다. 2026-08-06 까지 이 정규식이 모델 출력의 절 이름(`## 오늘 델타`)을
보고 있어서 렌더된 파일(`## 오늘 확정·변경 (N건)`)과 어긋났고, 그 재료가 한 번도
프롬프트에 실린 적이 없었다. 지금은 두 이름을 다 받는다.

**결정 원장의 폐지(2026-08-14, 사용자 확정).** 수확에는 원래 '결정 후보' 축이
있어 `decisions` 테이블(반영/유보/대체됨 + 결정자 대조 + 대체 관계)로 쌓였다.
사람이 승인하는 관문, 인용 대조, 대체됨 처리까지 갖췄지만 **활용도가 낮았다** —
DB 행이라 앱 밖에서 읽을 수 없고, 소비처(ask 주입·인물 카드)가 있어도 다시
찾게 되지 않았다. 같은 문제의식("승인된 것만 남긴다")을 파일이 산출물인 암묵지
축(§6.6b)이 잇는다. 테이블·라우트·주입 코드는 제거했고 기존 내용은 승계하지
않았다(사용자 확정 — 앞으로 캐는 것만).

#### 수확 재료 — 파생물을 끊고, 창은 넓히지 않는다 (2026-08-16)

- **진단(파생물)을 재료에서 뺐다.** 종전에는 스레드 요약/진단의 서술이
  `(요약: …)` 헤더로 들어갔다. 넣으면 지난주 판단이 오늘 수확으로 되돌아오고,
  그 문장은 원문에 있으므로 **인용 검증도 통과한다**. 주간 보고가 이미 지키는
  규칙(§6.5 "사실·상태·중요도·선별을 전부 원문에서 다시 한다")을 수확·디제스트·
  인물 요약에도 적용했다. '꼬리만 떼서 넣는다'는 중간 지대는 두지 않는다.
- **그 자리를 창 확대로 메우려다 접었다.** 데모 A/B(같은 날, 스레드당 상한만
  3통 → 6통): 인물 7→8 · 사안 5→7 로 신호는 늘었지만 **암묵지 후보가 3→1 로
  줄었다**. 재료가 늘자 모델이 더 일반적인 한 줄로 뭉쳤다 — 수확의 주 산출이
  암묵지이므로 넓히지 않는다. 1회 실행이라 강한 근거는 아니지만, **바꿀 이유가
  없다는 쪽**의 근거는 된다(상한 `distill._CAP_MSGS = 3` 유지).

### 6.6b 암묵지 — 조직 노하우를 md 로 (2026-08-14)

```
수확(AI, §6.6 과 같은 콜) → 인용 대조 → knowledge_candidates(pending)
  → 회고 화면·지식 탭 [지식으로 저장] → 보강(AI 1콜, 백그라운드 잡)
      → vault/knowledge/{날짜}-{슬러그}.md + 색인
          → 지식 탭 목록/본문 · 검색 '지식' 절 · ask 문맥
```

암묵지는 "무엇을 하기로 했나"가 아니라 **"어떻게/왜"** 다 — 검색으로 알 수
있는 일반 지식이 아니라 조직 고유의 판단 기준·제약·우회로다(선별은 수확
프롬프트의 규칙, 확정은 사람). 실패한 시도("버퍼 삽입은 면적 초과로 기각")도
지식이다.

**md 인 이유**: 폐지된 결정 원장(§6.6)은 DB 행이라 앱 밖에서 읽을 수도 조직과
공유할 수도 없었다.
md 는 파일 자체가 산출물이다 — 열어 읽고, 복사해 주고, 도구를 버려도 남는다.
참조의 메일 번호는 날짜 기반(§4 '번호 체계')이라 재수집에도 유효하다.

- **승인 전에는 파일이 없다.** 후보는 DB(pending)에만 있고, [지식으로 저장]을
  누르는 순간이 파일이 생기는 유일한 지점이다 — vault 가 초안으로 어지러워지지
  않고, 유보한 후보는 흔적 없이 사라진다.
- **보강은 저장 시점에.** 수확본은 롤링 요약만 본 2–4문장 초안이라 빈약하다.
  사람이 남기기로 판단한 것에만 참조 스레드 전문을 읽는 큰 호출을 쓴다.
  실패하면 수확본 그대로 저장(도구는 항상 산다).
- **저장은 백그라운드 잡**(2026-08-14). 보강 콜을 요청 스레드에서 돌리면 단일
  스레드 서버가 통째로 멈춘다(실측: 20초 보강 동안 홈 GET 이 19초 대기).
  다른 AI 잡과 같은 단일 슬롯 패턴 — 카드가 대기 카드로 바뀌고 폴링이 완료를
  갈아 끼운다(`data-kn-running`, JS-off 는 meta refresh).
- **참조 절은 코드가 만든다** — 앵커 메일(인용이 실제로 든 메일) 줄과, 그 본문에서
  정규식으로 추출한 외부 링크(wiki·jira 등, 상한 5). AI 에게 링크를 뽑게 하지
  않는다: URL 환각은 겉보기에 멀쩡해서 위험하고, 코드 추출은 본문에 있는 것만
  나오므로 그 자체가 검증이다.
- **파일이 원본**(notes 와 같은 계약) — `knowledge` 색인은 미러라 지워도
  `knowledge.reindex` 가 복구하고, 외부 편집기 수정을 mtime 으로 따라간다.
  frontmatter 의 모르는 키는 무시한다(나중에 tags: 를 더해도 안 깨진다).
- **기억 › 지식 탭**(2026-08-14) — 대기 후보를 **전 날짜** 모아 처리한다(그날
  회고에만 붙으면 회고를 안 열어본 날의 후보가 묻힌다). 저장된 지식은
  목록(mtime 순)·본문 뷰·검색으로 보고, 편집은 [외부 편집기로 열기](노트와
  같은 `_open_external` — 경로는 vault/knowledge 아래만 통과). 렌더 진입마다
  reindex(mtime 증분)라 밖에서 고친 것이 바로 따라온다. 웹 편집기·태그·삭제는
  두지 않는다(파일이 원본 · 사람 산출물은 코드가 안 지움).

### 6.6c 인물 프로필 — 발췌가 아니라 요약 (2026-08-18)

사용자 지적: *"프로필은 말 그대로 어떤 사람인지 인사이트 있는 짧은 요약이어야
하지 않나? 정보가 있든지 재미가 있든지 해야 할 텐데, 지금은 발췌가 되네."*
맞는 지적이고, **원인은 우리 계약에 있었다.**

- **모든 줄에 인용을 요구했다.** 검증을 통과하는 가장 쉬운 길이 발췌를 옮겨
  적는 것이라, 모델이 그 길로 간다. 진단에서 이미 배운 것과 같다(§6.4
  "판단 문장에는 인용을 요구하지 않는다") — 사람 축에만 안 적용돼 있었다.
- **재료가 그 사람이 쓴 발췌뿐이었다.** 관계는 한쪽 발화만 봐서는 안 보인다.

**슬롯 계약**(`distill._DOSSIER_*`, validator v3 — 옛 카드는 자동으로 '형식이
바뀌었다'로 숨는다):

| 슬롯 | 답하는 것 | 코드가 대조하는 것 |
|---|---|---|
| `한 줄` (1) | 이 사람이 나에게 어떤 상대인가 | — (판단) |
| `맡은 일` (≤2) | 담당 영역·책임 | **근거가 원문에 있는가** |
| `요즘 하는 일` (≤2) | 지금 굴리는 일 — 무슨 일을 하는 사람인지 | **근거가 원문에 있는가** |
| `일하는 방식` (≤2) | 여러 통에서 되풀이되는 패턴 | — (판단) |

**관계를 코드가 센다**(`store.person_relation`). 모델에게 세게 하면 틀리고,
안 주면 발췌만 보고 지어낸다. 넘기는 값은 넷이다 — 나를 **받는 사람(To)** 에
넣어 보낸 메일 수 vs **참조(Cc)로만** 온 수(둘은 다른 관계다) · 내가 보낸 메일
수와 **내가 답한 스레드 비율** · 먼저 메일을 보내는 쪽 · 교신 기간. 인용 검증이 필요
없는 사실이라 판단 슬롯이 근거로 쓸 수 있다. 실제로 그렇게 나온다:
*"먼저 보내는 쪽은 그 사람이 더 많고(3대2), 던지면 거의 매번 내가 받는다
(6개 중 5개)."*

**고르는 순서가 관계 순서다**(사용자 요구). 재료 스레드는 `(직접 + 내가 답함)`
순으로 먼저 고르고 그다음이 최신순이다 — 참조로만 돌던 공지가 앞자리를 차지하면
프로필이 '그 사람이 쓴 문장 모음'이 된다. 각 스레드에 **내 회신 한 조각**을
문맥으로 함께 싣는다(원문이라 §6.6 의 파생물 금지에 걸리지 않는다. 다만 인용
근거로는 못 쓴다 — `_PersonQuoteChecker` 가 그 사람 발화만 인정한다).

**표시**: `한 줄`은 라벨 없이 리드 문단(`.dxlead`), 근거 스레드 번호는 문장
**뒤에** 작은 `#` 로 — 11자리 번호가 줄 앞에 있으면 서술보다 먼저 읽혀 카드가
번호 목록이 된다. 인물 목록의 역할 줄(`dossier_roles`)도 이 `한 줄`을 쓴다.

**자주 같이 있는 사람**(`store.person_cohorts`, AI 0콜 — 2026-08-18 사용자 선택).
사람을 아는 데는 그 사람이 **누구와 같이 도는지**가 크게 들어간다. 카드 각주에
상위 3명을 링크로 달아 인물 사이를 건너다닐 수 있게 했다. 규칙 셋:

- **세는 단위는 메시지가 아니라 스레드다** — 한 스레드에서 열 번 말한 사람이
  다섯 스레드에 한 번씩 나온 사람보다 가깝지는 않다. 스레드 1개는 우연이라 뺀다.
- **말한 사람만 센다**(수신인은 안 센다). 전사 공지 수신자 200명이 '자주 같이
  있는 사람'이 되면 값이 0이다.
- 봇·자동발송은 인물 랭킹과 같은 기준(`is_noise_sender_hard`), 숨긴 스레드는 제외.

결정론이라 **프로필을 아직 안 만든 사람에게도 보인다** — AI 카드가 없을 때 오히려
더 쓸모 있다. 그때는 **안내 줄보다 먼저** 그린다(사용자 확인, 2026-08-18): 늘 있는
사실이 "아직 프로필이 없습니다" 아래로 밀리면 화면이 없는 것부터 말하게 된다.

**용어는 데이터가 말하는 만큼만**(2026-08-18, 사용자 확정). `먼저 거는 쪽`은 전화
말투라 `먼저 메일을 보내는 쪽`으로, `함께 도는 사람`은 은어에 가까워 `자주 같이
있는 사람`으로 고쳤다. 짝이 될 법한 `마무리하는 쪽`·`결정하는 쪽`은 **넣지
않았다** — 셀 수 있는 것은 '스레드의 마지막 메일 발신자'뿐이고 그 마지막 메일은
대개 "확인했습니다"라, 이름이 뜻을 부풀린다. 앞의 라벨은 AI 재료에 그대로 들어가
**모델이 받아 쓰는 말**이므로, 라벨을 부풀리면 산출이 함께 부푼다.

### 6.7 수집 폴더 범위 — 받은편지함 서브트리 (2026-08-09)

**왜 넓혔나.** 종전에는 `GetDefaultFolder(6)`·`(5)` 두 개만 열었다. Outlook 규칙이
수신 메일을 하위 폴더로 자동 분류하는 환경에서는 그 메일이 `Inbox.Items` 에 없어
**색인에 아예 안 들어오고, 경고도 없었다.** 화면은 그냥 조용했다 — 확산(다른 사람
배포)을 막는 가장 큰 결함이었다. 지금은 받은편지함 서브트리를 BFS 로 훑는다.
보낸편지함은 하위를 훑지 않는다(수신 분류가 동기였고 발신 분류는 드물다).

**정책은 COM 밖에 있다.** `plan_folders(cands, …) -> FolderPlan` 하나가 재귀·제외·
상한을 전부 정하고 COM 을 쓰지 않는다. COM 은 `_candidates()` 가 날 사실만
모아 준다. 덕분에 Windows 없이 전부 시험된다 — 여기서 검증할 수 없는 것을 최소로
줄이는 것이 이 파일의 오랜 방침이다.

불변식: **`len(specs) + len(skipped) == len(cands)`** — 어떤 폴더도 이유 없이
사라지지 않는다. `sync` 와 `doctor` 가 건너뛴 폴더를 이유와 함께 출력한다.

- **`received` 를 라벨과 분리한다.** 하위 폴더는 라벨이 `inbox` 가 아니면서
  내용물은 수신 메일이다. 종전의 `folder_name == "inbox"` 문자열 비교로는 정렬
  키와 시각 필드를 못 고르고, Sort 키·`_to_record` 시각·`heapq` 병합 키 셋이
  어긋나면 전역 시간순 입력 가정이 깨진다(§6.1의 mid-join 판정이 그 위에 있다).
- **지운 편지함·정크는 형제라 구조상 빠지지만 방어 판정을 남긴다** — IMAP 계정은
  `INBOX.Trash` 처럼 아래 붙는다. 동일 폴더 판정은 `==` 가 아니라
  `NameSpace.CompareEntryIDs` 다(MAPI 는 같은 객체에 short-term/long-term 두
  EntryID 를 준다). `GetDefaultFolder(23)` 은 스토어에 따라 예외라 try/except.
- **`DefaultItemType != 0` 폴더는 건너뛴다.** 최적화가 아니라 필수 — 일정·연락처
  폴더에 `Sort("[ReceivedTime]")` 을 걸면 예외가 난다.
- `messages.folder` 에 **상대 경로**(`inbox/프로젝트/NPX`)를 남긴다. 읽는 코드는
  아직 없지만 "이게 어디서 왔나"를 되짚을 유일한 수단이고, 루트는 종전대로
  `inbox`/`sent` 라 옛 행과 어긋나지 않는다. **폴더명은 AI 프롬프트에 싣지
  않는다** — 고객사·프로젝트명을 담기 때문이고, 지금도 안 실린다.

**워터마크 문제 — 이 변경에서 가장 날카로운 지점.** 증분 `Restrict` 는
`datereceived > last_sync` 다. 규칙이 **이미** 하위 폴더로 옮겨 둔 메일은 전부
워터마크보다 과거라, 범위만 넓히면 아무것도 안 들어온다. 그렇다고 `sync --full`
을 강요하면 규칙 5 위반이다. 그래서 **폴더별로 "한 번 완주했는가"** 를 기록하고
(`sync_state` 의 `outlook_folders_v1`), 처음 보는 폴더만 `Restrict` 없이 한 번
전체를 읽은 뒤 증분에 합류시킨다.

- 식별자는 EntryID 가 아니라 **정규화된 상대 경로**다. 폴더 EntryID 는 OST 재생성·
  프로필 재작성에 바뀌고 문자열 비교도 안 된다. 경로의 유일한 불안정성은 이름
  변경이고, 그 대가는 "한 번 더 읽고 전부 중복으로 건너뜀" 이라 자기 치유된다.
- **기록은 `ingest` 가 성공으로 끝난 뒤에만.** 부분 백필을 완료로 적으면 그 폴더의
  나머지가 영구 누락된다 — 다시 읽는 쪽이 비싸도 안전하다. 소비자가 제너레이터를
  버리면(`GeneratorExit`) 완주로 치지 않는다.
- **범위를 벗어난 폴더는 기록에서 뺀다.** 하위 폴더 수집을 껐다가 한 달 뒤 다시
  켜면, 기록에 남아 있는 한 그 폴더는 '아는 폴더'라 증분으로 열린다. 그런데 전역
  워터마크는 받은편지함 때문에 그동안 전진해 있어 **꺼져 있던 한 달치가 워터마크
  뒤에 숨어 영영 안 들어온다.** 그래서 sync 성공 시 `done` 을 이번에 실제로 연
  폴더와 교집합한다 — 다시 켜면 한 번 전체를 읽고(대부분 중복) 그 구간을 메운다.
  같은 장치가 `exclude_folders` 추가·해제와 `max_folders` 초과에도 적용된다.
  단, 계획이 비었으면(폴더 순회 실패) 지우지 않는다 — 지우면 다음 sync 가
  사서함 전체를 다시 읽는다.
- 명시적 `--since`/`--full` 은 사용자가 범위를 정한 것이라 백필을 유발하지 않는다.
- 루트 둘은 상태 파일이 없어도 '아는 폴더'로 친다 — 업그레이드 첫 sync 가 사서함
  전체를 다시 읽는 사고를 막는다.

**설정**(`[sources]`, 전부 `cfg.opt`): `include_subfolders`(기본 `true`) ·
`exclude_folders`(이름 또는 상대 경로) · `max_folders`(기본 50, 0=무제한).
기본을 켜 둔 이유는 **옵트인 수정은 정작 색인이 빈 사람에게 닿지 않기** 때문이다 —
그 사람은 켤 스위치가 있다는 것을 모른다. 상한이 필요한 이유는 `heapq.merge` 가
첫 소비 때 모든 반복자를 기동해 N 개의 `Restrict`+`Sort` 뷰가 첫 레코드 전에 다
만들어지기 때문이다(실측 확인).

웹 **설정 › 수집 폴더**는 **마지막 수집이 본 폴더 목록**(`sync_state` 의
`outlook_folder_view_v1`)을 렌더한다 — 설정 화면을 열 때마다 COM 을 부르면 페이지
로드가 사서함 순회에 묶이고 Windows 밖에서는 화면이 아예 안 뜬다.

**저장된 '건너뛴 이유'는 종류를 나눠 둔다**(`Skip.kind`). 이걸 뭉쳐 두었다가
2026-08-10 에 버그가 났다 — 제외를 풀어도 지난 수집의 `제외 목록` 이 남아 그 행이
버튼 없이 갇혔다. 저장된 이유가 **설정의 거울**인데 화면이 그걸 설정과 무관한
사실로 읽은 것이다.

| kind | 예 | 화면 |
|---|---|---|
| `structural` | 지운 편지함 계열 · 메일 폴더 아님 | 이유만, **버튼 없음**(켤 수 없는 것에 선택지를 주면 거짓말) |
| `setting` | 제외 목록 · 하위 폴더 수집 꺼짐 | 저장분을 **쓰지 않고 지금 설정**으로 판정 + 버튼 |
| `capacity` | 폴더 상한 N 초과 | 버튼 + 참고 사유(설정도 구조도 아니고 '그때 자리가 없었다'라 낡지 않는다) |

규칙 둘. **① 설정으로 정해지는 것은 지금 설정을 보고, 저장분은 설정과 무관하게
참인 것에만 쓴다. ② 사용자의 현재 제외 설정을 종류보다 먼저 본다** — 이 순서라야
저장분의 종류를 잘못 읽어도 사용자가 되돌릴 수 있다.

`kind` 는 나중에 생긴 필드다. 처음에는 키를 갈아 구 값을 무시했는데 **사용자
화면에서 폴더 목록이 통째로 사라졌다**(2026-08-10). 지금은 버리지 않고
`infer_skip_kind()` 로 사유에서 추정해 채운다 — 그 사유 문자열은 이 파일이
한 곳에서 만들므로 되짚을 수 있고, 다음 수집이 정확한 값으로 덮는다. 모르는
사유는 `structural` 로 본다(버튼을 안 주는 쪽이 안전하고, 규칙 ②가 탈출구다).

`_find_by_message_id` 도 같은 계획을 훑는다. 이건 일관성이 아니라 **버그 수정**
이다 — 종전에는 규칙으로 분류된 메일의 `open`·`attach` 폴백이 원리적으로 실패했다
(폴더 이동으로 EntryID 가 바뀌면 Message-ID 재검색으로 넘어가는데, 그 재검색이
기본 폴더 둘만 봤다).

### 6.8 Outlook 에서 사라진 메일 (2026-08-09)

Outlook 에서 지우거나 수집 범위 밖으로 옮긴 메일은 색인에 그대로 남는다. 그
자체는 의도다 — "Outlook 이 잊어도 여기는 기억한다"가 이 도구의 값이고, 용량
정리로 지운 메일까지 같이 없애면 그 값을 스스로 부순다. 문제는 그 메일이 계속
**'회신 필요'로 뜬다**는 것이었다. 열리지도 않는 항목이 목록에 남으면 목록 전체를
못 믿게 된다.

**원칙: 삭제는 사람의 의도라 코드가 해석하지 않는다. 다만 "Outlook 에 더 이상
없다"는 사실은 알린다.** 사람이 메일을 지우는 이유는 최소 네 가지이고(스팸 정리 ·
용량 확보 · 민감 정보 · 실수) 그중 둘은 서로 정반대의 처리를 요구한다 — 그래서
"Outlook 에 없으면 지운다"는 자동 규칙은 만들지 않는다.

- 기록은 **원문 열기의 부산물**이다(`messages.gone_at`). 열기가 실패한 그 순간
  적으므로 추가 COM 왕복이 0이고, 되돌아오면 다음 열기 성공이 알아서 지운다.
- **판정에서만 뺀다** — `unanswered()` 와 `open_thread_tails()` 가 최신 메일이
  사라진 스레드를 제외한다. 검색·분석·본문은 그대로다(내용은 여전히 사실이다).
- 스레드 화면에 `Outlook에 없음` 배지. 경고색을 쓰지 않는다 — 사용자가 직접
  지운 것일 수 있고, 이건 사실 통보지 문제 제기가 아니다.

**정말로 지우는 기능(`forget`)은 만들지 않았다** — 장기 과제로 미룬다. 설계 조사
결과는 아래에 남긴다(§12).

### 7.2 통계는 왜 이만큼만 남았나

2026-07-13 개편은 "mail-trends·Email Meter 등 **표준 지표 이식**"이었다. 그 기준이
이 도구의 목적("Outlook이 못 하는 것만")이 아니라 남의 제품에서 왔다는 것이
문제였다 — 개편 직전 기록도 "기존 §1–5가 신호성 위주라 **큰 도움 안 됨**"이었으니,
같은 질문에 두 번째로 답한 셈이다. 이번엔 **"그래서 뭘 할지가 나오는가"** 하나로
쟀다. 4타일+6섹션 → 2타일+4섹션.

| 뺀 것 | 이유 |
|---|---|
| 자주 주고받는 상대 | **인물 화면이 흡수.** `report.py` 안에서 `rank_people`과 옛 `sig_volume`이 같은 것을 두 번 랭킹했다. `person_metrics`는 §3·§5·§6 내용을 **그 사람 기준**으로 이미 전부 준다(docstring: "→ /stats 수치와 정의상 일치") |
| 답 기다리는 내 발신 | **2026-07-30 신호 노출 폐기의 잔존분.** 정규식(`?`·부탁드·바랍니다…)으로 '내 발신이 요청인가'를 판정했다. 데모 실측에서 1위·26일·critical 항목이 "상세는 별첨 참고 **바랍니다**"(진척 보고의 맺음말)였다. `person_metrics`도 이걸 계산했지만 **웹은 렌더하지 않았다** — 죽은 계산까지 함께 걷었다 |
| 야간·주말 비율 | 메일 지식이 아니라 자기 정량화. 활동 히트맵과도 중복 |
| 응답 시간 절 | 대기 목록이 빠지면 숫자 둘짜리 카드다 → **타일로 승격**. 내 값 하나로는 27시간이 느린지 알 수 없어 상대 값이 기준 역할을 하므로 **둘은 짝**이다(떼면 남은 하나가 해석 불가) |
| 볼륨 타일 2개 | §1 차트와 **같은 함수 한 번 호출**에서 나왔다. 스파크라인은 발신·수신이 각자 축을 써서 '두 선의 벌어짐'을 못 보여주므로 차트를 남기고, 타일에만 있던 최근 주 수치·델타를 §1 안 한 줄로 옮겼다 |

**검토 기간 선택(2/4/8/16W)도 없앴다.** 근거 셋:

1. **절마다 필요한 창이 다르다.** 추세는 길어야 읽히고(코드가 스스로 "6–8주부터
   안정화"라고 경고한다) 왕복 목록은 짧아야 '회의 전환 후보'로 쓸모가 있다(넉 달
   전 핑퐁은 끝난 논의다). 하나로 강제하면 **어느 값을 골라도 절반은 틀린 창**을
   본다. 선택기가 권한을 준 게 아니라 타협을 강요했다.
2. **안 쓰였다는 증거.** 이 선택기는 한동안 **고장난 채**였는데(축만 바뀌고
   데이터셋은 전량) 사용 중이 아니라 코드 검토로 발견됐다(2026-07-10 수정).
3. **전부에 먹지도 않았다.** 응답 지표만 늘 '최근 2주' 앵커라, 16주를 고르면
   `내 응답 중앙값`이라는 같은 이름이 한 화면에서 29.1h와 26.2h를 냈다.

대신 창을 상수로 고정하고(`TREND_WEEKS=12` / `RECENT_WEEKS=4`) **각 절이 자기 창을
화면에 적는다**(`최근 12주` 칩) — 전역 선택기가 있는데 일부만 따르는 것보다 정직하다.
`load()`는 가장 긴 창으로 **한 번만** 읽고 짧은 창 절이 잘라 쓴다(누를 때마다 전량
재적재하던 것보다 싸다). 구 북마크의 `?weeks=`는 조용히 무시한다.

**숨김의 취급이 절마다 다르다** — 왕복 논의 같은 **목록**은 숨김을 존중하고,
볼륨·히트맵 같은 **집계**는 전량 센다. 숨김은 "조용히 하라"이지 "없던 일로 하라"가
아니기 때문이다. `sig_pingpong`은 인물 카드의 '진행 중'도 만들므로 이 제외가
거기까지 전파된다 — 같은 규칙이라 의도된 것이고, 회귀 테스트가 지킨다.

#### 하나 더한 것 — 통계 5절 '기억 커버리지'

지운 것만 있는 정리는 아니다. **이미 있는 트레이드오프의 계량기**를 하나 더했다.

수확(`distill._harvest_window`)의 소급 상한은 `[ai] summary_max_days`(기본 1일)라
**앱을 안 연 날의 메일은 요약·수확에서 영구히 빠진다.** 그 함수 docstring이
"3일 넘게 비운 구간의 가장 오래된 날은 요약에서 빠질 수 있음(의도된 트레이드오프)"
이라고 스스로 적고 있다. 설계는 옳은데 **대가가 어디에도 안 보였다** — 사용자는
자기 기억에 구멍이 몇 개인지 모르는 채로 그 상한을 올릴지 판단할 수 없었다.

- 요일(행)×주(열) 격자에 **채운 칸 = 그날 지식이 쌓인 날**. 농도가 아니라 2단계인
  것은 질문이 '얼마나'가 아니라 '쌓였나'이기 때문이다. 주말은 테두리로만 구분한다
  (빈 칸이어도 문제가 아니므로).
- 판정은 **회고 파일의 AI 절 유무**(`## Executive Summary` · `## AI 회고 분석`)다.
  **파일 존재만 보면 거짓말이 된다** — 웹의 자동 생성(`_maybe_auto_review`)은
  `ai=False`라 파일은 매일 생기지만 요약·수확은 돌지 않는다.
- 숫자 셋: 지식이 쌓인 날 / 요약된 스레드 / 저장된 지식. 구멍을 메울 방법
  (`summary_max_days` 상향)을 문구에 함께 적는다 — 진단만 하고 처방이 없으면
  또 하나의 허영 지표가 된다.
- AI를 한 번도 안 돌린 설치에는 **0/N 격자 대신 한 문장**을 낸다. 실패·미실행·
  없음을 가르는 이 저장소의 관례(`review.EXEC_EMPTY`)와 같은 태도다.

### 7.3 관계 배지

목록 행의 발신인 뒤에 붙는 두 글자짜리 사실 — **`↩ 0`**(이 사람에게 한 번도 보낸
적이 없다, 받은 것이 `_ONEWAY_MIN`=3통 이상일 때만) · **`첫 메일`**(이 사람에게 받은
첫 메일). '읽을지 말지'의 1차 판단이 화면에 없었다는 것이 출발점이다.

- **왜 노이즈 규칙 위에 또 두나.** 노이즈는 발신 주소·제목 문자열이라 설치마다
  손으로 채워야 한다. 왕래 수는 **사용자 행동 기록**이라 설정 없이 개인화되고,
  규칙이 놓친 발신자를 잡는다(실측: 데모에서 광고·뉴스레터·웨비나가 노이즈 규칙을
  통과해 목록에 남았는데 셋 다 `↩ 0` 이었다).
- **할 말이 없으면 아무것도 안 쓴다.** 모든 줄에 붙는 배지는 배지가 아니라 소음이다.
- **표시만 한다.** 정렬·필터·자동 숨김에 쓰지 않는다 — 쓰는 순간 "내가 처음 답하는
  사람"이 화면에서 사라진다.
- `첫 메일` 판정은 `people.first_seen` 과 **그 행의 시각**을 맞춘다. `from_count` 는
  지금까지의 누계라 과거 행에 그대로 쓰면 옛 메일이 전부 첫 메일이 아니게 된다.
- 재료는 목록 쿼리에 `LEFT JOIN people` 하나로 딸려 온다(행당 추가 조회 없음).

### 7.4 선택 검색

우측 본문에서 텍스트를 고르면 「이 말 찾기」 버튼이 뜨고, 누르면 **좌측**이 검색
결과로 바뀐다(`/search` 는 좌측 라우트) — 읽던 스레드는 우측에 그대로 남는다.
새 엔드포인트·새 화면이 없다: `load("/search?sel=1&q=…&exclude=…", "left")` 한 번이
조각 로딩·히스토리·`←` 복원을 전부 기존 경로로 태운다.

- **읽던 그 메일은 뺀다**(`exclude`). 안 빼면 1등이 늘 방금 읽던 문장이다.
- **질의를 다듬지 않는다.** 대신 정밀 결과(tier 1–3)가 하나도 없을 때만
  **좁힐 말을 칩으로** 내고 고르는 것은 사람이 한다(`_narrow_chips`).
- 버튼은 **포커스를 훔치지 않는다**(`mousedown` 에서 `preventDefault`) — 훔치면
  브라우저에 따라 선택이 풀린다. 버튼이 떠 있는 동안 `Enter` 실행 · `Esc` 닫기 ·
  `Space` 는 읽기 창을 넘기지 않는다(기존 키보드 가드는 **입력란 포커스만** 보고
  선택 상태를 모른다).

#### 왜 질의를 자동으로 다듬지 않나

2026-08-07 실측(코퍼스 문장 150개, 읽던 메일 제외):

| | 정밀 결과 회복 | 평균 스레드 | 0건 |
|---|---|---|---|
| 선택 그대로 | 0% | 8.3 | 17% |
| 드문 말 3개 AND | 6% | 1.2 | **64%** |
| 긴 말 3개 AND | 10% | 5.8 | 30% |

**AND 로 묶으면 소음 대신 아무것도 안 남는다.** 그런데 같은 표본에서 **97%는
선택 안의 어느 한 단어로는 정밀 결과가 나온다** — 정보가 없는 게 아니라 어느
단어인지 코드가 모르는 것이다. 그래서 고르지 않고 **보여 준다**(칩 3개면 94% 커버,
긴 말 순. 드문 말 순은 75% — 드문 말은 변별력이 아니라 토큰화 조각이 드물어서
올라온다). 서술형 어미는 뺀다(커버리지 손실 없이 조각이 0이 된다).

**같은 약한 신호라도 코드가 대신 고르면 해가 되고 사람에게 보여 주면 해가 없다** —
칩이 빗나가면 안 누르면 그만이지만, 자동 정제가 빗나가면 결과가 통째로 사라지고
사용자는 이유를 못 본다(폐기한 '지금 할 일' 큐와 같은 부류의 실수다).
칩 아래에 기존 「AI로 다시 찾기」가 이어진다 — 긴 선택의 진짜 답은 어휘 검색이
아니라 의미 검색이고, 싼 수를 먼저 낸다.

또 하나: **"길다"를 자수로 정의할 수 없다.** 어절 수를 1→10 으로 늘리며 재 보면
정밀 결과 비율이 75% → 36% → 19% → … → 0% 로 매끄럽게 떨어진다. 계단이 없어서
어디를 잘라도 임의값이다. 그래서 기준은 입력 길이가 아니라 **결과**다.

### 7.5 검색으로 들어간 낱말 강조

검색 결과 링크가 `?focus={mid}&hl={낱말}` 을 싣는다. **어느 메일인지는 `focus`
가, 무엇 때문에 걸렸는지는 `hl` 이** 알려준다 — 종전에는 앞의 절반만 있었다.

- `hl` 은 원문 질의가 아니라 `search.parse_query` 가 갈라낸 **본문 낱말만**이다
  (`from:강미래 after:2026-06 리포트` → `리포트`). 질의 문법의 진실원은 한 곳이다.
- 칠하는 것은 **클라이언트**다. 서버는 `render_thread` 를 손대지 않는다 —
  본문은 정제된 메일 원본 HTML 이라 정규식으로 `<mark>` 를 끼우면 태그 안쪽에
  걸려 마크업이 깨진다.
- **CSS Custom Highlight API**(`CSS.highlights` + `::highlight(kw)`)로 Range 만
  등록한다. DOM 무변형이라 되돌릴 코드가 없고, 선택 검색이 고른 문자열이 노드
  경계에서 잘리는 일도 없다(`<mark>` 로 감쌌다면 둘 다 문제가 됐다).
  못 쓰는 브라우저에서는 조용히 넘어간다 — 스크롤·메일 테두리는 그대로다.
- **접힌 인용 안에 일치가 있으면 먼저 편다.** 닫힌 채로는 칠해도 안 보인다.
  순서가 중요하다: 접힘을 열어 높이를 확정한 **뒤에** `focusMsg` 가 스크롤한다.
  (실측: `CMA` 로 찾아 들어가면 일치 1건이 전부 인용 안에 있다.)
- 흔한 말(`합니다`)로 들어올 때를 위해 Range 상한 `HL_MAX`=200.
- 끄는 것은 `Esc` 인데 **맨 뒤**다 — 입력란 탈출이 먼저다. 순서를 뒤집으면 검색창
  포커스 중 `Esc` 가 blur 를 안 하고 강조만 끈다(실기 확인).

### 7.6 키보드

`j/k` 이동 · `n/p` 스레드 내 메시지 이동 · `f` 플래그 · `h` 숨김 · `/` 검색.
`f/h`는 우측에 열린 스레드에, 없으면 목록 커서 행에 동작한다.
필터 바 오른쪽 ⓘ에 안내가 있다.

### 7.7 테마와 스킨 — 두 개의 독립 축

`<html data-theme data-skin>` 두 속성으로 갈린다. **밝기(theme)와 모양(skin)은
별개 축**이라 네 조합이 모두 성립한다. 둘 다 즉시 적용되고 `overrides.json`에 남는다.

| 축 | 값 | 바꾸는 것 |
|---|---|---|
| `theme` | `light` · `dark` | 색 |
| `skin` | `classic` · `bento`(화면 표기 **카드형**, **기본** 2026-08-11–) | 색조·둥글기·그림자·서체 + 홈·리포트 배치 |

- **classic 은 스킨 블록의 영향을 받지 않는다.** `_SKIN_CSS`의 모든 규칙이
  `[data-skin='bento']`를 요구하므로, classic 을 고르면 존재하지 않는 것과 같다
  (회귀 테스트가 모든 선택자를 검사한다). 기본은 카드형이다(2026-08-11 사용자
  확정 — 카드형이 완성돼 기본 경험으로 승격. 미설정 사용자만 바뀌고, 설정에서
  classic 을 고른 값은 `overrides.json` 에 있어 무영향). 불법값 폴백도 기본과
  같은 `bento` — 기본이 둘이 되면 설정 화면 active 표시와 실제 화면이 어긋난다.
- **스킨은 토큰 오버라이드가 본체**다. `_CSS`는 컴포넌트 규칙에서 `var(--…)`를
  342곳 쓰고 색을 박아 넣은 곳은 9곳뿐이라 값만 덮으면 된다. 선택자 규칙은
  토큰으로 표현할 수 없는 것만 최소로 둔다(현재 3개). 규칙을 계속 더하고 싶어지면
  그건 스킨이 아니라 레이아웃 변경이라는 신호이므로 별도 렌더러로 간다.
- **특이도 함정**: 다크 토큰은 `:root[data-theme='dark']`(0,2,0)이라 스킨의 라이트
  블록과 같다. 순서로 이기게 두면 '다크+벤토'에서 라이트 색이 덮어쓰므로, 라이트
  블록에 `:not([data-theme='dark'])`를 붙여 특이도를 올린다.
- 벤토는 **강조색을 건드리지 않는다** — 라이트의 파랑, 다크의 코랄은 앱이 이미
  내린 판단이다(다크에서 파랑보다 눈이 편하다).

**레이아웃까지 바꿀 때의 선.** 색·모양만으로는 벤토의 감각이 안 나온다(목록 행이
이미 카드 형태라 토큰이 바꿀 것이 적다). 마크업을 바꾸되 **"이미 화면에 있는 것을
다시 배치"하는 데까지만** 한다 — 새 AI 호출이나 새 질의가 끼면 그건 스킨이 아니라
다른 기능이다(2026-08-01 사용자 지적). 현재 적용분은 하나다:

- **리포트 절 카드** — `_md_to_html(cards=True)` 가 `##` 절마다
  `<section class='rcard'>` 로 감싼다. 읽는 파일도 계산도 그대로고 감싸는 방식만
  바뀐다. `## 참고` 는 이미 접힘이라 이중으로 감싸지 않고, 꼬리말(조사 범위)은
  카드 밖에 둔다. classic 은 `cards=False` 로 지금과 완전히 같은 HTML 이다.
- **벤토 홈** — 랜딩(`_ask_landing`)이 '이어서 볼 것' 줄 대신 격자를 깐다.
  재료는 지금 랜딩이 이미 읽는 값(지식 카운트·최근 지식 제목 3건·최근 주간
  보고·자주 왕래)과 **저장된 오늘 회고 파일**(`load_daily` + `_md_sections`)
  뿐이다 — 리포트를 **다시 만들지 않는다**. 회고가 아직 없으면 안내 타일 하나를
  세운다(2026-08-11 — 홈 GET 이 자동 생성을 이미 걸어 두므로 "만드는 중"은
  사실이고, 완성되면 `/latest` 재렌더가 실제 타일로 바꾼다). AI 가 쓴 절
  (Executive Summary)은 사용자가 AI 회고를 돌렸을 때만 파일에 있으므로 있으면
  보여주고 없으면 비운다.
  홈 타일에도 '처리함' 버튼이 붙는다(2026-08-11 사용자 확정 — "누르면 화면이
  튄다"던 2026-08-01 결정을 뒤집음: 홈은 `/latest` 로 in-place 재렌더되는
  화면이라 전제가 사라졌다). 버튼은 `back='/'` 로 홈에 그대로 돌아오고
  (`_report_back` 은 리터럴 `/` 만 상수로 되돌린다 — 헤더 인젝션 방어 유지),
  접기를 절 분해 **전에** md 전체에 적용해 타일 라벨의 `(N건)` 도 다시 센다.
  실측: 클래식 홈 DB 질의 2회, 벤토 5회(0.04 → 0.14ms). 결정론 엔진을 돌렸다면
  회당 +7.4ms 였다.
  **링크 있는 타일은 통째로 눌린다**(2026-08-11) — `data-href` 를 `app.js` 위임
  리스너가 줍고(내부 링크·버튼·폼·접기가 항상 우선, 텍스트 선택 중엔 무시),
  키보드는 `tabindex=0` + Enter. `<a>` 로 감싸지 않는 이유는 본문의 스레드
  링크·처리함 폼과 인터랙티브 중첩(invalid HTML)이 되기 때문이고, 헤더의
  '열기' 앵커는 JS 꺼짐 폴백으로 남긴다(`tabindex=-1` 로 탭 스톱은 타일당 하나).
  **칸 크기는 내용 수에 맞춘다** — 전부 같은 크기면 격자가 아니라 표다. 12열 위에서
  줄이 딱 떨어지는 조합만 쓴다(내용 타일 1장 `12` / 2장 `8+4` / 3장 `12+6+6`,
  숫자 타일 3장 `4+4+4`, 회고 없는 날은 안내 `12` + `4+4+4`). 화면 표기는
  '카드형'이고 **저장값은 `bento` 그대로**다 —
  값을 바꾸면 이미 고른 설정이 조용히 풀린다(암묵지 후보의 '저장/유보'와 같은 방식).

### 7.8 다크 모드에서 메일 본문

메일은 **흰 배경을 전제로** 색을 고른다. 메일 본문은 `body`의 `--bg`(다크 기준
`#16181b`) 위에 그려지는데(`#right`·`.msg`에 배경 선언이 없다), 거기 그대로 얹으면
Outlook 기본 강조색이 전부 WCAG AA(4.5:1) 미달이다 — 빨강 `#C00000` 2.75:1 ·
파랑 `#0070C0` 3.45:1 · 보라 `#7030A0` 2.22:1. 그래서 `.mailhtml *`을 테마색으로
평탄화하는데, 그러면 작성자가 준 강조가 전부 사라진다.

`clean.add_dark_colors()`가 **색상(H)은 두고 명도(L)를 올린**(채도는 0.75로 상한)
값을 `--dk` 커스텀 속성으로 함께 실어 보내고, 어느 쪽을 쓸지는 CSS가 고른다.

```
<span style="color:#C00000; --dk:#ec7979">      6.42:1 로 올라가면서 빨강은 빨강
```

- 채도 8% 미만(검정 본문·회색 안내문)은 손대지 않는다 — 본문 글자는 테마색이 맞다
- **인라인 `!important`는 렌더 시점에 걷어낸다** (2026-07-27). 인라인 스타일의
  `!important`는 시트의 `!important`를 항상 이기므로, 남기면
  `color:black!important`(Confluence·뉴스레터형 표 템플릿에 흔한 패턴)가
  평탄화를 뚫고 다크 배경 위 검은 글자로 남는다. 메일 색과 경쟁하는 시트
  규칙은 다크에만 있어 제거해도 라이트 표시는 안 변한다 — `add_dark_colors`가
  `--dk` 주입과 함께 처리한다
- **저장이 아니라 렌더 시점**에 붙인다. 저장 시점에 구우면 이미 저장된 메일은
  재수집해야 색이 살아나고, 그건 §1 원칙 5 위반이다. 비용은 데모 코퍼스 기준
  본문 1건당 0.002ms(색이 많은 본문도 0.03ms 미만)
- **서버가 한쪽 색만 구워 보낼 수 없다.** 테마 토글이 클라이언트에서 즉시
  `data-theme`을 바꾸고 다시 받아오지 않기 때문이다
- CSS 두 줄의 **순서가 중요하다** — 자손 상속이 먼저, 자기 색이 나중. ①이 없으면
  `<span color=red><b>긴급</b></span>`에서 `<b>`가 평탄화에 걸려 혼자 흰색이 된다.
  둘의 특이도가 (0,4,1)로 같아 순서가 승부를 가른다. 링크는 둘 다 제외(링크색 유지)
- 라이트 테마에는 `--dk`를 읽는 규칙이 없어 선언만 남고 무해하다

**배경색은 아직 다루지 않는다** — 형광펜과 표 헤더 `bgcolor`는 다크에서 사라진다.
살리려면 배경 명도를 낮추면서 그 안 글자 대비까지 함께 설계해야 한다.

### 7.9 SPA 배선 (건드릴 때 주의)

- `paneFor(path)`(클라이언트)와 `route()`의 pane 배정(서버)이 **반드시 일치**해야
  한다. 어긋나면 폴링이 엉뚱한 패널을 보다가 대기 화면이 멈춘다.
- `history.pushState`는 `inject()` 한 곳에서만 부른다. 뒤로가기는 좌·우 URL과
  깊이를 함께 담은 상태로 두 패널을 동시에 복원한다.
- 백그라운드 잡(리뷰·동기화·분석·주간)은 단일 슬롯 + 진행 dict + `/xxx/status` 폴링
  구조를 공유한다.
- 분석 잡 생성은 **POST `/ask/jobs`**만 한다. GET은 저장된 것만 연다 — 새로고침이나
  북마크가 AI를 부르면 안 되고, 질문 문구가 브라우저 이력에 남아서도 안 된다.
- **자리를 옮긴 요소는 옛 자리의 여백도 함께 내려놓는다.** 쟁점 분석 진입
  (`.tmap`)은 원래 액션 바 아래 독립 줄이라 `margin-top:10px` 을 갖고 있었는데,
  2026-08-16 에 `.diagbar`(브리핑 버튼 줄) 안으로 옮긴 뒤에도 그 여백이 남아
  flex 아이템이 5px 내려갔다 — 두 버튼의 윗변이 어긋나 보였다(2026-08-18 사용자
  보고, `getBoundingClientRect` 로 실측). `.analysis .diagbar .tmap { margin: 0 }`.
- **가로채기에서 빼는 링크는 그 이유가 링크에 적혀 있어야 한다.** 예외는 셋이고
  전부 근거가 다르다: `/stats`(전폭 페이지) · `.imgshow`(주입은 문서의 CSP 를 못
  바꾼다) · **`.more[data-more]`**(목록 하단 센티널 — 관찰자가 이어 붙이고, JS 가
  꺼졌을 때만 전체 페이지 폴백). 종전에는 마지막이 `.more` 였는데, 벤토 타일의
  '열기'가 **모양 때문에** 같은 클래스를 써서 함께 빠졌다 — 같은 타일인데 본체를
  누르면 SPA, '열기'를 누르면 문서 재로드였다(2026-08-18 실측). 클래스가 모양을
  뜻하는지 동작을 뜻하는지 갈리는 자리라, 선택자는 **동작이 걸린 표식**
  (`[data-more]`)까지 적는다.

#### 한 클릭에 두 번 이동 — '← 인물' 되돌아오기 (2026-08-18)

사용자 보고: *"프로필을 만들고 난 직후 '← 인물'을 누르면 목록에 들어갔다가 다시
그 인물 화면으로 돌아온다."* 원인은 **핸들러 둘이 같은 클릭을 처리한 것**이다.

- 링크 가로채기(`load(href)`)가 `/people` 로 이동시킨다 — 목록이 뜬다.
- 곧이어 `.backlink` 핸들러가 `leftBack()` 을 돌려 **좌측 스택 맨 위**를 다시
  연다. 평소엔 그 값이 `/people` 이라 목적지가 같아 아무도 눈치채지 못했다.
- 프로필 잡은 POST 뒤 `/people/dossier/status?addr=…` 로 돌려보냈고, 그 주입이
  직전 인물 화면을 스택에 밀어 넣는다. 그래서 그때만 스택 맨 위가 인물 화면이
  되고 — 목록이 깜빡 뜬 뒤 인물 화면으로 되돌아온다.

고친 것 둘. **겉모습이 같아도 동작이 다르면 클래스를 가른다**(사용자 지적:
*"명시적 link 가 back 으로 되어 있는 경우가 문제"*) — 되짚기 링크는 `.uplink`
하나로 모으고 `.backlink`(`href="#"`) 와 그 전용 핸들러는 없앴다. 그리고 **잡의
복귀 주소는 '장소'여야 한다** — 프로필도 현안 브리핑처럼 `/people?addr=…` 로
돌아온다(인물 화면에도 대기 마커가 있어 폴링은 이어진다).

#### '←'는 어디로 가야 하나 — 이름을 함께 쌓는다 (2026-08-18)

`← 인물`(목록 고정)로 바꾸자 **반례가 나왔다**(사용자): 인물 화면에 들어오는 길은
여섯이다 — 스레드의 발신자 이름 · 인물 목록 · 업무 어휘 지도 · 자주 같이 있는
사람 · 분석의 인물 추천 · 홈 타일. 목록은 그중 하나뿐이고, 스레드 발신자 링크가
실사용에서 가장 잦다. 게다가 인물 화면은 **좌측 패널의 한 뷰**라(스레드는 우측에
그대로 남는다) '목록의 자식'이라는 계층이 애초에 약하다.

그래서 좌측 이력에 URL 과 **그 화면의 이름**을 함께 쌓고(`leftStack` 항목이
`{url, label}`), 인물·주소별 메일 화면의 `←` 를 그 값으로 그린다(`paintUpLink`).
이름은 새로 만들지 않는다 — 인물류는 화면 제목(`.ptitle`), 나머지는 **상단 메뉴의
글자**를 그대로 읽는다(`screenLabel`). 링크는 여전히 **진짜 링크**라 우클릭·새 탭이
되고, 되짚기 이동은 스택에서 빼며 다시 쌓지 않는다(왕복해도 안 자란다).
좌측 이력이 없으면(직접 진입·새로고침) 서버가 렌더한 기본값(`← 인물`)이 남는다.

부수 효과로 **앱 밖으로 나가는 길이 사라졌다**. 종전 `.backlink` 는 스택이 비면
`history.back()` 을 그대로 불렀고, 그게 Minerva 밖이면 창이 문서를 떠나 **서버가
스스로 종료**된다(§7.11 창 수명). 이제 `history.back()` 은 상단 ← 버튼 하나뿐이고
거기엔 `appDepth > 0` 가드가 있다.

**CDP 로 14가지 경우를 클릭까지 태워 확인했다** — 목록·메일함·검색·홈·인물→인물
(자주 같이 있는 사람)·주소별 메일에서 각각 라벨과 목적지가 맞는지, 프로필 만든
직후·같은 인물 재진입·왕복 3회·브라우저 뒤로 뒤에도 어긋나지 않는지, 그리고
인물로 갔다가 되돌아와도 **우측 스레드가 유지**되는지. 그리고 **잡의 복귀 주소는 '장소'여야 한다**
— 프로필도 현안 브리핑과 같이 `/people?addr=…` 로 돌아온다(인물 화면에도 대기
마커가 있어 폴링은 그대로 이어진다). 상태 엔드포인트는 폴링만 쓴다.

CDP 로 클릭까지 태워 전후를 확인했다: 고치기 전 `← 인물` → `/people?addr=…`
(목록행 없음), 고친 뒤 → `/people`(목록행 있음).

#### 창 크기는 창을 열 때만 복원한다 (2026-08-19)

사용자 보고: *"통계 창에 들어갔다 나오면 창 크기가 재설정된다."* 맞다 —
**통계는 전폭 페이지라 `app.js` 가 없다**(`/stats` 는 `appwin.js + report.js`).
창 크기 기억은 전부 `app.js` 에 있으므로 통계 화면에서 창을 조절하면 아무도
저장하지 않는데, 돌아오는 순간 `app.js` 가 저장값을 읽고 20px 이상 다르면
`resizeTo` 로 되돌려 놨다.

고친 방식: **복원은 창마다 한 번**(`sessionStorage` — 창을 닫으면 비워지므로 '이
창에서 이미 복원했나'와 정확히 같은 뜻이다). 저장은 종전대로 매번 — 다음 실행의
`--window-size` 는 그대로 최신 크기를 받는다. storage 가 막힌 환경에서는 복원을
건너뛴다: 앱 창은 실행 인자로 이미 저장 크기로 열리므로 잃는 것이 없다.

원칙 한 줄: **창 크기는 사용자가 마지막에 만진 것이 정답이다.** 화면을 옮길
때마다 앱이 되돌리지 않는다.

#### Executive Summary 에서 검토 소감을 뗀다 (2026-08-19)

사용자 보고: *"Executive Summary 자리에 감상평이 오고, 본문은 `---` 뒤 단락으로
나온다."* 2패스(고쳐쓰기)가 이렇게 답한 것이다 — 소감 한 문단 + 구분선 + 본문.
`strip_summary_header` 는 `**갱신된 요약**` 계열만 떼므로 그 서두가 그대로 저장됐다.

프롬프트 금지 문구로는 못 막는다 — **코드가 자른다**(불변식 7의 태도).
`strip_meta_preamble` 은 구분선이 있으면 **마지막 조각**을 본문으로 보고, 남은
문단 중 검토 소감을 버린다. 어휘만으로 자르지 않는다: '검토 결과 …' 로 시작하는
**진짜 보고 문장**이 있을 수 있어 **스레드 번호 인용 여부**를 함께 본다. 소감밖에
없으면 빈 문자열을 돌려주고 호출부가 초안으로 되돌아간다(2패스는 되면 좋은
것이지 필수가 아니다).

**이미 저장된 회고 파일은 그대로다** — 그 날짜의 AI 회고를 다시 돌리면 정리된다.

### 7.10 보안

- stdlib `http.server`, 의존성 0, **`127.0.0.1` 바인딩만**
- CSP — 원격 이미지(추적 픽셀) 기본 차단, 인라인 스크립트 차단(`script-src 'self'`)
- POST Origin 검사
- **원격 이미지는 브라우저가 받는다**(2026-08-15) — 서버는 소켓을 열지 않는다.
  저장 HTML 에는 `data-blocked-src` 로 URL 만 남고, 배너의 [⚠ 위험을 감수하고
  보기]가 `/thread/<id>?images=1` 로 **전체 페이지 이동**하면 그 응답에만
  `CSP_IMAGES`(= `img-src` 하나만 푼 완화본)를 실어 `src` 를 되돌린다. 저장분은
  그대로라 다음에 열면 다시 차단 상태다. 감수하는 위험은 명시한다 — 추적 픽셀이
  발사되고 그 도메인으로 쿠키가 간다(서버가 받을 때는 안 갔다). 리퍼러는 전역
  `Referrer-Policy: no-referrer` 로 여전히 막히고, 스크립트·외부 CSS 도 그대로
  막힌다. **선언 치수 5px 미만은 되살리지 않는다**(`_IMG_MIN_PX`) — 추적 픽셀만
  살아나면 차단의 목적이 무너진다. 링크에 `imgshow` 클래스를 두는 이유: app.js 의
  패널 주입은 이미 받은 문서의 CSP 를 못 바꾸므로 **가로채기에서 빼야** 한다.

  이 자리에 서버 프록시(`/imgproxy` + SSRF 하드닝 + 캐시·워커)를 잠깐 두었다가
  걷어냈다. 사내망이 직접 egress 를 막아 프록시 경유가 필요했는데, 프록시를
  거치면 목적지 IP 를 프록시가 해석해 피어-IP 검사의 근거가 사라지고 PAC·프록시
  인증·사내 루트 인증서가 줄줄이 따라온다. 얻는 것(뉴스레터 배너·로고)에 비해
  비용이 크고, 업무 그림은 첨부·cid 로 이미 보인다. **방어를 낮춰야만 되는
  기능은 넣지 않는다** — 그 결정으로 서버의 아웃바운드가 0 으로 돌아왔다.
- 메일 HTML은 저장 시 정제하고 CSP로 다시 막는다(이중 방어)
- 단일 스레드 `HTTPServer`가 의도다 — Outlook COM은 스레드마다
  `CoInitialize`가 필요하고, sqlite 스레드 규칙도 함께 피해 간다. 로컬 1인 도구 전제.

### 7.11 앱 창과 서버 수명

`serve --app`(Edge 앱 창)은 **창과 서버가 함께 산다** — 창을 닫으면 서버가 끝나고,
Ctrl-C 로 서버를 끝내면 창이 닫힌다. 창이 곧 앱이라 한쪽만 남는 상태가 쓸모없기
때문이다. 아이콘 실행기(`launch_minerva.pyw`)도 같은 계약을 노렸지만 아래 이유로
성립하지 않았고, 지금은 **옛 서버 종료 + `serve --app` 시작**만 하고 빠진다 —
창 열기와 수명 관리는 서버 한 곳에 있다.

**창이 열려 있는지는 페이지가 알린다.** 창 프로세스를 붙잡아 감시하는 방법을 먼저
만들었지만 Windows 실측에서 무력했다 — Edge 는 창을 이미 떠 있는 인스턴스에 넘기고
우리가 띄운 프로세스는 0.0초 만에 끝난다(전용 프로필을 줘도 그렇다). 한 번도
성립하지 않으면서 실패 보고 두 줄만 매번 찍었으므로 **통째로 걷어냈다**(전용 프로필
`--user-data-dir` 도 그 감시 때문에 있었으므로 함께 뺐다 — `serve --app` 은 다시
사용자의 기본 Edge 프로필로 뜬다).

- 페이지가 뜨면 `/appwin` 으로 app 모드인지 묻고, 맞으면 자기 id 로 `open` 을 등록한 뒤
  4초마다 `beat` 을 보낸다. 떠날 때는 `pagehide` + `sendBeacon` 으로 `bye`(창 크기
  기억이 이미 쓰는, 검증된 경로다).
- **이 스크립트는 `_head` 가 모든 문서에 싣는다**(`/appwin.js`). `<!doctype` 이
  이 패키지에서 `_head` 한 곳뿐이라, "모든 문서가 참여한다"가 관례가 아니라
  구조적 사실이다 — 앞으로 생길 전폭 페이지도 자동으로 딸려 온다.
  **`app.js` 안에 두면 안 된다**: app.js 는 좌/우 셸이 있는 문서에서만 돌고
  (`if (!left || !right) return`), 통계처럼 셸 없는 전폭 페이지는 app.js 를
  싣지도 않는다. 2026-08-10 에 정확히 그 구멍으로 사고가 났다(아래).
  예외는 **403 차단 페이지 하나**(`_page(appwin=False)`) — 그 HTML 은 남의
  오리진 탭에서 렌더되므로 창을 등록시키면 진짜 창을 닫아도 서버가 안 죽는다.
- 서버는 열린 창 id → 경로 표를 들고 있다가 **집합이 비고 유예(5초)가 지나면**
  내려간다. 새로고침·이동은 `bye` 직후 새 id 로 다시 등록되므로 종료로 세지 않고
  (로그가 `앱 창 교대: /mail → /stats` 로 그 인계를 보여 준다), 창이 둘이면
  하나를 닫아도 집합이 비지 않는다. 한 번도 등록되지 않았으면(옛 캐시 JS·JS 꺼짐)
  조건이 성립하지 않아 **모르면 안 내리는 쪽**으로 실패한다.
- 반대 방향은 페이지가 맡는다 — `beat` 이 연속 2회 실패하면 서버가 사라진 것이므로
  창이 스스로 닫히고, 못 닫는 브라우저에서는 종료 안내를 덮어 죽은 화면을 남기지
  않는다(`.srvgone`). 이제 통계 페이지에도 beat 이 있으므로 여기서도 동작한다 —
  종전에는 그 페이지만 죽은 서버를 눈치채지 못했다.
- `bye` 는 `event.persisted` 를 보지 않고 **무조건** 보낸다. bfcache 라고 건너뛰면
  그 id 가 영영 남아 진짜로 창을 닫아도 집합이 안 비고 **서버가 영영 안 죽는다**
  (bfcache 항목은 예고 없이 폐기되고 그때는 아무 이벤트도 안 온다). 지금은 모든
  HTML 이 `no-store` 라 크로미움이 bfcache 에 넣지 않으므로 이 문제 자체가 없다 —
  `no-store` 를 걷어내게 되면 `pageshow{persisted}` 재등록이 필요해진다.

**2026-08-10 사고 — 통계 페이지가 창 수명에서 빠져 있었다.** 증상: "창이 안
닫혔는데 서버가 죽었다", 재현은 "통계로 들어가서 5–6초". `/stats` 는 SPA 링크
가로채기의 **문서화된 예외**(전폭 레이아웃)라 진짜 이동이 일어나 나가는 문서가
`bye` 를 보냈는데, 새 문서는 app.js 를 안 실어 `open` 을 영영 못 보냈다. 유예
5초 + 틱 1초 = 정확히 그 시간. 게다가 그 페이지엔 beat 이 없어 창이 스스로
닫히지도 못했다. 고친 것은 한 페이지가 아니라 **불변식**이다 — 종전 규약
"SPA 문서는 app.js 를 싣는다"는 예외를 허용했고, 지금 규약 "모든 문서는 창 수명
프로토콜에 참여한다"는 `_head` 가 유일한 문서 시작점이라 예외를 허용하지 않는다.

**로그는 현상을 그대로 말한다.** 초판은 "창을 닫아도 서버는 유지됩니다"라고 찍어
놓고 실제로는 종료됐다(죽은 감시 경로만 보고 판단했다). 지금은 시작 한 줄
(`앱 창 모드 — 창을 닫으면 최대 6초 뒤 서버가 끝납니다`), 실제 종료에 걸린 시간
(`앱 창이 모두 닫혔습니다(5.4초 전) — 서버를 종료합니다`), Ctrl-C 한 줄
(`종료 — 앱 창은 최대 8초 안에 닫힙니다`)뿐이다. 뒤 꼬리는 **등록된 창이 실제로
있을 때만** 붙인다(`_app_win_open`) — 없는데 붙이면 또 거짓말이다. 수치는
`_app_close_sec`/`_app_quit_sec` 가 상수에서 계산하므로 주기를 바꿔도 안내가
따라간다(테스트가 파이썬 상수와 `appwin.js` 값을 묶어 둔다).

비용: beat 1회가 서버 CPU 0.10ms·왕복 0.23ms(2026-08-09 WSL 실측). 창 하나가
하루 종일 떠 있어도 서버 CPU 2.2초(0.002%)로, 기존 `/latest` 60초 폴링(회당
0.80ms — DB 를 연다)보다 회당 8배 싸다. 백그라운드 창은 브라우저가 타이머를
분당 1회로 조여 더 낮아진다.

정지는 강제 종료가 아니라 `httpd.shutdown()` 이라 `serve_forever` 가 정상 반환하고
뒷정리(keepalive 연결·PID 파일·COM 해제)가 그대로 돈다. `--open`(사용자 브라우저
탭)은 이 계약 밖이다 — `/appwin` 이 0을 주므로 페이지가 아무것도 하지 않는다.
`_Handler.app_mode` 는 클래스 속성이라 `serve` 가 **매번 덮어쓴다**(앞선 app 서버의
값이 남으면 일반 서버의 페이지까지 창 수명 관리를 켠다).

### 7.12 설정 › AI 백엔드 상태 — 웹이 답할 수 없는 것만 (2026-08-19/20)

`doctor` 는 설치 시점 CLI 도구로 태어났는데, 실사용 진입점은 `serve --app` 창
하나다. 회사 PC 에서 터미널을 여는 건 사실상 설치 한 번뿐이라 **백엔드가 실제로
대답하는지를 사용자가 확인할 길이 없었다**(`web.py` 에 `doctor` 라는 낱말이 한 번도
없었다). 그래서 백엔드를 고르는 표 바로 아래에 상태 절을 세웠다.

**doctor 전체를 옮기지는 않았다.** 첫 판은 그렇게 만들었다가 걷어냈다 — 이 화면이
보인다는 것은 **이미 웹이 떴다**는 뜻이라 Python·tomllib·Outlook COM·config.toml·
DB 유무는 스스로 답이 돼 있고, 그 줄들이 화면을 채우면 정작 봐야 할 한 줄이 묻힌다
(2026-08-20 사용자 지적: *"이미 web 이 떴는데 억지로 만들 필요는 없다"*). 런타임에
남는 물음은 하나다 — **어느 모델이 실제로 대답하는가.**

    ● 응답    sonnet    claude    요약·회고 · AI 검색 · 분석 · 주간   OK
    ■ 실패    haiku     claude    미사용        model 'haiku' is not available
              → 그 CLI 가 이 모델을 부를 수 있는지…
    ▲ 무응답  opus      claude    현안 브리핑   30초 안에 응답 없음
              → 느린 백엔드일 수 있으니 한 번 더…
    ·  없음   internal  opencode  미사용        PATH 에 없습니다
    [응답 시험]  AI 3콜 — 실제로 불러 봅니다(없는 것은 안 부릅니다)

- **역할이 쓰는 것만 보여 주지 않는다.** 백엔드를 바꾸려는 사람이 알고 싶은 것은
  "지금 무엇을 고를 수 있나"이고, 그건 안 쓰는 모델(haiku)까지 물어봐야 안다.
  역할 열은 `config.backend_for` 한 곳에서 온다 — 화면이 엔진과 갈라지지 않게.
- **없는 것은 경고가 아니라 사실이다.** opencode 는 안 깔린 것이 보통이고 안 쓰면
  무방하다. `· 없음` 으로 흐리게 적고 처방을 붙이지 않는다 — 매번 눈에 걸리는
  경고는 배경음이 된다(doctor 가 `internal (ask·weekly)` 로 냈던 그 경고다).
- **PATH 검사로는 부족하다.** `doctor` 는 실행 파일이 있는지까지만 본다. claude
  CLI 는 모델마다 권한이 다를 수 있어(현안 브리핑의 기본이 opus 다) 불러 봐야
  안다. 실패 줄은 **무엇이 안 되는지를 역할 이름으로** 말하고(`opus (현안 브리핑)`),
  원문 오류를 그대로 싣고, 위 표에서 바꾸라는 처방을 붙인다.
- **'안 된다'와 '늦는다'를 가른다**(2026-08-20). PATH 에 있어도 동작하지 않는
  백엔드는 30초(`_AITEST_TIMEOUT`)를 다 쓰고 끝난다 — `subprocess.run(timeout=)`
  이 자식을 죽이고 `review.AITimeout` 이 오른다(`AIError` 하위라 재시도·삼킴
  경로는 그대로다). 그걸 '실패'로 찍으면 사내 게이트웨이를 거쳐 느린 CLI 가
  고장으로 읽히고 처방도 엉뚱해진다. 그래서 상태는 넷이다 — **응답 · 무응답 ·
  실패 · 없음**. 무응답의 처방은 모델 지원 여부가 아니라 느림·로그인·프록시를
  짚는다. 터미널의 `mailkb diagnose` 도 같은 어휘를 쓴다.
  최악 대기는 30초 × PATH 에 있는 백엔드 수이고, 그동안 서버는 멈추지 않는다
  (잡 스레드 + 3초 폴링). 재시도는 하지 않는다(`retries=0`) — 점검이 백오프까지
  돌면 사람이 화면 앞에서 기다리는 시간이 배가 된다.
- **[응답 시험]은 백그라운드 잡.** 절 자체는 호출 0 이고(PATH 조회뿐), 실제 호출은
  누를 때만 나간다. PATH 에 있는 백엔드마다 1콜이라 요청 스레드에서 돌리면 단일
  스레드 서버가 그동안 멈춘다 — 지식 저장·인물 브리핑과 같은 판례다. 마커는
  `data-aitest-running`, 폴링은 `/settings/status`(좌측 패널 — §7.9 의 3자 일치).

백엔드마다** 짧은 시험 호출을 보낸다(`cli.py`의 `[AI 백엔드]` 절 — 기본 설정이면
sonnet·opus 2콜). 플래그 유무가 아니라 이 표의 AI 열을 기준으로 판단한다.

`serve`는 명령 자체로는 호출이 0이다 — **예외 없다**(원격 이미지도 서버가 받지
않는다, §7.10). 웹 UI를 열어 두는 것만으로는 AI가 돌지
않는다 — 화면을 열 때 배경에서 도는 일간 회고 자동 생성은 `ai=False`로 결정론
층만 만든다(`_maybe_auto_review`). AI는 **사용자가 누를 때만** 나간다: 분석 질문 ·
AI 회고 버튼 · 주간 보고(AI) · AI 검색 · 인물 AI 요약 · 메일 분석 · 스레드 쟁점 분석 ·
암묵지 [지식으로 저장](저장 시 보강 1콜 — §6.6b) · 설정 › AI 백엔드 상태의
[응답 시험](PATH 에 있는 백엔드마다 1콜 — §7.12).

메일 분석(2026-07-30)은 스레드 화면의 메일별 '분석' 버튼 — 그 메일+스레드를
seed 로 분석 엔진(ask)을 돌리되 범위를 잠그지 않아 관련 스레드로 확장한다
(`ask.analyze_mail`). 결과는 ask_cache 에 영구 저장돼 분석 이력에 나타나고,
머리글이 '분석 보기 · N일 전 · 이후 새 메일 M통'으로 낡음을 알린다. 제거된
회신/기한 신호의 '이 메일이 뭘 요구하나'를 온디맨드로 대체하는 기능이다.

스레드 쟁점 분석(2026-08-09)는 스레드 머리(4통 이상일 때만)의 '쟁점 분석' 버튼 —
스레드 전체를 seed 로 같은 엔진을 돌리되 인물 브리핑처럼 **범위를 잠근다**
(`ask.map_thread`, lock_scope=True). 쟁점 분석의 계약은 "이 스레드 안에서 누가
무엇을 말했나"라, 범위가 열리면 다른 스레드의 문장이 '사람별 입장' 인용으로
통과해 분석이 오염되기 때문이다. 저장·낡음 표시·다시 만들기는 메일 분석과
같은 문법(scope=thread:<id>)이다.

분석의 골격(쟁점명·상태·경위)은 answer 산문이 아니라 **전용 필드 `issues[]`**
에 담는다. 상태 판정("합의됐다")은 여러 메일을 종합한 문장이라 보수적 검증기가
인용 미지지로 기각하고, 재작성·`_safe_answer` 폴백이 answer 를 갈아끼우며
구조가 소실됐기 때문이다(2026-08-09 실측 — headline 이 같은 이유로 전용
필드인 것과 동일한 판례). 쟁점 등록 기준은 이견 유무가 아니라 **"결론이
필요했는가"**(①결론을 요구하며 제기 ②누군가 다룸 ③상태를 물을 수 있음 — 단순
공유·통보·발단 보고는 제외), 상태 어휘는 합의·해소·진행 중·보류·평행선 다섯.
코드가 강제하는 것: 검증 통과 claim 이 0이면 issues 도 내지 않고
(`_clean_issues`), 상태는 어휘 밖이면 비우며, 근거-쟁점 연결(claim 의 `issue`
번호)은 인용 검증을 통과한 claim 에만 실린다.

인물 요약은 2026-07-29 까지 일간 회고 파이프라인에 얹혀 있었다(회고가 돌 때마다
상위 15명 중 낡은 6명을 배치 갱신). 하루 정리와 인물 카드 유지보수는 성격이 다른
일이라 한 버튼의 비용·시간에 묶여 있을 이유가 없어, **인물 화면의 '요약 갱신'
버튼**으로 분리했다(`distill.refresh_person_dossier`, 1인 1콜). 대신 자동 신선도가
사라지므로 카드 푸터가 경과일과 반영되지 않은 새 메일 수를 함께 보여준다.
`DOSSIER_VALIDATOR_VERSION` 을 올려 옛 카드가 숨겨졌을 때도 화면이 다시 만들기를
안내한다 — 배치가 없으니 그것이 유일한 복구 동선이다.

## 9. 검색 DSL

| 표현 | 의미 | 예 |
|---|---|---|
| 일반 단어 | 제목·본문 | `납기 검토` |
| `"정확한 구"` | 연속 구 | `"최종 승인"` |
| `from:` `to:` `cc:` | 사람 (이름은 공백 무시, `@` 있으면 주소) | `from:강미래` |
| `after:` `before:` `on:` | 날짜 (`YYYY` \| `YYYY-MM` \| `YYYY-MM-DD`) | `after:2026-01` |
| `is:` | `unread` `read` `sent` `received` `flagged` | `is:unread` |
| `has:attachment` | 첨부 있음 | |
| `file:` | 첨부 파일명 | `file:schedule.xlsx` |
| `thread:` | 특정 스레드 | `thread:42` |

`after:`는 이상(포함), `before:`는 미만(배타). **OR 문법은 없다** — 필요하면
여러 번 검색한다.

### 완화 tier

정밀 → 느슨 순으로 내려가며 `limit`을 채운다. `--json`의 `tier` 필드로 노출된다.
**tier 가 1차 정렬키**이고, 같은 tier 안에서는 `bm25(fts, 3.0, 1.0)`(제목:본문 = 3:1)
→ 최신순이다. 시간 감쇠 블렌드는 넣지 않았다 — 지금은 동점일 때만 최신이 이긴다.

| tier | 방식 |
|---|---|
| 0 | 본문 검색어 없이 필터만 |
| 1 | 연속구 |
| 2 | FTS AND |
| 3 | LIKE AND (부분일치) |
| 4 | FTS OR — **유일한 '관련 낮음'** |

**trigram FTS는 3자 미만 토큰을 색인하지 못한다.** 그래서 2자 이하 한국어
키워드는 `LIKE`로 우회하고, 인접한 2자 단어는 구(phrase) tier로 회수한다.

## 12. 장기 과제 — `forget` (본문 지우기)

**만들지 않았다.** 2026-08-09 설계 조사만 했고, 필요해질 때 여기서 이어 간다.
지금은 §6.8(사라진 메일 표시)까지만 있다.

### 왜 미뤘나

이 앱에서 **유일하게 되돌릴 수 없는 동작**이 되는데, 조사해 보니 한 통의 내용이
**22곳**으로 흘러간다. 하나라도 빠지면 "지웠다"가 거짓말이 된다. 그리고 실제로
그런 요구가 있는지(회사 메일 중 로컬 DB 에서도 반드시 지워야 하는 건)가 아직
확인되지 않았다. 되돌릴 수 없는 기능은 안 만드는 것이 기본값이어야 한다.

### 조사 결과 — 내용이 남는 곳

| 계층 | 위치 | 무엇이 |
|---|---|---|
| 메일 | `messages` · `message_html` · `messages_fts` | 본문·제목·발신자·수신자 |
| | `message_term_bags` · `_features` · `_subject_delta` · `message_features` | 본문에서 뽑은 어휘·신호 |
| | **`reclean_backup`** | **인용 절단 전 원본 전문**(45일) |
| 스레드 | `threads.rolling_summary` | AI 가 본문으로 쓴 산문 |
| | `knowledge_candidates.quote` · `distill_signals.quote` | **원문 인용 그대로** |
| | `intervention_ai` · `thread_state` · `action_overrides` | AI 문장 · 파생 상태 |
| 인물 | **`people_dossier.dossier_md`** | **인용 포함 — 메일 연결 키가 없다** |
| | `people_word_profiles` · `person_term_window` | 어휘 |
| 캐시 | **`ask_cache.result_json`** | **claim 마다 인용 원문**(실측 확인) |
| | `ai_search.result_json` | 검색 결과 |
| 파일 | `vault/daily/*.md` · `weekly/*.md` | 회고·보고서 안의 인용 |
| | **`logs/harvest.jsonl`** | **모델 원문 출력 8000자 그대로** |
| 밖 | Outlook 원본 · 이미 AI 로 나간 프롬프트 | 회수 불가 |

### 조사가 결정한 것 둘

**① 행을 지우면 안 된다 — 묘비여야 한다.** `store._insert` 의 중복 판정이
`SELECT 1 FROM messages WHERE message_id=?` 다. 행을 통째로 지우면 다음
`sync --full` 이 그대로 되살린다. `message_id`·`thread_id`·`sent_on`·`is_sent`·
`purged_at` 만 남기고 비우는 것이 유일한 정답이다. 부수 효과가 오히려 좋다 —
스레드 구조가 안 깨지고 "여기 뭔가 있었다"가 남는다.

**② 파일은 코드가 지우면 안 된다.** `vault/daily/*.md` 는 AI 산출물과 사람이 쓴
노트가 섞인 파일이고 `logs/harvest.jsonl` 은 감사 기록이다. 목록으로 알려주고
사람이 지우는 것이 정직하다.

### 만든다면

- `mailkb forget <스레드ID>` 는 **기본이 미리보기**다. `--yes` 없이는 아무것도
  안 지운다. 미리보기는 지우는 것·남기는 것·코드가 못 지우는 파일 목록을 전부 적는다.
- **저장된 지식은 기본으로 지우지 않는다.** 사람이 승인한 유일한 자산이라
  조용히 지우면 기록이 "그런 지식은 없었다"고 거짓말한다. DB 쪽은 인용문만
  지우고, 파일(`vault/knowledge/`)은 코드가 지우면 안 되는 목록에 올린다
  (위 ② — 없던 일로 만들지 않는다).
- **인물 요약은 부분 삭제가 불가능하다**(주소로만 연결). 참여자 카드를 통째로
  무효화해 다시 만드는 수밖에 없다.
- 웹 UI 에는 넣지 않는다(처음에는). 오클릭이 쉽고 미리보기를 읽게 만들기 어렵다.
- **검증**: 스레드를 넣고 `forget` 한 뒤 **DB 전체를 훑어 그 본문 문자열이
  어디에도 안 남았는지** 확인하는 전수 대조 테스트. 테이블을 새로 추가해도
  이 테스트가 잡는다. 그리고 `sync --full` 후에도 되살아나지 않는지.

### 그래도 못 하는 것

이미 AI 백엔드로 나간 프롬프트는 회수할 수 없다(사내 LLM 이면 그쪽 로그 정책을
따로 확인). Outlook 원본은 그대로다. SQLite 는 `VACUUM` 을 함께 돌려도 디스크
수준 복구까지 막지 못한다 — 그 수준이 필요하면 `data/` 를 지우고 다시 수집하는
것이 맞다.

## 13. 장기 과제 — 인라인 SVG 렌더링

**만들지 않았다.** 2026-08-15 범위 조사만 했고, 필요해질 때 여기서 이어 간다.
지금은 §6.1 정제 2단계에서 svg 를 통째로 버리되 "🖼 다이어그램 생략(SVG)" 한 줄을
남기는 데까지만 있다(무흔적 삭제가 "이미지가 안 나온다"는 문의로 돌아왔다).

### 왜 미뤘나

정제기는 이 저장소에서 **가장 위험한 표면**이다 — 메일 HTML 은 통제 밖 입력이고,
SVG 는 그림 파일이 아니라 **스크립트를 담을 수 있는 문서**다. `<foreignObject>`
하나만 빠뜨려도 SVG 안에서 HTML 로 되돌아가는 문이 열려 정제 전체가 우회된다.
작업량 자체는 크지 않지만(대부분 허용목록 나열) 검토 밀도가 필요한 종류다.

그리고 **실제 빈도를 모른다.** 저장 시점에 정제한 HTML 만 남기고 원본은 안 갖고
있어서, 과거 메일에 인라인 SVG 가 몇 번 나왔는지 되짚을 방법이 없다. Outlook 이
다이어그램을 이미지로 변환해 보내는 경우가 많아 첨부·cid PNG 는 지금도 잘 나온다.
**판단 근거는 재수집 후 위 placeholder 줄이 실제로 자주 뜨는지** 하나다.

### 조사 결과 — 손댈 곳

| 위치 | 무엇을 |
|---|---|
| `clean.py` `_DROP_TREE`/`_ALLOWED_TAGS` | svg 를 옮기는 것만으로는 **껍데기만 남는다** — 자식 태그·속성이 전부 허용목록 밖이라 그대로 버려진다 |
| `clean.py` (신설) | SVG 전용 허용목록 2벌 — 태그 25–30개(`path·g·rect·circle·line·polyline·text·tspan·defs`…), 속성 50–60개(`d·viewBox·fill·stroke·transform·x·y·width·height`…) |
| `clean.py` `_Sanitizer` | "지금 svg 안인가" 분기 4곳 — `handle_starttag`·`handle_startendtag`·`handle_endtag`·`_attrs`. 닫는 태그 경로가 빠지면 `<path></path>` 형태에서 중첩이 깨진다 |
| `web.py` `_CSS` | 다크 모드 `.mailhtml svg` 규칙 2–4줄 (아래) |
| `store.py` `_prune_html` | "이미지 있었음" 카운트에 `<svg` 포함 1줄 (아래) |
| `tests/` | 렌더 통과·위험 태그 차단·다크·프룬 8–10건 |

**반드시 버리는 것**: `<foreignObject>`(HTML 재진입 = 정제 우회) · `<use>`/`<image>`
의 `href`·`xlink:href`(외부 참조 = 추적 픽셀·유출) · `<animate>` 계열 · `on*`
(기존 필터가 이미 잡는다) · `<script>`·`<style>`(이미 `_DROP_TREE`). style 태그를
버리는 대가로 CSS 클래스로 정의된 그라디언트·색은 깨진다 — 그림은 나오되 단색이
되는 식이고, 그 편이 CSS 정제기를 새로 짜는 것보다 낫다.

### 조사가 확인한 것 셋

**① 대소문자는 문제가 아니다.** `html.parser` 가 이름을 소문자로 접지만
(`viewBox`→`viewbox`, `linearGradient`→`lineargradient`) **브라우저가 HTML5 파싱
때 되돌린다**(SVG 이름 보정표). Chrome `--dump-dom` 실측:

```
정제기 출력 형태  <svg viewbox="0 0 100 50"><lineargradient id="g">
브라우저 DOM      <svg viewBox="0 0 100 50"><linearGradient id="g">
```

인라인 HTML 경로에서만 성립하는 성질이고, 우리가 그 경로다(XML 로 내보내면 깨진다).

**② 다크 모드에서 안 보인다.** §7.8 의 평탄화는 `.mailhtml *` 에 `color` 를
덮어쓰는데, SVG 의 선·면은 `color` 가 아니라 `fill`/`stroke` 속성이다. 흰 배경
전제로 그려진 검은 선 도형이 어두운 배경 위에 그대로 남는다. `.mailhtml svg` 전용
규칙이 필요하다(이미지에 예외를 준 선례가 바로 옆에 있다).

**③ 보존 기간 뒤 조용히 사라진다.** `store._prune_html` 은 "이미지가 있었다"를
`data:image/` 와 `data-blocked-src="cid:` 로만 센다 — SVG 만 있는 메일은
`image_retain_days` 경과 후 **마커 없이 행이 통째로 삭제**된다. 지금 고친 것과 같은
종류의 무흔적 소실이라 카운트에 함께 넣어야 한다.

### 만든다면

- **표시 우선 최소 집합부터** — 도형·텍스트·그룹·transform. 이것만으로 블록
  다이어그램은 대부분 나온다. 그라디언트·필터·마스크·패턴은 필요가 확인된 뒤에.
- `_SKIP_TAGS` 의 svg 는 **그대로 둔다.** 그림을 보여주는 것과 라벨 조각을
  검색·AI 본문에 싣는 것은 별개고, 후자는 여전히 안 싣는 것이 맞다("매출 3억"
  같은 조각이 문맥 없이 서사에 섞인다 — 2026-08-15 에 닫은 유출).
- placeholder 는 남긴다 — 정제로 전부 걸러진 경우엔 여전히 흔적이 필요하다.
- CSP 는 무관하다(인라인 SVG 는 `img-src` 대상이 아니고, 외부 참조는 버린다).

### 그래도 못 하는 것

**저장된 메일에는 소급되지 않는다.** 원본 HTML 을 보관하지 않으므로 이미 정제된
SVG 는 복원할 수 없다 — 재수집분부터 유효하다(§5 재수집 강요 금지와 상충하지
않는다: 안 해도 지금 동작이 유지될 뿐이다).

서명에 로고를 SVG 로 넣는 발신자가 있으면 매 메일 하단에 로고가 그려진다.
`hide_image_signatures` 는 base64 PNG 만 보기 때문이다(§6.1). 실제로 흔한지는
역시 재수집 후에야 안다 — 흔하면 서명 판정에 svg 를 함께 넣는다.
